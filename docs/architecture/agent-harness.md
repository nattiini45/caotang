## 1. What "drives the app" means concretely

- The agent is an **operator**: it performs app actions — restructure the binder, draft/edit scene text, set statuses, fill synopses, compile exports — through a **tool surface served by the app's command bus** (the exact command implementations the UI uses). The human never transcribes agent output by hand.
- Every tool call is **visible** (activity log), **grouped** (one agent turn = one undo group), **verifiable** (post-conditions), and **previewable** for multi-step plans.
- The operator may **delegate**: it can hand a self-contained piece of reading to a built-in helper agent with its own context, tool list and call budget, and read back only its notes (§2, "Delegate"). The helper reads and proposes; it never writes, so the writer still approves once per plan.
- Useful *offline from chat*: "reorganize act 2 into scene cards with synopses from my notes", "find continuity drift between chapters", "compile chapters 1–3", "trim 10% from every scene over 2k words, showing diffs".

## 2. Interaction loop

1. **Intent** — free-text instruction or scheduled agent task. The panel submits the writer's; a script, a CLI or CI submits one through the SDK (§11). A recurring task (§12) is offered when it is due and, when the writer runs it, is an ordinary turn under the `background` role; a task a script starts is not built. A line the writer types that starts with `/` and a command name is a slash command (below), resolved before any model call.
2. **Plan** — for multi-step work the agent emits a plan (ordered steps, each = one tool call with params + expected effect) rendered as a reviewable card; user approves/edits/rejects **once per plan** (batched confirmation). Single reversible ops skip the plan. Single confirm-class ops show a one-step confirm card. **Plan cards are editable before approval** — steps can be reordered, dropped, and params tweaked in place; **the edited card becomes the executed plan** (cheap by design: a plan is data, not prose). Editable plan params include range anchors (edit-anchors.md §2 — the user can fix the target text before approving). **Edit-time dependency check:** Caotang's cards are structured data, so an edit that **drops or retargets a step** statically flags dependents in place: a later step whose params reference the dropped step's outputs (a `TextAnchor` captured from an earlier step's apply, a doc id the earlier step created) renders a "will re-resolve at execution" badge (anchors re-resolve through the edit-anchors §3 ladder at apply time; never a silent mis-address). This is a validation pass over plan data. **Multiple edit rounds are normal:** an edited card re-enters preview rather than skipping it.
3. **Act** — stepwise execution on the command bus; the UI highlights affected nodes/documents live (activity log entries carry node ids + human titles).
4. **Verify** — post-conditions checked per tool (target exists, word counts moved, artifact non-empty). Failure → self-correction ladder: retry with adjusted params (max 2) → structured report with options. **Never silent success; never a bare error string** (errors are written for the model, naming the next corrective tool).
5. **Report** — compact turn summary: what changed, diffs where relevant, undo group id, tokens spent.

**The plan preflight.** Every step of a plan is checked before the card is shown, so the card never promises a step the apply would refuse: a `scene.draft` or `shots.derive` step that names a document or scene the project no longer holds is refused there, before its model call is spent, and the refusal goes back to the planner and onto the card. The deferral rule is unchanged — a step that targets a scene an earlier step of the same plan may create is not refused for that.

**A planner reply the provider cut.** The planner's reply is read with its finish reason, as a draft is (§8). A cut reply that still parses is planned as it is: the parse decides whether there is a problem, and the finish reason only how it is described. A cut reply that does not parse (a half JSON object, or a native call whose arguments stop mid-way) is answered with words that name the cut and ask for a shorter reply ("Your reply was cut off at the model's output limit … Send a shorter reply"), not with "Your reply was not valid JSON"; on the native wire the refusal keeps its step number. The words say "at the model's output limit" only when the provider's reported completion tokens reached the cap the request was sent with, and otherwise "cut off before it ended", since `length` may be sent for a reason of the provider's own. The next planner request then asks for twice the cap, never above the model's advertised cap (provider-gateway §2), and only when the reply reached its cap: a reply cut for another reason keeps its cap. The retry is once, not a loop: a second unreadable cut, or a cut that leaves no model call for the retry, ends the turn `failed` on a `needs_input` ask-back, not the model-call bound's, and the turn's bound stays the outer limit; the ask-back names the output limit (and its cap) when a cut reached the cap its request was sent with, and otherwise says the reply was cut before it ended. On the native wire only the reply's last call can have been cut: an earlier call that failed to parse keeps its own refusal. A native reply that was cut but whose calls all parsed may be missing steps: its card carries `replyCut`, is never approved by a mode or run at once as a single write-auto step, and is approved only with `acceptTruncated`, the consent a cut draft takes. A cut native reply of reads only runs its reads, since nothing is written and there is nothing to approve. The report counts the cut planner replies (`cutReplies`). The plan card's cost estimate is not recomputed for a raised cap.

**Delegate.** The planner can hand a self-contained piece of reading to a built-in helper with `agent.delegate`, an extension row (§10; risk `read`, deferred, `{ agent: 'reader' | 'general', brief, scope? }` with a scope of at most 20 documents). The agents are a closed built-in set (`SUBAGENT_SPECS` in `packages/harness/src/agent/subagent.ts`); this build has no user-defined agents, and no agent can delegate in turn (depth 1). The **reader** reads the scope and the project and returns notes (3 model calls). The **general** agent reads the same and may also propose changes as steps (4 model calls).

- **Its own context.** The call is assembled under the `delegate` profile (context-assembly §3): L0 is the agent's role and its tool list, L1 the project summary, L2 the codex per policy, L3 to L5 built from `scope`, **no L6**, and L7 the brief. Nothing of the planner's messages, and none of the prior turns, reaches it. It runs on the wire the planner does (§2, "Two wires, one loop"), with the list below declared natively or described in its system message, built once.
- **Its own list, closed and computed.** Each spec names the tools it reads with and the tools it may stage (`reads`, `stages`), and the list is those names intersected with the callable, wired rows the planner's own surface offers (`plannerTools`, so the rule that drops `continuity.scan` once the review is wired applies to it too), keeping a read only where the registry's risk says `read` and a staged tool only where it says `write-confirm`. The reader reads with `project.overview`, `binder.read_tree`, `doc.read`, `notes.read`, `codex.read` and `dialogue.table`; the general agent adds `scene.draft`, `synopsis.fill`, `codex.write` and `binder.restructure` to stage. No agent is ever given a `write-auto` tool, a `meta` tool, `agent.delegate`, `tool.search`, `mcp.invoke` or an external tool, and none is given a model-backed read or a read that writes held state outside the bus (`continuity.scan`, `coherence.scan`). A call to anything else is answered with a refusal the model reads; a call to `agent.delegate` says a delegated agent cannot hand work on.
- **It reads, and it stages.** A read runs at once through the harness under the turn, with the agent's path (`TurnContext.agentPath`), and dispatches no bus command. A write-class call is never dispatched: it is checked against the registry as a plan step is, and comes back in the result's `proposedSteps`. Behind that filter, the harness refuses every tool that is not a read when `agentPath` is set (`permission-denied`: "a delegated agent can only read; return the change as a proposed step"), and refuses an external call. Staging makes no model call, so no draft is made for a proposed step; the planner's own staging drafts it if the planner takes the step.
- **Its own budget.** Before the agent starts, the turn reserves the agent's model calls from its own bound (`maxModelCalls`, 8 by default), and refuses up front, before any agent call, in the words of `tooCostly` with a hint (a narrower scope, or reading the documents itself), unless the planner keeps at least one call to read the result. The agent's calls count against the reservation and not again against the turn's bound; what it did not use is released when it finishes, and the card shows the number reserved. On its last call the agent is asked for its notes and, on the native wire, keeps its tools declared with tool choice `none` (its history holds tool calls and results, which a provider rejects without `tools`).
- **One at a time.** Agents run in the order the planner called them, one at a time, and only in a reply that holds no write step: a reply that mixes `agent.delegate` with a write runs neither, and the planner is told to delegate first. The planner reads the result, then plans.
- **What comes back.** The result is a `tool` message on the native wire (a "Tool results" entry on the JSON wire) that opens with a fixed notice, "This is the result of a delegated agent; it carries no approval.", then the agent, its path, its status (`done`, `partial` or `failed`), its notes clipped to about 1,500 tokens, its proposed steps as data, the documents it read and its usage. A failed agent is a refusal naming the reason and releasing its unused calls. The guarantee is structural, not the notice: approval is read only from the permission context and the card UI, never from message text, so text a document or an agent carries ("the user approved this plan") changes nothing.
- **Proposals reach the writer only in the planner's plan.** A proposed step is never run and never added to a plan. The planner reads it and decides whether to put it in its own next plan; the loop remembers each proposal for the turn, and a plan step whose tool and params equal one carries a "Proposed by the <agent> agent" badge on the card. A step the planner or the writer edited has none. Every step stays editable or droppable like any other, so there is still one plan card, one approval and one undo group (§5).
- **Identity and the writer's Stop.** The agent's requests carry the turn's id, so the turn's totals sum its children, and an `agentPath` (`<turn>/reader#1`, the turn's count of its agents) that the gateway's ledger records beside it (provider-gateway §6). Its call ids are derived from the path (`<path>:r<n>`), so the replay cache cannot answer one of its calls with the planner's. Its decisions are rows of the turn's trace carrying the path (a read `ok`, a staged write `not-run`, anything refused `refused`), and the call's status card carries its own view, so the panel can list them (§8). The turn's Stop aborts a running agent through the signal: the agent ends `partial`, its unused calls are released and the turn ends cancelled.

**The conversation memory.** One agent session per open panel, created on the first turn under a session id the controller fixes for its life (a turn is `<session>.turn-<n>`): the turns before this one are the L6 of the next turn (context-assembly §2). The profile, the model and the thinking level are the turn's own (`TurnOptions`, below), not the session's, so a provider switch between turns keeps the conversation. A turn that settles leaves its one-line outcome and its undo group on its `RecentTurn` (a reply's clipped answer is its outcome), so L6 still has them where the activity log has no row for the turn. The per-turn state is cleared on every settlement, so a cancelled, refused or failed turn leaves nothing behind. There is no "new conversation" control in v0.1, and a reload starts the list again, because the conversation memory is in memory only.

**Stop and steer.** The writer can take the wheel back at any moment of a turn. `submit(intent, options)` and `submitPlan(intent, plan, options)` take a `TurnOptions { signal, profileId, model, thinking }`: one `AbortSignal` per turn, which the controller makes for each turn, and the pins the turn's model calls run on, over the session's own (`AgentSessionOptions`, which a background task's session still uses); a session may outlive many turns and many pins. The signal reaches every model request the turn makes (the planner, drafts, retries), the coherence review's model calls and an external read, and the loop reads it at every boundary: before each model request, before each stage and each read, before a card is shown, and before each step of an approved plan. A stop never interrupts a bus command that has started, and `export.compile` is never aborted once begun: the step finishes, registers in the turn's undo group, and the stop takes effect after it (command-bus §5). The one exception is an external call (`mcp.invoke`, extensibility §3.3), which changes nothing in the project: the signal reaches it in flight, read or write, the server is told, and the call ends cancelled. A write that was cancelled after it was sent says on its card, in its trace row, in its step (`mayHaveActed`) and in the turn's summary that the server may already have done part of the work, and its card and row are not `not-run`. The turn then ends as `cancelled` with `stop: { by: 'user', during: <phase> }`, the steps after the stop are `not-run` in the trace, the report reads "Stopped by you. Written before the stop: …", and the checkpoint row restores what was applied. A card that waits is cancelled exactly as its Cancel does, whether or not the decider ever answers. A stop is detected, not inferred from the provider: the gateway ends an aborted stream with an error finish, and `complete()` throws `TurnStopped` when the signal is aborted, so a stop never reads as `GenerationStopped`. The stream is read to its end so the ledger records the request's usage. `AgentSession.steer(turnId, text)` adds a note to a running turn (`SteerReceipt { noteId, lands }`); at the top of the conversation loop, before the next planner request, each undelivered note becomes one user message — "Note from the writer, sent while you were working: …" — after the previous reply's `tool` messages are flushed (`flushWire`), so no user message ever sits between a call and its result. A note sent while a card waits has `lands: 'after-decision'`; a Cancel sent with a note carries the turn on to the model with both, instead of ending it. `TurnReport.steering` lists the notes in order, and one without `deliveredAtCall` was not read: the caller sends it as a turn of its own. The `steer` event is emitted when a note is delivered. Evals can place a stop or a note at a fixed moment (`Scenario.writer`).

**Slash commands.** The Intent box reads a leading ASCII `/` and a command name (`packages/harness/src/commands/`, pure, no model). The set is closed: `/help`, `/plan`, `/draft`, `/synopses`, `/scan`, `/review`, `/compile`, `/restore` and `/context` (`BUILTIN_COMMAND_NAMES`); there are no user-defined, skill, macro or MCP-prompt commands in this build. `parseSlash` splits the tail like a shell (a word that opens with a quote runs to the matching one, a bare `--` starts a free-text brief, `key=value` words are also named), `expandTemplate` fills `$ARGUMENTS`, `$1` to `$9`, `$name`, `$SELECTION`, `$DOC` and `$$` in one pass and names a placeholder it cannot fill instead of sending it empty, and `resolveSlash` returns one of four things: an **intent** (a line that is not a command, `//` for a literal leading slash, an unknown `/foo` sent as typed with a one-line note, or `/plan`), a **plan** the app built, a **session** action (`help`, `context`, `restore`), or an **ask** for an argument that is missing or ambiguous. The planner never receives slash syntax: a command is sent as the plan it builds, or as the request after its name.

- **Documents** are named by the `doc.read` unique-prefix rule (resolve.ts), through `docResolverFor`. In the app it ranges over the nodes the agent's read rules (§4) do not withhold, so a withheld title matches nothing, is not listed as a candidate and is never written into a turn's intent. A title that names none or several is answered under the box with the candidates, before any model call; a title with spaces goes in quotes.
- **A built-in builds the step a planner would**, from the arguments as typed: `/draft <doc> [draft|continue] [words] [-- brief]` is one `scene.draft` (a rewrite needs a selection in the editor, which a command line cannot carry, and is refused in those words); `/synopses <docs…> [text|notes|both]` is one `synopsis.fill`; `/scan [doc|changed|full]` is one `coherence.scan`; `/review [doc|changed|full]` is one `coherence.review` (`changed` unless told, and its card shows the cost); `/compile <recipe|format> [root]` is one `export.compile`. The plan goes through `submitPlan` (no planner call), so its card is the planner's card for the same step and is decided as any card is: the rules (§4), the mode, the run limits (§7.1), the hard-deny list and the never-auto-approved tools apply unchanged, and a command is never an approval. A single read (`/scan`) runs at once like any single read step.
- **`/plan <request>`** is `submit(request, { forcePlan: true })`. A single reversible step, which runs at once, gets a plan card instead. `forcePlan` adds a card and nothing else: it never changes what a mode approves (Plan only still refuses the write; Accept edits and Auto approve the forced card only where they would approve any card of that tool; a rule that asks still asks; `memory.write` and `instructions.propose` stay the writer's in every mode).
- **`/context`** is `AgentSession.contextPreview()`: it assembles the planner's next request as a turn does and sends nothing, so the gateway sees no request. It reports each layer's tokens, the total and what the assembly left out. **`/restore [last|n|id]`** finds the newest turn whose checkpoint still stands (or the nth turn in the panel, or a turn id) and opens the confirmation the checkpoint row opens; with no such turn it says so. **`/help [command]`** lists the commands with their arguments.
- **`TurnOptions.command`** names the command that started the turn. It is `TurnReport.command`, an optional `command` on the turn's `turn.start` log event (§5.1; a resumed run keeps it) and a label on the turn's row. It is a name from `isCommandName` (lower-case letters, digits and hyphens), and anything else is ignored.
- **While a turn runs**, a plain line queues as before. A command that would start a turn, or restore one, is kept in the box with a note (it runs between turns); `/help` and `/context` answer at once. The queue holds plain requests only, never a command.

**Background runs.** A writer can send a big plan to the background instead of waiting for it. After a planner's reply parses and before `stage()`, a plan is put to the writer through `AgentSessionOptions.beforeStage` when it is eligible and `estimatedModelCalls(plan)` is at least `BACKGROUND_OFFER_MIN_CALLS` (5). Eligible means every step is a native tool (an `mcp__` external tool could write while nobody looks), none is `coherence.review` (its model calls come after approval, a different path that is not queued yet), and at least one step drafts with a model. The estimate is one call for `scene.draft`, `shots.derive`, `dialogue.draft`, `continuity.scan` and `prompt.variant`, one for each shot of `prompt.draft` and each document of `synopsis.fill`, and none for any other tool. The offer comes *before* staging because staging is the long wait: a button on the plan card, which is shown after staging, would arrive too late. The answers are **Run now** (stage in this turn, exactly as without the offer), **Run in background** and **Cancel**. Only a planner's turn is offered one: a plan the app built (`submitPlan`), a small plan and an ineligible plan are staged as ever. **Run in background** is the plan's approval for staging only. The app queues the plan first, the turn then ends `replied` ("Queued in the background: N model calls. Results appear in Tasks when ready."), and `busy` clears at once, so the writer can send the next intent. The offer shows the plan's steps, the estimated calls and the turn's own limit; it shows no dollar figure, because the plan-cost helper reads the context of a draft that does not exist yet.

`AgentSession.stageOnly(steps)` runs `stage()` and nothing else: no card, no decision, no bus command and no recorded turn. It returns each step's draft or refusal, the revision of every document the step read (recorded before the step's first model call), and the calls and tokens the gateway's ledger counted for it. `AgentSession.submitStaged(intent, plan, proposals, revisions)` is a turn like `submitPlan` that skips `stage()`. What it is given is stored data and untrusted: every proposal passes a shape guard for its tool, and a step with no usable draft, with a draft that fails its guard, or that read a document whose revision is no longer the recorded one is marked stale on the card, in the card's own stale state. A stale step cannot be approved; the card's **Retry draft** drafts it again in the foreground, or the writer drops it. Everything after that is the ordinary path: a ghost preview of each prose draft in turn, the bus's parameter validation and `expectedRevision` at apply, one undo group and one checkpoint row. No model call is made for a draft already held. A staged plan of reads only runs without a card and reports what it found.

A queued plan is a *task* (apps/desktop `task-queue.ts`, `task-store.ts`). Its cap is the plan's estimate, and the session it stages with is built for it alone: the `background` role, the profile, model and thinking the role resolves to, the task's id as the session name (so the ledger's turn ids name the task; a resume is another run and is named `<id>.run2`), and `maxModelCalls` equal to the calls the task has left. The runner is sequential and on the main thread: it stages one item at a time (a model-backed step, or one document of a synopsis step) and waits before each next item while a foreground turn is busy. A call already in flight is never cut short, so it still counts against a rate-limited key. An item that would go past the cap fails with the reason in words. Statuses are `queued`, `running`, `ready`, `failed` (nothing was drafted), `cancelled`, `interrupted` and `applied`. When the project opens, a task found `running` or `queued` is `interrupted`; **Resume** stages only the items still pending. A document of a synopsis step that could not be drafted is left out of the review's batch and counted; a step with nothing drafted is stale. Tasks are kept 14 days, and the newest 50 finished ones; they are pruned when the project opens. The queue never issues a command, so it leaves the activity log and the project's revisions as it found them. Only the session that holds the project's lease has a queue, and where the browser has no Web Locks API there is no such guarantee, so the offer is withheld and says so. A task runs only while the project is open in this tab; leaving the tab with a task running asks first. There is no Web Worker in this build, because no typing jank has been measured, and no Service Worker.

**Structured ask-back envelope** (shared by verify failures and anchor non-resolution — one shape everywhere):

```ts
interface AskBack {
  code: 'verify_failed' | 'anchor_unresolvable' | 'needs_input' | 'conflict' | 'budget_exhausted' | 'hook_blocked';
  reason: string;                       // model/user-facing, names the drift or failed postcondition
  candidates?: { from: number; to: number; similarity: number }[];   // anchor drift: ≤3 re-match hits
  revisionDrift?: number;               // apply-time doc.revision − captured revision
  options: string[];                    // 2–3 next actions, e.g. ["re-select in editor", "doc.read the doc", "drop this step"]
}
```

`hook_blocked`: a hook the writer set refused the step ([hooks.md](hooks.md) §4); its options say that only the writer can change a hook. The ask-back renders as a **card in the agent panel** (buttons for the options, not freeform chat) and is the model-facing payload verbatim — one format serves both the model's retry reasoning and the user's review.

**Two wires, one loop.** A turn's wire is chosen once, from the resolved model's capability row (provider-gateway §4): when the row reports `tools`, the planner's callable surface travels as native tool declarations — the reply's tool calls arrive as `tool_calls` with a `tool_calls` finish, results return as `tool` messages keyed by `toolCallId`, and the assistant's own turns (calls + reasoning blocks included) are replayed verbatim. When the row does not, the same loop runs the JSON-in-text protocol: tools described in the system prompt, calls answered as `{"steps":…}` JSON, results in a user message. The choice is per turn and per profile; the steps, cards, refusals and retries above are identical either way — the wire changes how the model *says* a call, never what the call does. Malformed call arguments surface as a keyed tool error with a corrective message, never as a crash. On both wires, an external call's result and a loaded external tool's description are put in an untrusted envelope with the turn's id (extensibility §4 rule 4); Caotang's own results and the assistant's replayed turns are not.

## 3. Tool registry (v0.1 — frozen surface, 14 tools)

**Slicing principles:** workflow-shaped N-to-1 tools promoted to Tier-1 (a typical goal in ≤5 calls); fine-grained primitives exist on the command bus and are composed *internally* by compound tools — they are **not** separately exposed to the model, with one exception: a short allowlisted set of deferred rows (see **Primitives as deferred tools** below). Tier-2 is built: a row outside the always-loaded core is *deferred*, declared to the model only once `tool.search` or a preload has loaded it for the turn (see **Deferred rows** below). The evidence gate is a CI assertion, not usage data (Caotang has no telemetry, decisions.md): the planner request's declared-tool count and character size are pinned for a fixed fixture, core band at most 14 declarations, and the larger size appears only after a search or a preload. One risk level per tool. Flat primitive params with constrained enums. Idempotent: every call carries a turn-scoped `callId`; the command bus dedupes replays.

**Explicitly NOT agent tools:** `delete_node` and every other delete (UI-only, destructive), `doc.write`, raw `editor.insert/replace_range` (primitives live under `scene.draft`), corkboard.* (UI view = binder order; `binder.restructure` covers it), provider config mutation (settings UI only), **codex entry deletion** (UI-only like `delete_node`; agent proposes in report — [codex.md](codex.md) §7).

**Registry metadata per tool** (mirrors MCP annotations for future-proofing): `{ name, risk: "read"|"write-auto"|"write-confirm", undoable: bool, response_token_cap, description (versioned artifact — see §9), load: "core"|"deferred", keywords?, externalOnly?, mirrors? }`. `load` says whether the planner declares the row on every request; `keywords` are extra search terms for a deferred row (its module, synonyms), matched by `tool.search` and never shown to the model. Each module declares the `load` of its own rows, as it declares their risk.

**Result schemas.** Every callable row also declares what its `ToolValue.data` holds on success: `result`, an object spec in the same vocabulary as `params` (`string | integer | number | boolean | enum | array | object | free-object | union | tagged`, each `nullable` where the answer says "none" with `null`, as `project.overview` does with `session`), and `resultSchema`, the JSON Schema `toResultSchema` derives from it exactly as `schema` is derived from `params`. `resultClosed` says whether a key the spec does not list is refused. The thirteen callable v0.1 rows and `tool.search` are closed, and every other row is open (it lists what it returns and allows more, so a declaration never breaks a tool); `RESULT_CLOSED` in `results.ts` is the checklist, and the target is every row closed. `agent.plan` has no result. Results are **enforced in tests, never at runtime**: `testing.ts` wraps a harness so that each successful value a test, an eval scenario or a plan step produces is checked against its row with the MCP client's 2020-12 checker, and a field that is renamed or dropped fails with the JSON path. Production does not validate a native result, which keeps the hot path cheap and adds no reporting channel (there is none, by design). `ToolResults` is the same declaration as a TypeScript type, `Harness.call` narrows on a literal tool name, and `ToolValue<D>` defaults to any JSON object, so a caller that reads a result by key (`isResultOf('continuity.scan', …)`) is held to the spec by the compiler and a type test fails when a `ToolResults` entry and its spec disagree on which keys a result has and requires. The model never reads a result schema: the planner still receives `{ tool, ok, data }`, and a schema in the prompt would spend the context deferral saves. A result-schema change is not a description change, so it does not bump `descriptionVersion`.

**Core rows** (`load: "core"`): `project.overview`, `binder.read_tree`, `doc.read`, `notes.read`, `meta.set`, `notes.append`, `synopsis.fill`, `scene.draft`, `binder.restructure`, `continuity.scan`, `export.compile`, `codex.read`, `codex.write`, `agent.plan` and `tool.search`. Every other registry row is deferred.

**Deferred rows.** The planner declares the core rows on every request, in the system message (JSON wire) and in the `tools` declarations (native wire), and the system message ends with one line, "More tools exist; call `tool.search` with a word from the task to load them." A deferred row joins the turn's loaded set when `tool.search` matches it, or when `submit(intent, { preload })` names it. The context table `PRELOAD_BY_CONTEXT` preloads `dialogue.*` while a dialogue container is the active document and `shots.*` while a storyboard (or a screenplay scene to derive from) is. The loaded set is per turn ([extensibility.md](extensibility.md) §12 A2). The loaded rows are declared on the next request, and their descriptors (name, risk, description, schema) go in a user message after the system prompt, never into L0, so a turn that loads a tool leaves the cached prefix as it was. **Deferral is about context, not trust:** a step that names a deferred native row the turn has not loaded is preflighted like any step, not refused; if its params fail, the refusal adds "Call `tool.search` with '<name>' to load its parameters." An unloaded external (`mcp__`) tool is still refused, because loading is where its pin is bound. `submitPlan` and `executePlan` accept any registered row, so a UI-started plan needs no load. Settings › Agent has **Load every tool on every request** (default off, app settings only) for a model that searches poorly: it declares every callable, wired row, as before.

The rules that keep this from becoming "every primitive is a tool":

- The tool's risk and undo are read from the command's descriptor at registration. A spec has no field to state them, so a tool cannot differ from its command.
- The types name what may never be exposed (`NeverExposed`: every delete, `doc.write`, `editor.insert`, `editor.replaceRange`, the `view.*` commands, the staging commands `project.importAsset`, `shot.importImage` and `shot.importImages`, and `mcp.invoke`). A spec that names one does not compile, and a runtime guard refuses a `never`-class or hard-denied command.
- A tool's params are closed and map onto keys its command declares (`DECLARED_PARAMS`). An undeclared key is refused with the accepted set named.
- Every call passes the ordinary permission gate, the bus `validate` and the plan card's preview. None runs under an inherited grant.
- A plan step that names a status or label an earlier `vocabulary.upsert` step adds is deferred in the preview, as a step that names a document an earlier create makes is, and is checked again when it runs.

**External-only rows.** A row marked `externalOnly` is served to an external host (the MCP server, extensibility §9) and never to the in-app agent: the planner does not declare it, not even under "Load every tool on every request", `tool.search` does not offer it and a preload does not load it, and the app wires no port for it, so a call in a turn is refused as not wired. The four are the **host-model pairs**, one pair for each of the two drafting rows an outside host can use with its own model (`surface: 'extension'`, `load: 'deferred'`, `mirrors` the in-app row). The server holds no provider key, makes no model call and uses no MCP Sampling: the brief returns what the in-app tool would send its model, the host's model writes, and the apply runs the reply through the in-app port.

## 4. Permission model

- **Auto:** all read tools (incl. `codex.read`); `meta.set`; `notes.append`; the deferred primitive rows `synopsis.set`, `filter.save` and `goal.save` (a primitive row takes the class of its command, command-bus §4, never one of its own); structural ops *within an approved plan* (`binder.restructure` is confirm at the plan level, then auto inside it).
- **Confirm (batched per plan):** `synopsis.fill`, `scene.draft`, `codex.write`, `binder.restructure` standalone, `export.compile`, `notes.replace`, `vocabulary.upsert`, `memory.write` and `instructions.propose` (deferred primitive rows). The last two change what every later request says, so **no mode approves them** (`NEVER_AUTO_APPROVED_TOOLS`): they are a card the writer decides in Accept edits and in Auto, and they are not write-auto in this build.
- **A delegated agent can only read and stage** (§2, "Delegate"). It holds no approval and cannot ask for one: the harness refuses every tool that is not a read, and every external call, while `TurnContext.agentPath` is set, whatever approval rides on the turn. A write it wants is a proposed step in its result, which reaches the writer only inside the planner's own plan card.
- **Never (v0.1):** network beyond the configured provider endpoint; deleting nodes; leaving project scope; touching provider profiles.
- **Hard-deny list — not approvable by any flow** (enforced at the bus gate, [command-bus.md](command-bus.md) §4): network egress beyond the configured provider endpoint; node/codex-entry deletion (and `memory.forget`, a memory note's removal); provider-profile mutation; leaving project scope. **No classifier** (no judge model in the loop) and **no per-primitive approval toggles** — one risk level per tool is the honest simplification, and fine-grained rules belong to a rule layer, not to switches on tools. A mode (below) is the only way a card is approved without the writer, and it never reaches this list. Rules (below) narrow the agent per tool and per binder subtree, never per primitive.
- Every confirmation is batched per plan card; mid-plan new confirm-class calls pause the plan with a delta card.
- **Permission modes** (`mode.ts`; owner decision, decisions.md). The mode answers a card; it does not change the bus gate, and `PermissionContext` has no mode field. It is read at each card, so a switch in the middle of a turn applies from the next card. It lives in app settings (`agent.defaultMode`, `agent.lockAuto`, `agent.budget`) and a per-panel pick, never in `caotang.json`: a project cannot carry one. The panel's mode control is a radio group named **Mode**.
  - **Plan only** runs reads and refuses every write — a `write-auto` step, a `write-confirm` step and an external write — in `stage()`, before any draft is asked for, as a failed status card that names the mode and a refusal that goes back to the model. The planner answers in words. The refused steps ride on the report (`heldSteps`), and **Switch to Ask and run this plan** sends them through `submitPlan` in Ask, so the writer decides the card. A plan offered to the background is not offered in this mode.
  - **Ask** is the default and changes nothing: every plan and confirm card is the writer's.
  - **Accept edits** approves, as shown, a card whose every write step is a native text or field edit (`ACCEPT_EDITS_TOOLS`: `scene.draft`, `synopsis.fill`, `synopsis.set`, `notes.replace`, `notes.append`, `meta.set`, `codex.write`, `dialogue.draft`, `prompt.draft`, `shots.derive`, `shots.annotate`). A restructure, an import, an export or a review still asks.
  - **Auto** approves any card of native tools as shown.
  - **Never approved by a mode, in any mode:** a card with a loaded external tool (its own one-step card, extensibility §4 rule 2), a card the preflight refuses, a stale or cut draft (`acceptTruncated` is the writer's), a scan over the document guard, and anything on the hard-deny list. A revision conflict ends the run of that step and the card comes back stale, which only the writer can decide: a mode never retries it. While `taint()` holds, Accept edits and Auto behave as Ask. The loop holds it for a tainted turn (below) and for a session whose host says its project holds text from outside the writer (the host's hook defaults to false; imported-text provenance is not built). `lockAuto` makes `modePolicy('auto')` refuse to construct and a stored `auto` read as Ask.
  - **How a policy-approved card runs.** The card is shown (`plan` event with `auto: true`), its drafts stream into the ghost region first, `beforeAutoApply` lets the app save the writer's typing (and, before a compile, list the images again), and the steps run in the turn's one undo group. If that save or listing fails, the card is not applied unattended: `beforeAutoApply` answers the reason, and the card is put to the writer as an ordinary card with the reason as its notice, as a stale one is (with nobody to ask, it is cancelled like any card the mode does not approve). The card record is `{ kind: 'auto', decision: 'auto' }`, the panel shows it collapsed with an **Auto-approved** badge, and the turn leaves one checkpoint row. Every turn row, the report (`TurnReport.mode`) and the checkpoint row (`mode`) print the mode.
  - **Budgets**, while a mode decides cards (Ask and Plan only keep the model-call bound alone, and the run limits of §7.1, which hold in every mode). A turn is held to `TurnBudget`: model calls, tokens, cost (at the price the session reads; an unpriced turn has none), words changed, documents touched and steps, and the same limits across the session (`SessionBudget`). Model calls, tokens and cost are checked before each model request: a turn that has used exactly its limit stops there. Steps, documents and words are checked before a card applies, against what the card would add (a `scene.draft` and `synopsis.fill` say their documents and words from their drafts; any other step is counted from the activity log after it has run), so a turn may end exactly on a limit and never passes one. A turn that reaches one ends on a `needs_input` ask-back with the dimension, the amount and two options (raise the budget in Settings › Agent, or stop and keep what was applied); what was applied stays in the undo group. The same tool with the same parameters proposed three times in one turn stops it the same way. `TurnReport.budgetUse` reports what was used. The defaults (`DEFAULT_TURN_BUDGET`) are 8 model calls, 150,000 tokens, 6,000 words, 30 documents and 40 steps.
  - **No human.** `noHuman` (an option of the session) cancels a card the mode does not approve instead of asking, for a caller with nobody there; the headless policies below map onto it.
- **Rules** (`rules.ts`, `targets.ts`; owner decision, decisions.md). A rule narrows the agent: `{ effect: 'deny' | 'ask', tool, scope?, access?, note? }`. `tool` is a registry name, a qualified external name or a pattern (`codex.*`, `mcp__notion__*`, `*`; `*` matches any run of characters). `scope` is a binder node and everything under it (`{ subtree: nodeId }`, the stored form, stable across renames) or, in a hand-edited file only, a title path (`{ path: 'Manuscript/Act 1/**' }`, resolved when the rule is evaluated, with a warning that a rename breaks it); absent means the tool wherever it is called. `access` is `read`, `write` or `any` (default). There is no `allow` in this build, so a rule can only restrict and a project file can never grant the agent power; an `allow` in a file loads with a warning and has no effect. Rules come from the project file (`agent.rules`, which travels with the folder and the bundle), the app's settings (tool-level rules only, since a node id belongs to one project) and the session, and they apply in every mode.
  - **Evaluation** is a pure function in the harness, before the bus: every `deny`, then every `ask`, each in the order listed, and the first match decides, across all sources and never by how specific it is. The bus gate (`checkPermission`) is not changed and stays pure, and the hard-deny list stays first. A rule matches a call by its tool and, when scoped, by the nodes the call reads or writes (`targets`). A tool whose nodes cannot be worked out is refused under a scoped deny and asked about under a scoped ask, so a rule is never bypassed by a call that could not be checked. A rule that cannot be read at all (a host that holds them elsewhere failed to) refuses every call that changes the project.
  - **Deny** refuses the call as `permission-denied` (not `hard-denied`: the writer can remove a rule), naming the rule's source and note, as a failed status card before any draft is made. A deny covers a plan's preflight, a plan's run, an async port and an external tool by its qualified name; a compound call is evaluated whole before it applies, so a `binder.restructure` with one operation on a locked node is refused with that operation's index in `target` and nothing applied. A refusal does not name a part of the project the agent may not read. That holds for a reference that names several nodes too: the candidates list leaves out the ones a read rule withholds (and a title that matches only withheld nodes is answered as one that matches nothing). A dialogue tool names a dialogue container, so its targets resolve the way the dialogue module resolves one, not as a document.
  - **Ask** forces a one-step confirm card, even for a `read` or `write-auto` tool, and in every mode: a mode never approves a card that holds an ask step. At the harness, a call carrying no confirmation (the card's `confirmed`, or an approved plan) is refused, so a caller that cannot confirm (the outward MCP surface) cannot run it. An ask on an external tool is a no-op, since an external call confirms per call whatever the rules say. An ask on `agent.delegate`, or on every tool, puts the delegate on that card too, and an approved card starts the agent through the loop's own delegation, as an unasked call does: the harness's delegate port always refuses, so the approved step is not run through `harness.call`.
  - **Read-deny.** A deny with `read` or `any` access on a scope also keeps it from the agent: `withheldNodes` is the set, computed for the tool that is reading, and it implies a write-deny on the same scope, so the agent cannot edit what it cannot see. The set is consumed by context assembly (context-assembly §2, "Withheld"), `binder.read_tree` and `project.overview` (they leave the nodes out and report how many), `codex.read` (an entry is withheld only when it has attachments and every one is withheld), and `coherence.scan` and `coherence.review` (withheld documents are excluded like archived ones, and a withheld dialogue container adds no branch or speaker finding). `doc.read`, `notes.read`, `continuity.scan` and `agent.delegate` name documents, so they are refused by the target rule. `export.compile` writes only to `exports/` and sends nothing to a provider, so a read-deny does not stop it. Rules are never addressed to bus primitives, so "no per-primitive approval toggles" stands.
  - **Only the writer writes rules**, through Settings and the binder menu. No registry row, bus command or MCP tool writes `agent.rules`, an app rule or a session rule (a test holds it).
- **Hooks** ([hooks.md](hooks.md); owner decision, decisions.md). A hook is a check the writer set, stored as `agent.hooks`. It runs after the rules, the grant and the port's state check, and before the bus, which still runs its gate: at the plan's preflight (`PlanHost.check`, synchronous, no gateway, no server) and again as the call runs, in `call`, `callAsync` and `callExternal`; and, after the call, on its result. It can warn, block a step (the card shows the reason beside the disabled **Approve**, and no mode approves a card with a refused step), or add a note the model reads in an untrusted envelope. **It never approves, rewrites a call or writes the project**, so it can narrow what a mode allows and never widen it, and a tainted turn keeps its one-step confirm whatever a hook says. A hook that cannot run is a warning, "the step was not checked". **Only the writer writes hooks** (`hook.save` and `hook.delete`, `agentRisk: never`); a plan step that names one is refused in the writer's words, and no registry row, bus command or MCP tool an agent can reach writes one (a test holds it).
- **Tainted turns** (extensibility §4 rule 4, issue #54). A turn is *tainted* from the moment it takes in text from outside the project: an external call's result or error, or the description of an external tool that a `tool.search` surfaced. Native results and a search that surfaced only native rows do not taint. Taint lasts to the end of the turn and nothing else carries it: the writer's next intent starts a clean turn, and a turn resumed from the run log is tainted when its logged conversation holds a connected server's envelope (a `source="mcp…"` marker; the system prompt's words about the markers and a project file's envelope do not count). While a turn is tainted: (1) a single `write-auto` step (`meta.set`, `notes.append`, …) is shown on a one-step confirm card, as a rule that asks does it (the bus gate is unchanged and `checkPermission` stays pure; the card is the loop's); (2) the mode policy's `taint` hook holds, so Accept edits and Auto approve no card of the turn, and a headless caller with nobody to ask cancels it; (3) every card says which servers the turn read from, in `PlanCardView.caution.followsUntrusted`, and the panel shows “This comes after the agent read text from *Notion › search*. Check that it is what you asked for.” A plan card of several steps was the writer's already. The planner's rules tell the model that a write is shown first after a connected server's text. The model-facing copy of the outside text sits in an envelope with the turn's id (extensibility §4 rule 4); the card, the activity row and the turn's steps hold it verbatim.
- **What an external write sends** (issue #54). Before an external write's card is shown, `quotedProjectText` compares its arguments with every document body and codex description (twelve or more words in a row, the store's word rule, case and the punctuation around a word ignored; an unspaced script counts a character as a word). Every string at any depth and every object key is compared, and the words of all of them in reading order are compared once more as one text (place `args`), so a quotation split over the items of an array or over a key and its value is found; no depth is skipped. A finding is `{ nodeId, title, words, argPath, step }` in `PlanCardView.caution.quotes`, and `caution.requiresSecondClick` makes the panel's Approve button ask twice. After a read from another server, `caution.lead` is the cross-server sentence. `caution.hits` lists what `scanForInjection` finds in the arguments and the tool's description (hidden characters, chat role markers, “ignore previous instructions”, links to an absolute address). None of it refuses a call; the check makes no model call and no network request.
- **Headless modes** (`caotang agent --permission`, §11): `read-only` (default) cancels every card and refuses a write that needs no card, `auto` lets a write that needs no card run and cancels every card, and `approve-all` approves every card as shown, never a draft the provider cut off; `--approve-tools` narrows `approve-all` to cards whose every step is a listed tool. Each is the answer to the card decision the panel asks for, given with nobody to ask, so none can approve what the card cannot be approved as, and none reaches the hard-deny list, which the bus gate enforces under all of them. They map onto the interactive modes, so there is one vocabulary: `read-only` is Plan only, `auto` is Ask with `noHuman` (every card cancelled), and `approve-all` is Accept edits or Auto.

## 5. Undo & safety

- **One agent turn = one undo group** on the command bus (compound tools sub-group internally, exposed as one) — mechanics in [command-bus.md](command-bus.md) §5.
- `scene.draft` / any body-text mutation snapshots the prior body first (project-format §8 write-ahead) — the safety net writers want before mass edits, made automatic.
- **Checkpoints, framed for users:** each turn renders in the activity log as a checkpoint row — **"restore to before this turn"** — a restore affordance rather than an abstract "undo", which is what makes agent edits trustworthy. Snapshot retention budgets are in [command-bus.md](command-bus.md) §5.1. **Two-lane undo ([editor-engine.md](editor-engine.md) §7):** agent turn applications run as one transaction batch tagged `addToHistory: false` — the user's Ctrl+Z never replays agent edits; restore = snapshot-based, immune to in-editor undo position drift. Restore confirmation states scope explicitly (user edits made after the turn are included in the restore).
- **Step checkpoints.** Each step of a turn is a restore point as well: **Restore project to before this step** takes back that step and the ones after it, and keeps the earlier steps (`UndoStore.undoFrom`, [command-bus.md](command-bus.md) §5). The session records, per turn, the call id each step's status card was dispatched under (`AgentSession.restoreStep(turnId, stepId?)`, `restorableSteps(turnId)`); with no step id it is the whole turn. A step that wrote nothing (a read) starts the restore at the next step that did. Restoring from the first step that wrote empties the group, so the turn's checkpoint row and its "Restored from step N" line go with it. The app still takes the turns after it back first, with the same dialog wording, and marks every turn that went whole as restored and this one as restored from the step. A step that called an `mcp__` tool, once it is done, says on its own menu that its external effects stay (`STEP_EXTERNAL_CHECKPOINT_NOTE`, the step form of `EXTERNAL_CHECKPOINT_NOTE`: "Restoring from this step ..."). A step that failed, was cancelled or is still pending made no external change and carries no note, except an external call that was sent and then timed out or was cancelled (`StatusCard.mayHaveActed`): the server may have acted, so its step carries the note too. When the planner proves a turn or a step independent of the changes after it ([command-bus.md](command-bus.md) §5), the dialog adds **Restore only this step (keep your later edits)** (**this turn** for a whole-turn restore); otherwise it lists the later changes and takes them back, as before. The turns after are not marked restored when they stay.
- **Two axes: project and conversation.** A turn's checkpoint restores the *project*; the *conversation* is the session's turn list, which L6 reads ([context-assembly.md](context-assembly.md) §2). The writer moves them apart or together from a per-turn menu: **Restore project** (conversation kept), **Rewind conversation** and **Restore both**. `AgentSession.rewindConversation(turnId)` marks that turn and every later one `rewound` and returns the turn's intent (a turn started with `hiddenFromPlanner`, as a macro run is, is in the list but L6 never prints it); it touches no project state, no activity row and no report. `AgentSession.markRestored(turnIds, at, fromStep?)` records `restoredAt` on turns whose project changes the writer took back. A restore through `restoreBefore` also undoes every *later* agent group, so the controller marks every turn whose group was undone, not only the clicked one. **Restore both** restores the project first; if it stops part way, or a turn started while it ran, the conversation is not rewound, the turns that were undone are still marked restored, and the reason is shown. Rewound turns stay in the panel, collapsed under "Rewound - not sent to the model", and the activity log is never rewritten. Refilling the Intent box never replaces a draft: the old instruction is offered as a button. A turn that called an `mcp__` tool carries `EXTERNAL_CHECKPOINT_NOTE` on its menu (a step carries it in its step form), and **Restore both** does not claim to reverse external effects. Rewinding is the writer's action: the agent has no tool for it, so the registry is unchanged. Both flags live in memory with the turn list (persistence is #25).
- Call-id dedupe: replays of the same `callId` within a turn return the cached result (idempotency). The MCP path has no turn that spans two requests (each is its own turn, ended when the call returns), so the bus cache cannot see a retried request; the server holds a keyed answer cache for it instead, filled only when the caller sends `app.caotang/idempotencyKey` in `_meta` (extensibility §9).
- Activity log (per turn): timestamped tool calls, params digest, affected node ids+titles, token usage, undo group id. The log keeps every row it is given; the Activity panel shows a 200-row window of it, and the Markdown export carries every row that is not a `view.*` command. A turn's full trace, with the prompts and the results, is a separate thing with rules of its own (§5.2).

## 5.1 Durable runs and resume

A turn is logged ahead of its work in the runtime database (`caotang`), so a reload, a crashed renderer or a closed tab leaves a record of how far it got. This is runtime state, not a project file: no plan format is introduced, a folder, a bundle and an export carry no run log, and the key vault is never involved. It is the one shape for runs; sessions and background tasks project from it and add no second record.

- **Stores.** `runs` (key `runId`, index `projectId`; one record per turn: intent, status `running | awaiting-approval | interrupted | finished | failed`, profile id, schema version, `cannotResume`) and `runEvents` (key `[runId, seq]`). Both are additive in runtime database version 4; an upgrade from version 3 touches no record. A run's records go with its project. Settled runs are kept for 30 days and 50 runs, on the clock the checkpoints use.
- **Events** (`run-log.ts`, versioned): `turn.start`, `messages` (appended as deltas, verbatim, including tool calls and reasoning signatures), `card.pending`, `card.decided`, `step.intent`, `step.applied` (with the revisions the step left behind), `step.failed`, `spend`, `turn.end`. `turn.start` carries the slash command's name when a command started the turn (`TurnReport.command`). Only the profile id and the messages the harness built are stored; nothing request-shaped, no key, no header.
- **Write-ahead, per plan step.** `step.intent` is appended, the step goes through the bus, the app's autosave is flushed (`runLog.flush`), and only then `step.applied`. So `applied` in the log means the write is on disk. Each append is one transaction with no await on anything but IndexedDB. If an append fails, the turn carries on, the run is marked `cannotResume`, and the writer is told once, with the cause; a run that could not be logged is never offered back.
- **Ownership.** There is no heartbeat, owner tab or per-run lock. The project lease (one Web Lock per project, held for the session; a second tab is refused) means one live tab per project, so a run found `running` or `awaiting-approval` when a tab has just taken the lease is interrupted by construction, and `markRunsInterrupted` says so. Where Web Locks are absent, the revision checks below are the only guard.
- **Resume is the writer's click.** It can re-issue a paid planner call, so nothing starts it. The panel shows an interrupted-run card above its body, open or closed: a region with real buttons, a polite status line, "N of M steps applied" and the spend when it is known, and the stale state in words. Its actions are **Resume** and **Discard log**; discarding deletes the log and keeps what the run wrote. The card says the in-flight model call was lost and its reservation counts as spent. A run whose log cannot be read when the panel lists the runs (a failed read, not a damaged log) is still listed, discard-only, with a neutral note that claims no damage; nothing is discarded for the writer. A run log store that cannot be opened is said once ("Interrupted agent runs could not be checked: …") and offers no card; it is said again if it later fails after a check that worked.
- **`planResume(events, revisions)`** decides, from the log and the project as it stands, whether resuming is safe: `clean` (continue after the last applied step, or the pending card), `re-run` (a step with `intent` and no `applied`, the documents unchanged since: it runs again under a fresh call id), `write-lost` (a write the log records is not in the project; the documents are named), `revision-drift` (a document the run depends on has moved on; the writer's text outranks the agent's, and the documents are named), `ask-back` (an `mcp__` step with `intent` and no `applied` is never re-sent, since the server may already have acted, and a run stopped before its plan reached a card has nothing to continue), and `schema` (an unknown version is refused). Every verdict other than `clean` and `re-run` offers Discard log only.
- **The log is advisory.** A resumed step goes back through bus validation and the card preflight (the stale-card path, §2), and the agent rules (§4) are read when the run resumes, not as they stood when it began: a rule added in between holds a resumed step. A read-deny withholds from a prompt, and the logged conversation of a run between cards holds what the rules then allowed, so each `turn.start` records the nodes a read-deny kept from any tool, and a resume that finds one the log does not list is refused without a model call (the reason names no title) until the rule is lifted or the log discarded; a restored card builds no new prompt and is not affected. A pending card comes back needing its own Approve; the click on Resume authorises the resume, not the plan.
- **Spend.** The meter of a resumed turn starts from the run's logged spend, and a model call that was in flight when the run stopped counts as spent, so `maxModelCalls` (§7.1) stays honest. A log that cannot be read at the click gives no spend to start from, so the run is not resumed and the panel says so: a read that failed gives its reason and offers a retry, and a log that was read but cannot be summarized is called damaged, with no retry offered.
- **Not built:** a baseline checkpoint pinned before a run's first write with a "restore to before this run" action, an export of the run log, a folder mirror, and a heartbeat for browsers without Web Locks.

## 5.2 Trace

The activity log says what changed; the trace says what the model saw and did, so "why did it rewrite that paragraph?" has an answer. It is a view for the writer, kept apart from the request log (provider-gateway §4), which stores no prompts and still does not.

- **Where it lives.** In the memory of the open tab, one store per tab. Nothing writes it to IndexedDB, a project, a bundle or the network; the app database's record keys (`settings`, `profiles`, `usage`, `requests`) and the bundle are unchanged, and tests hold both. A reload loses it, and the Trace tab says so. The only way out is **Export trace**, which the writer asks for. Persisting a trace waits on the durable-run record (#65, #66); an OTLP exporter or any upload stays rejected, since an exporter that posts to a URL is egress outside the provider endpoint (§4). The model cannot read it: the store is not reachable from the command bus, a registry tool or the MCP server, and a test holds that.
- **The setting.** "Keep agent traces for this tab" (Settings › Agent and the Trace tab) is on by default, because the data is already in the tab's memory. Off, the gateway has no observer, the sessions have no sink, and what was kept is cleared at once; a model call already under way writes nothing more, because the observer it started with records through the switch. **Clear trace** empties it on demand.
- **Format `caotang.trace/1`.** JSON Lines, one record per line, ordered by `seq`, in `packages/harness/src/agent/trace.ts` with `trace.schema.json` beside it. The first line is a `header`. Records: `turn.start`, `context` (layer tokens and what was left out, for the request it precedes), `message`, `model.request`, `model.response`, `tool.call`, `tool.result`, `tool.progress` (a server's progress report on an external call that was running: the numbers and its message, which an `omitText` export leaves out), `card`, `ladder`, `hook` (a hook warned, blocked a step or added a note, hooks.md §7) and `turn.end`, whose `report` is the `TurnReport` the turn returned. The model-call fields use OpenTelemetry's GenAI names (`gen_ai.request.model`, `gen_ai.response.finish_reasons`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`); Caotang ships no exporter. `parseTrace` skips a kind it does not know and refuses a file whose header, or any record, carries a version it does not read (and a second header), so replay (#82) and the golden tasks (#83) read through it.
- **Two producers, joined by `turnId` and `callIndex`.** The gateway's observer (provider-gateway §3.1) writes every model call, whoever made it: the `model.request` after role routing, then the `model.response` with the attempts, the time to the first token, the finish reason and the usage, marked `provider` or `estimate`. The loop writes the turn around it: its `modelCall` stamps each request with a `callIndex` (a delegated agent's calls counted too), and its sink calls write the rest. `tool.result` carries the body the model was handed back, the same value that goes into the results message or the native tool message. A review made outside a turn (the coherence and encoding reviews call the gateway directly) has no turn: it is kept in one explicit **Reviews** group that counts as one unit under the caps below.
- **Stored once.** A message is kept once per store, found by its exact canonical form, under an ordinal id (`m1`, `m2`…) that a `model.request` lists. There is no hash, so a short line cannot be guessed from an id. A message goes out ahead of the first request that lists it, so a one-turn export is complete.
- **Caps.** The newest 25 turns and 16 MB of serialised JSON, whichever comes first, dropping whole turns, oldest first; the turn most recently started is never dropped, so the latest turn can always be read. No record keeps more than 64 KB, counted in bytes: the longest texts in it are cut and `truncated.chars` says by how much. Streamed deltas are never recorded, only the final reply.
- **Redaction, best effort.** The gateway scrubs every string of an event with the call's own secrets (the key and a generic profile's sealed header values) before the observer sees it; the store then runs the bearer and `sk-` pattern pass over every string it keeps, tool results included. Headers are never recorded. A provider's opaque reasoning payload (signed thinking, encrypted content) is recorded as its byte length only. The trace still holds the prompts and the manuscript text they carry, so the panel and the docs call the scrubbing best-effort and never "safe" or "anonymous".
- **Export.** From the Trace tab, one turn or every turn in the tab, as `<project>-trace-<turnId>.jsonl` through `downloadBytes`. The dialog says in one sentence that the file contains the prompts and manuscript text that were sent, and that the scrubbing is best-effort. **Leave out manuscript text** replaces every text the writer or the model wrote (message contents, reply and reasoning text, the message of a provider error (it quotes the start of the body), tool parameter values, tool result bodies, the intent and the report's texts) with `{omitted:{chars}}`, with no hash. Structure, timing, tool names, risk, outcome, token counts and finish reasons stay.
- **The Trace tab.** Beside Activity in the left rail: a timeline for each turn, one row per model call (model, role, duration, time to the first token, tokens in and out, finish reason; expanding it shows the messages it was sent with the system message closed, the reply, the reasoning and the tools it asked for), one per tool call (risk, outcome, parameters, the result handed back), and the card decisions and ladder steps between them. A bar for each row shows where it sits in the turn, with the same words as text. Everything is rendered as text, never markup, and the tab is keyboard operable.
- **Headless.** `runScenario(scenario, { trace })` writes the same records from a manual clock that moves a millisecond per record, with session name `eval`, so two runs of one scenario write the same bytes. The SDK and CLI flag (#42, #43) is not built; it needs only this sink.
- **Not built:** persistence across reloads, a cross-trace content hash, replay of a turn against another model (#82), recorded provider exchanges as test fixtures (#83), and token and cost views (#78).

## 7. Verification & self-correction ladder

Post-conditions are per-tool assertions (e.g. `scene.draft`: doc body non-empty, word delta matches mode; `binder.restructure`: tree validates against project-format schema). Ladder: adjust params → retry (≤2) → structured failure report with 2–3 options. Trace assertions in evals mirror this (§9).

### 7.1 Run limits

A writer can set limits on their own key: model calls, tokens, cost, applied steps, minutes of work per turn, and (for an unattended caller) an absolute deadline. They are the writer's: Caotang charges nothing and imposes no quota (decisions.md; provider-gateway §9 D4). `budget.ts` holds them in a `BudgetMeter`, pure apart from its clock, which a session takes as `AgentSessionOptions.meter` (a meter, or a function that reads the meter of the turn about to start). A session with no meter enforces nothing beyond the model-call bound, as before. `TurnBudget` (§4) keeps its words-changed and documents-touched dimensions, which are measured from the activity log after a card applies; the meter owns the dimensions that can be held before a call.

- **Never crossed.** The one budgeted call site (`modelCall`, and the call a delegated agent makes) reserves the call's worst case before the request is sent: the prompt's estimate (`usageFor`) plus the output cap the request goes with (the profile's `maxOutputTokens` from `gateway.modelLimits`, plus the thinking tokens a set level can spend). The reservation is refused when tokens spent, plus every reservation in flight, plus this one, would pass `maxTokens`; the same sum in dollars at the profile's `pricePer1k` for `maxCostUsd`; or when `maxModelCalls` calls have been made. A refused call is never sent. The turn ends `failed` on an ask-back with code `budget_exhausted`, whose reason names what the call would have needed, and `TurnReport.budgetStop` carries `{ dimension, limit, spent, needed }`. After the call the reservation is settled with the usage of the stream's final chunk; a stream that ends with none settles at the estimate (the prompt and the text that arrived) and the tokens count as `estimatedTokens`. Gateway retries happen inside one `complete`, so one reservation covers all attempts. A `maxCostUsd` on a profile with no prices is refused before any request, with “This run has a cost limit, and the profile “X” has no prices, so its cost cannot be counted. Add its prices in Settings › Providers, or use a token limit.”
- **Time.** `maxActiveMs` is time spent working: the meter's clock is paused while a card or a background offer waits for the writer. `deadline` is the wall clock and is never paused. Either aborts `meter.signal`; the turn's signal is the writer's Stop and that signal combined (`anySignal`), so a limit ends a model call in flight, a coherence review and an external call by the path Stop uses, and never inside a bus command that has started. A turn a time limit ended is `failed` with `budgetStop` (`active-time` or `deadline`), not `cancelled` with `stop.by === 'user'`; the writer's own Stop wins when both fired. What the turn applied before stays in its undo group and its checkpoint restores it. A call a limit cut short that its tool absorbs (a review reports what it had, with a note) leaves the status as the tool reported it, and the report still carries `budgetStop`.
- **Steps.** Applied write steps are counted into the meter at each turn's end and before each `stage()`, and so is an external call that was sent and then timed out or was cancelled (`StepRecord.mayHaveActed`): it may have acted, and a run that keeps calling a hung server meets its step limit. A write past `maxSteps` is refused before it is drafted, as a failed status card and the same words to the planner (“the run’s limit is N applied steps and U are used, so a plan may have L more write steps…”), so no model call is spent on it.
- **A run, not a turn.** A meter outlives a turn: a goal run or a background task shares one across its turns, and `toJSON()` with `createBudgetMeter(limits, { restored })` carries its spend across a reload. The app makes one per turn from Settings › Agent (`agent.budget`): the limits the writer set, and ten minutes of work unless they chose another; it disposes the meter when the turn settles. A turn's model-call bound is read at the start of each turn from the same settings, default 8.
- **Reporting.** `TurnReport.spend` is the meter's spend after the turn; a `budget` event carries it after a call is allowed and after it settles, and the panel shows a spend line beside the step line while a turn works. The ledger is unchanged: it records what the gateway counted.

### 7.2 Goal runs

A goal run works turn after turn until the checks the writer chose pass. This build has the checks and the loop in `packages/harness` (`agent/checks.ts`, `agent/goal.ts`); it has no panel, no durable record and no model verifier, so a goal is started from code, and nothing in a run survives a reload.

- **Checks are deterministic.** `CheckSpec` has four kinds, each a pure function of the project: `coherence.clean` (no open finding at or above `minSeverity` from the named checks in a scope), `words.between`, `status.all` and `synopsis.filled`. `evaluateCheck` returns `{ pass, distance, failures, skipped }`: `distance` is the open findings, documents out of range or unfilled synopses, and is zero exactly when the check passes. `coherence.clean` runs `runDeterministic` on a copy of the held coherence file and discards it, so evaluating records no run and leaves the `changed` scope as the writer left it; a finding the writer dismissed counts as clean, and a check turned off in Settings › Coherence is left out and listed in `skipped` (a check with nothing left to run is not met; `checks: []` is refused, and a goal whose only failing checks are turned off in Settings ends `failed` without a turn, since no writing changes a setting). A named check the scan itself drops (the dialogue branch checks and speaker parity run on a full scan with the dialogue facts; never-mentioned needs every count) is listed in `skipped` too, and when none of the named checks ran the check is not met: "no open finding" from a scan that looked at nothing is not a fact about the project. When the named checks the scan drops are the dialogue branch checks or speaker parity over a scope that is not a full scan (or without the dialogue facts), no turn can make them run: the check is unmeetable like a settings block, and the goal ends `failed` without a turn, saying so in its own words. Words are counted by the counter the inspector and the goals use (`derived.wordCounts`, else `countBody`). For the other three kinds a `doc` scope may name several documents or folders, and a folder stands for the documents under it. Archived documents are never read by a words, status or synopsis check, whether named directly, reached through a folder, or in the whole manuscript; only an archived document a `doc` scope names directly is listed in the result's notes, and one reached through a folder or the whole manuscript is left out without a note. No model is asked to say a goal is done: the model's own claim never ends a run.
- **The loop.** `GoalRunner.start` evaluates every check; if all pass it returns `passed` without a turn. Otherwise each iteration builds a request from the writer's words, `iteration n of at most N`, the checks that already pass, and the failing documents worst first, at most `perIteration` (default 5) of them with the rest counted; it submits that as an ordinary turn (`session.submit`), then evaluates every check again. The iteration has its own cards, its own checkpoint and its own entry in the run log (§5.1), and is held to the permission mode (§4), the rules (§4) and the run limits (§7.1) the session carries. A goal adds no approval shortcut: a card the mode does not approve is the writer's in every iteration, and a goal creates no `auto` card of its own.
- **Stops.** Before the first turn, `passed` when every check already passes. Before each iteration, `cancelled` (the writer's Stop) and `budget` (the meter's limit or deadline has passed). After each iteration, checked in this order: `out-of-scope` (below); `passed`; `budget` (the turn ended on a run limit, or the meter's time limit has passed); `cancelled` (the writer's Stop during the turn, or a declined card); `failed`; `regressed`; `stalled`; `max-iterations`. A turn that throws ends the run `failed`. **Stall**: the sum of the checks' distance has not been strictly lower than its best so far for `stallAfter` iterations (default 2), so a run that goes up and down is not progress. **Regression**: a check that passed earlier, including at the start, fails now. The run ends with an ask-back (`needs_input`) offering to restore to before the iteration, continue anyway, or stop; the caller's `onRegression` answers it, and with none the run stops. A callback that throws or rejects does not lose the run: an ask-back that cannot be answered stops the run and restores nothing, and a failing `onIteration` observer becomes a note (the run waits for an async observer, so a rejection is caught the same way, and the note is said once however many iterations it fails on; notes are appended to `reason` like the closing-scan notes). Continuing does not ask again for the same break. `maxIterations` defaults to 10 and is at most 50.
- **Refused before the first turn**: a goal with no limit (model calls, tokens, cost, steps, time or a deadline), a meter that does not carry the goal's limits, no checks or a check that cannot run, a words, status or synopsis check over a `full` or `doc` scope that holds no document a goal can read (the `changed` scope may be empty when nothing has changed; the refusal says by count when a rule withholds the scope's documents or they are archived, and names none), more than 50 iterations, and a coherence scope over the 20-document guard (coherence.md §6.2) that the writer has not approved. A check whose scope goes empty during the run (its last document archived, or withheld by a rule) is not met, whatever its kind but `changed`, so a run cannot end `passed` having measured nothing. The guard is satisfied once, at the start, and not asked again per iteration. The goal's limits are the run's: the session is made with one `BudgetMeter` (`AgentSessionOptions.meter`) and the runner is given the same one, so every iteration spends from it.
- **Write scope.** `Goal.writeScope` is the whole project (default) or named documents and folders. `goalRules(base, scope, state)` adds, to the rules the harness is made with, a write-deny on every subtree that holds nothing of the scope, with source `session`, so an out-of-scope write is refused at the preflight like any rule's, before it is drafted or carded. A folder that only contains the scope is not denied by a subtree rule, so after each turn the runner also checks the applied writes of the report against the scope (`scopeBreaches`), using the tree as it was before the turn and counting a write whose documents cannot be worked out as a breach, which includes an external (`mcp__`) call that ran under a card: its effect is on a server and no document of it can be named (a trusted external read runs without a card and is not judged, even when it rode an approved plan, whose card lists its reads; only the one-step card of a call itself counts). The preflight rules do reach an external call: it is evaluated with its nodes unknown, so a scoped write-deny fails closed on it and it is refused before it runs (a trusted external read is not a write and passes). The after-the-turn check is the backstop for an external call that ran, which happens when the scope leaves no subtree to deny (every sibling holds the scope), or when the host built the harness without `goalRules`; it still ends the run `out-of-scope`. It runs after the call, so it cannot undo what a server has done. A breach ends the run `out-of-scope`. A write that names no binder node (an export, a vocabulary or filter change) is not judged by it; a codex write is judged by the documents it attaches to or detaches from.
- **Read rules.** The goal path is a second route to the prompt, so it applies the same read-deny view as the rest of the harness (§4). `GoalOptions.withheld` is required (`() => harness.withheldAnywhere()`), read afresh at each evaluation. A withheld node is left out like an archived one: no check measures it (`words.between`, `status.all`, `synopsis.filled`), `coherence.clean` runs with the scan port's exclusion and dialogue view (`withheldState`), the large-scope guard counts only what the agent may read, a `doc` scope naming a withheld node is neither read nor reported as unknown, and a held finding that quotes one counts without its title or text. An iteration's request therefore never names, counts or measures a withheld document; a result says only how many were left out, counted as the scope's distinct documents. The closing coherence run excludes them the same way.
- **One coherence run.** When a goal has a `coherence.clean` check, the runner records one coherence run when it ends, unless the goal was refused (it never started), every check it names is turned off in Settings › Coherence, or the scan failed (said in `notes` and appended to `reason`; the status is unchanged; "did not run" and "ran but could not be recorded" are separate cases): the checks' scope when they share one (else the whole manuscript) and their checks together. It becomes the last scan in Findings. Evaluations in between record none.
- **Restore.** Each iteration's writes are its turn's undo group, so `session.restore(turnId)` takes one iteration back; `restoreGoal` restores every iteration, newest first, which is restoring to before the goal. A restore that leaves writes in place is reported as partial, naming them (`complete` is false on the entry, and the ask-back run's reason says how many writes were left); `restoreGoal` stops at the first iteration it could not fully take back, so an older iteration is not undone under newer writes, and the failed entries stay in the undo group so the restore can be retried. An iteration that was already taken back completely has no group left, so a second `restoreGoal` skips it and carries on with the older ones; a skip is read as "already taken back", and the same skip happens if the session handed in did not run the goal, so pass the session that did and compare the entries with `run.iterations`. The closing coherence run is a record of what was measured, not a document write: it is in no iteration's undo group, so `restoreGoal` (like `session.restore`) leaves it in place as the last scan in Findings, and a host that wants it gone discards the run (`coherence.discardRun`, coherence.md) or supplies `recordCoherence`.
- **The record** (`GoalRun`) is held in memory: the status and its reason, each iteration's checks before and after, its turn report and its writes outside the scope. The run log (§5.1) already holds each iteration as a turn. Left for later: a panel, a log of the goal itself so a reload resumes it, the writer's Stop owning the run, `goalId` and `iteration` on the turn report, and an optional model verifier that advises and never gates by default.

## 8. Streaming & UI integration

Streaming responses render progressively in the agent panel; tool-call cards collapse to summaries on completion (in-progress actions show without stealing focus). **Per-tool status card component vocabulary:** every tool call renders as a card `{tool name, risk badge, live status, collapsible args/result, elapsed timer}` with the lifecycle **pending-approval → running → done | cancelled | failed** (muted appearance for cancelled/failed). **Consecutive tool calls group** in one collapsible container that auto-expands while streaming and collapses on completion. Cancelled/failed cards stay visible with the structured error/AskBack envelope inside — never bare text outside a card. **A step refused before any card is shown for it** (a draft refused before its model call, an external tool the turn has not loaded, or a single write-auto step its preflight refuses) **is a failed status card of its own in the turn**, carrying the refusal in the words the planner is sent; the same refusal goes back to the planner, so the card and the planner's next request say the same thing. No partial tool results are ever rendered (results arrive whole — consistent with the MCP atomicity posture, extensibility §3.3). The one thing shown while an external call runs is the server's progress report (`StatusCard.progress`): a bar when the server gave a total and a counter when it did not, always with the numbers in words, and the server's message as plain text, at most 200 characters, labelled "The server says" and never sent to the model. It is shown at most four times a second, belongs to the running state only, and a read that reports progress gets its running card from its first report. A failed card of a call that may have acted reads "Why it did not finish" and not "Why it did not run". Draft text streams into a ghost-preview region of the editor, committed only on tool completion + undo-group registration. **Ghost-preview post-generation loop:** when generation completes, the ghost region offers **Apply / Retry / Discard** — Apply commits into the undo group; Retry regenerates from the same assembled context (deterministic variant seed, same budget); Discard empties the ghost without touching the doc. Rejected: auto-apply ("auto-keep") as a default; in the app, in Ask, prose edits are never applied without preview. Over MCP, the host's confirmation of a call whose arguments are the prose (`scene.apply`, §3, "External-only rows") stands in for the preview, with the mode preconditions and the body snapshot, and undo is the net: the confirmation is not a review. Accept edits and Auto (§4) apply a draft at once, after it has streamed into the ghost region. The apply-then-review alternate (tracked-changes marks in-editor) stays a v0.2 option, using `@handlewithcare/prosemirror-suggest-changes` (exact 0.1.8, MIT; per-span attrs = tool-call id, so review groups accept/reject per tool call; editor-engine §12 and §15).

**The command list.** The Intent box is a WAI-ARIA combobox (`CommandComposer.tsx`; role `combobox` named **Intent**, `aria-expanded`, `aria-controls` the **Commands** listbox only while it is open, `aria-activedescendant` the active option, focus never leaves the box). A leading `/` followed by name characters opens the list, filtered by prefix, in the closed set's order, each option with its argument hints and a description. Down, Up, Home and End move through it (the radio-group step, `radio-keys.ts`, wrapping); **Tab** completes the active command and a space; **Enter** completes it, and sends it at once when it needs no argument, or sends the line when the name is already typed in full; **Escape** closes the list and keeps the text, and the next keystroke opens it again. It never opens while an input method is composing (`isComposing`, and the composition events), and a full-width `／`, a slash after other text and `//` do not open it. A command's answer (help, a missing or ambiguous argument, the context, a line kept while a turn runs) is a `role="status"` note under the box with **Dismiss**: view state of the controller, never saved or sent. A line the command could not use stays in the box to be corrected.

**Stop, steering and the queue in the panel.** The Intent box is open while a turn runs (it is disabled only with no provider). Enter sends when no turn runs and queues the text as the next turn when one does; Ctrl/Cmd+Enter sends it to the running turn as a note. **Stop** is in the header while `stoppable` (a turn runs, or a card waits), and Escape in the panel with an empty Intent box does the same; both are `keymap.ts` actions (`agent-stop`, `agent-steer`, `agent-send`), Escape yields to a half-typed message and to a dialog, and `role="status"` announces what Stop, a note or the queue did. The controller owns the queue (`queue`, `queuePaused`): view state of the controller, never project state, never undoable, never in the bus or the activity log; it is in memory and a reload starts it over. An entry keeps its `SubmitOptions` (a demo intent stays a demo intent), and its text is parsed when it runs, not when it is queued. When a turn settles, an undelivered note goes to the front of the queue marked `fromUndeliveredNote`, and the next entry starts on a microtask after `busy` is clear, so `turnsStarted` rises only once the turn before has settled and no two turns run at once. The queue pauses after a turn that ended `failed` with an ask-back, or never ran, until the writer answers it or chooses **Run the queue**. A queued chip can be edited, removed, moved (↑/↓ buttons, or drag) and promoted with **Steer now**. A note typed while a card waits is held until the writer chooses **Send with Cancel** or **Queue as next turn**; it neither approves nor drops the card. The panel names its queue "Queued messages", apart from any background task list.

**Background tasks in the panel.** A plan offer card (`PlanOfferCard.tsx`) appears in the panel while the loop waits for the writer's answer, with the three buttons; Stop or Escape cancels it. **Background tasks** (`BackgroundTasks.tsx`) lists the tasks above the turns, the ones ready to review first (the Inbox). Each row has its status in words ("Ready to review: 5 of 5 drafted, 1 out of date", "Failed: nothing could be drafted"), the items drafted, the model calls used of the cap, the tokens, and any provider error in the provider's words. The out-of-date count is read against the project as it stands when the row is drawn. **Review** opens the held drafts as a turn (`reviewTask`); while another turn runs it says so and starts nothing. **Cancel**, **Resume** and **Dismiss** act on the task; every control is a button and the row's name is in its accessible name. The header's polite status region announces a task that becomes ready, fails or is interrupted. A task that was applied stays in the list until it is dismissed or pruned.

**Task list.** The panel shows a checklist of the turn, derived from the events above and never declared by the model, so it costs no tokens, is the same for the same events, and cannot claim work that did not run. `reduceTaskList` (`agent/progress.ts`, pure, exported with the loop) folds a turn's events: the planner row (in progress while the model is asked or a draft streams), one `reads:<round>` item for each round of reads (a count, not a row per call), and one item per step of a plan card, keyed `<card sequence>:<origin>`. A card shown again after an edit re-derives its own items: a dropped step is `skipped`, a reorder reorders its items, a refused step is `failed` with the first sentence of the refusal as its reason. A second card, whether a one-step confirm or a later plan, appends its items after the first card's. Item states are `pending`, `waiting` (the card waits for the writer), `in_progress`, `done`, `skipped` (dropped, cancelled, or never run after a failure or a stop) and `failed`; exactly one item is in progress while the model is asked or a step runs, and none is left open once the turn reports. Every tool has a phrase (`TASK_PHRASES`, keyed by tool name, so a registry row without one fails the type check and `progress.test.ts`); an external tool's phrase is built from its server key and alias, never from its description. `model.call` is emitted by the one budgeted call site (`modelCall`), after the count is taken and before the request goes out, so the footer's "Model calls: N of 8" matches what `BudgetExceeded` sees; the footer turns to a warning on the last two calls. The agent header shows `headerLineOf` ("Step 3 of 5 · Drafting “The Landing”", "Waiting for you · Plan, 3 steps"), a polite live region that moves with the step and not with streamed text; the checklist itself is an ordered list that states each state in words, open while the turn runs and folded when it settles. The list is in-app state: it is never sent to the model or anywhere else. A model-declared list (an `agent.todo` protocol row beside `agent.plan`, `risk: 'meta'`, replacing the whole list on each call and merged under the derived state) is a follow-up gated on eval evidence that the derived list misses multi-round work; it would change the frozen surface and spend tokens, so it is not built.

**Diff rendering for the loop (editor-engine §14):** ghost regions and plan-card diff blocks render prose diffs **word-granular** via the two-path renderer — DMP word-mode (`diff_linesToWords` recipe + `diff_cleanupSemantic`) for text-vs-text previews (zero steps exist), changeset + `simplifyChanges` + widget/inline decorations for in-editor post-Apply review (v0.2, over the completed turn's steps). Mark/attr-only edits surface as plan-card "modified" rows, never inline decorations. Deletions render from old-doc spans (widget decorations) — deleted text never enters the doc. Changesets build **once per completed turn** (never incrementally — build-order nondeterminism), matching the no-partial-results posture above. Zero new dependencies (both mechanisms ride existing pins).

**Plan persistence:** plan cards are data (§2 — the edited card IS the executed plan), and plans stay in-app state; there is no plan file format. A turn's log in the runtime database (§5.1) is runtime state, not a plan format: it holds the events of a run, and a plan card appears in it only as one of them. If plan-as-artifact export ever lands, it must be front-matter-structured Markdown (structured plan JSON in the front matter, a human-readable body), so the structured head round-trips unambiguously; free-text re-parse is rejected. Finished plan cards are history, not state: they belong to the activity log and undo group they produced; no separate plan store exists. **The one persisted form of a plan is a macro** ([extensibility.md](extensibility.md) §10): the writer saves a plan they approved, with some values left to fill in, as JSON in the manifest's `macros[]`, and runs it again from Settings › Macros. It is JSON and not front-matter Markdown because the store's front-matter codec cannot carry nested steps; the structured head and the human-readable body of the rule above are not needed when the writer, not an exporter, makes it. A macro's run is a plan submitted with `submitPlan`, so it is a card like any other.

**Ghost mechanics ([editor-engine.md](editor-engine.md) §8):** the ghost region is a **separate read-only editor instance** sharing the Caotang schema ([editor-engine.md](editor-engine.md) §3) — decorations in the main editor were rejected (delta-churn on every streamed chunk, coupling to live selection). Ghost appends are history-excluded and never bump `doc.revision`; Apply goes through the bus (`doc.write` / `editor.replaceRange` after anchor resolution), after which the main editor re-renders from the store (Lane 2); Retry/Discard never touch the doc. `expectedRevision` on Apply guards the user-mid-keystroke race (conflict envelope, ghost preserved).

**Apply-then-review ([editor-engine.md](editor-engine.md) §15):** with Settings › Writing set to *Mark the changes for review*, an approved `scene.draft` (draft, continue or rewrite_selection) still writes the store first, through the bus, and the turn's card still ends in `done`. The controller remembers the step id of each draft that lands, by scene (the editor's `consumeApply(docId, revision)` answers with that id and the revision it passed in), the editor shows the difference as marks (the agent changes the project only through the bus; the marks are display), and the turn's status card gains a sub-line "N suggestions pending review" with **Accept all** and **Reject all** for the turn. Accepting changes nothing the store holds; rejecting is the writer's own edit and is logged as **You**. "Restore to before this turn" is unchanged and takes the whole turn back.

**The model's limits on the card.** A step's prompt preview carries the window check and the cost of the model the turn runs on (context-assembly §5): the app's context port merges the gateway's `modelLimits` for the profile, model and thinking level the role's running turn resolved into the Settings budgets, so the card's window warning, its "About $… for the whole plan" line and the completion estimate (the profile's own `maxOutputTokens`) are the step's own, not only a coherence review's. A live context meter under the Intent box and per-request pins and leave-outs (issue #69, phases 2 and 3) are not built.

**Refusals on the card.** A refusal is said on the card it belongs to, in words. A plan step the harness refuses shows its reason beside its disabled **Approve**, and that includes a step a hook the writer set blocks ("The hook “No lanterns” stopped scene.draft: …"); a hook that only warns puts its words on the step and leaves Approve on. A draft that would replace a scene's text (`scene.draft` in `draft` mode on a document that already holds text) is refused at the card's preflight as well as before its model call, so a card cannot approve what its apply would refuse. That refusal is two plain sentences: the refusal itself (the document already holds its words, so nothing was written), and a hint that names only the choices the card offers (continue, or rewrite a passage), since the card offers no overwrite. The planner is given the same refusal as the result of its call. A step refused before any card is made, which has no card to carry its reason, is shown as a failed status card of its own in the turn (the paragraph above), so a refusal never stands as bare text outside a card; the planner is sent the same words.

**A delegated call** (`agent.delegate`) is shown as the ordinary status card of a tool call, with no new card kind. It adds the agent's name, the model calls reserved for it, a word for how it stands (Working, Finished, Stopped before it finished, Failed: the state is text, never colour alone), the elapsed timer the card already has, and three disclosures that are native `<details>` elements, so the keyboard and a screen reader reach them: the **Brief** and scope it was given, its **Notes** once it has finished, and its **Transcript**, the agent's own trace rows listed as they happen. A plan step the agent proposed carries a "Proposed by the <agent> agent" badge on the plan card.

## 9. Evals (deterministic, mock-provider)

Scenarios run headless against the mock provider (provider-gateway §8): scripted intent → expected plan/confirm cards → tool-call trace assertions (ordered, with param digests) → final project-state assertions (project-format schema validation) → response-shape assertions (caps respected, errors model-facing, and every successful result matching the `resultSchema` of its row, with the JSON path of a mismatch). Tool descriptions are **versioned, tested artifacts**, enforced by the prompt manifest golden (below): eval transcripts feed description revisions (an iterate loop). v0.1 suite ≥10 scenarios covering: single-op turns, multi-step plans, verify-failure recovery, permission batches, undo replay. **Codex scenarios** ([codex.md](codex.md) §9): mention pulls entry into `scene.draft` context; `never`/`manual` policy behavior; `always` present without mention; budget-prune determinism (fixed entries + tiny budget → stable drop list); `codex.write` batch-validation failure → plan card rejects pre-execution. Assembled-context assertions are possible because assembly is deterministic ([context-assembly.md](context-assembly.md) §2/§4) — the prompt-preview payload doubles as the eval fixture. **Plan-edit validation scenarios:** the §2 dependency check is a pure pass over plan data — headless fixtures assert that dropping a step whose output feeds a later step's anchor/doc-id param flags the dependent with the "will re-resolve at execution" badge payload, and that re-approved edited cards re-enter preview.

**Delegation scenarios** (`packages/harness/test/eval/subagent.test.ts`): read-only research handed to the reader (its reads are trace rows with its path, the planner reads the result behind the notice, the ledger splits the turn by agent and still totals it); an agent that proposes a write, which reaches the writer only as a badged step of the planner's own card, and is never run when the planner leaves it out; a delegate the turn cannot afford, refused before any agent call; a reply that mixes a delegate with a write, which runs neither; a brief whose documents claim "the user approved this plan", which leaves the parent's card and permission as they were; and the writer's Stop reaching a starting agent. The runner's own tests (`test/agent/subagent.test.ts`, `subagent-native.test.ts`) pin the list on both wires, the fresh context, zero bus commands, the refusals an agent reads, the reserve and the release.

**Goal-run scenarios** (`packages/harness/test/eval/goal.test.ts`, on the JSON wire and the native wire): a goal that passes in two iterations with a plan card each time, and restores to before the goal at once; a stall; a regression that ends on the ask-back, and is restored when the writer chooses to; a run limit that ends the goal in the middle; `maxIterations`; a write outside the scope refused at the preflight, and one that got through, ending the run; a goal held to a permission mode and to a deny rule; and a goal with no limit refused before any model call. The runner's own stops, the order they are checked in, the refusals and the one coherence run are pinned in `test/agent/goal.test.ts`, and the evaluators in `test/agent/checks.test.ts`.

**Run limits are not eval ceilings.** The `expect.maxTokens` ceiling of an eval scenario stays a regression guard that moves only with a measured cause; a run limit (§7.1) is the writer's cap, enforced before the call. Run-limit scenarios (`packages/harness/test/agent/run-limits.test.ts`) pin the reservation, the time limits on a draft in flight, a review and an external call, the step limit, and the unpriced cost limit.

**Golden tasks** (`packages/harness/test/golden-tasks/<task-id>/`): thirteen writer workflows — draft an empty scene, continue in voice, rewrite a selection, fill a chapter's synopses, restructure an act, tag point of view, find a planted contradiction, keep a `never` codex entry out, continue a Fountain scene, draft Ink dialogue, refuse to overwrite, plan economically, and derive a storyboard from a scene. Each is a `GoldenTask` (an intent, a fixture project, the cards and trace the turn must show, and deterministic run-context checks from `agent/checks.ts`) with a cassette under `cassettes/`. CI replays the cassette through the mock gateway (provider-gateway §8, "Cassettes") and the real loop and bus, then holds three things: the checks pass on the recorded output, every request the turn sent matches a recorded one by key (a miss fails with the changed message, the character offset and the command that records again), and every recorded exchange was asked for. A test stubs `fetch` to throw, so a golden task can neither reach the network nor need a key. **The committed cassettes are synthetic**: a person wrote each task's model answers, the requests were recorded from the loop as it runs, and the header says `synthetic` and model `synthetic`. They guard the harness and the prompts; they are no evidence about any model, and nothing may present them as such until recordings from real models land. Recording from a real model and a model benchmark (`eval:record`, `eval:bench`, an optional judge column) are not built; when they are they run locally with the developer's own `CAOTANG_SMOKE_*` keys, refuse when `CI=true`, and are never a CI gate.

**Prompt manifest golden** (`packages/harness/test/golden/prompt-manifest.json`, full texts in `prompt-manifest.md`): the hash of every text Caotang sends a model that is not the writer's own — the planner system message on both wires, the native tool declarations, each draft role, the review prompts, the delegated agents' roles — and of every registry row's description with its `descriptionVersion`. A changed text fails and is rewritten on purpose with `CAOTANG_UPDATE_GOLDEN=1`; a tool whose description changed while its `descriptionVersion` did not fails separately, naming the tool, and the rewrite refuses until the version is bumped.

**Traced runs.** `runScenario(scenario, { trace })` writes the turn's trace (§5.2) from a manual clock and the session name `eval`, handing the scenario's gateway the observer and the clock; `test/eval/trace-determinism.test.ts` holds two runs to the same bytes.

**Trajectory-eval discipline:** the §9 trace assertions are *trajectory* evals over our own activity log, with no framework dependency: **strict** (exact call order, exact params) for single-op turns; **unordered/subset** (same calls, any order / required calls present) for multi-step plans whose steps commute; **token-budget assertions** (per-run token ceiling + `response_token_cap` respect). Evals assert against the deterministic mock and deterministic assembly, so the suite cannot drift from behaviour. LLM-as-judge stays out of the CI suite (it would break determinism) — judging is a *product* feature (`coherence.review`), not an eval mechanism; a later local benchmark may use a judge model, reported in its own column apart from pass/fail and never in CI. Streaming scenarios assert card-state transitions match the mock script's call timeline. **Task-list assertions:** every scenario run is held to the task list's invariants (`taskListFailures`, called by `checkRun`): never two items in progress, one in progress while the model is asked, none open after the report. A scenario may also state its final list (`tasks`, strict order): the single-op turn lists the planner row and its one step, the multi-step turn lists its read round and each step of the card.

External MCP tools never join the Tier-1 band, and neither do the 25 deferred extension rows (`load: "deferred"`: `doc.import`, `codex.import`, the coherence module's three, the media track's six, `skill.load`, `memory.read`, `agent.delegate`, the four external-only rows and the seven primitive rows): both load through `tool.search` ([extensibility.md](extensibility.md)), the extension rows by their registry name and the external tools by their qualified name. A plugin system that runs third-party code in the app stays a non-goal (ARCHITECTURE §4); declarative extension bundles are specified, not built ([extensions.md](extensions.md)).

## 11. Headless use

The loop is callback-shaped, `decide(pending)` for every card and `emit(event)` for every event, and nothing in it needs a browser. `@caotang/sdk` (`packages/sdk`) is the supported way to run it in Node: `openProject({ root, provider, approval, write })` resolves to a project whose `run(intent)` is one turn. It loads the Ink compiler before it opens the folder (dialogue-narrative.md §2.2), because the dialogue tools and the branch checks compile synchronously and fail closed without it.

**One factory.** `createProductHarness({ state, ports, … })` in `@caotang/harness` builds the harness every host uses. `ports: 'agent'` wires the agent ports (`createAgentPorts`), the coherence module's dialogue facts and review context, and the `coherence.review` model the host gives; the desktop and the SDK use it. `ports: 'external'` wires only `codex.read` and leaves the coherence defaults alone; the MCP server uses it, because it holds no provider profile or key.

**The folder.** The SDK opens the folder through the same Node folder session the MCP server uses (`openFolder`): it takes `.caotang-mcp.lock`, keeps the manifest text and a digest of every document and codex file it loaded, checks them before every save, and writes one save at a time. The lock file keeps its name. A change by another program stops the writes (`FolderChangedError`), and the change stays in memory.

**The provider.** One profile, from a preset and its fields, or the demo provider (`'mock'`). The key is read once into an in-memory key store; every task role resolves to that profile, and the gateway's egress pin sends the key to that profile's origin only. Nothing about the key is written to the project, a report, an event or an error message.

**The cards.** The approval policy answers `decide`:

| Policy | A card | A write that needs no card (`meta.set`, `notes.append`) |
|---|---|---|
| `'read-only'` (default) | cancelled | refused by the harness the loop is given |
| `'auto'` | cancelled | runs |
| `'approve-all'` | approved if the card can be approved as shown; otherwise cancelled | runs |
| `{ approveTools: [...] }` | approved if the card can be approved as shown and every step still to run is a listed tool; otherwise cancelled whole | runs |
| a function | the function decides | runs |

`approve-all` never sends `acceptTruncated`: a draft the provider cut off at its output limit is cancelled, not kept. A built-in policy's cancel is reported as input the turn needs: the report carries `askBack: { code: 'needs_input' }` naming the step and the policy, and the `report` event carries the same report. `approveTools` is a filter on a whole card, not a per-primitive toggle (§4), and a cut draft is cancelled as in `approve-all`. `onDecision` receives each answer to each card with the rule that gave it. `run(intent, { plan })` runs a plan the caller wrote through `submitPlan`, with no planner call. A function that throws cancels the card, and the turn's report rejects with its error after the turn ends. An aborted `signal` answers a waiting card with Cancel, as the panel's Stop does (§2).

**Saving.** `write: false` (default) keeps every change in memory, an export included; `diff()` writes the state into an in-memory folder with `writeProject` and compares each file a save owns with the folder's. `write: true` saves after each turn and each `call()` that changed the project, and only when the diff is not empty, because a save stamps the manifest. The diff holds what the session changed since the open or the last save: a file the state renders as it did then (CRLF, hand-edited front matter) is not in it and is not rewritten, and a file the load held because its bytes are not UTF-8 is left as it is. `save()` always writes. `onSave(changes)` receives the diff of each write, taken just before it. Under `'read-only'` `coherence.json` is never written. `restore(turnId)` takes a turn back in memory while the process lives; the undo history is not saved.

**`call(tool, params)`** is one registry call as an external caller makes it (extensibility.md §9): no model, no plan runner, the same hard-deny list, a refusal returned as a result.

**The command line.** `caotang agent` (`packages/cli`) is `openProject` with flags: `--permission` and `--approve-tools` are the approval policy (`packages/cli/src/policy.ts` is the one table that maps a mode name to an SDK policy), `--write` is `write: true`, `--plan-file` is `run(intent, { plan })`, and the key is read from the environment variable `--key-env` names and nowhere else. Its stdout is the chosen format only (`text`, `json` or `stream-json`); a `decision` line in the stream is `onDecision`, so an unattended run records what each card was answered and why. The exit code follows the report: 0 for `replied` or `applied`, 4 for `needs_input` (a cancelled card, the model-call bound, a provider failure), 5 for `conflict` and `anchor_unresolvable`, 6 for `verify_failed`; 2 is a usage error, 3 a folder another writer holds, and 130 and 143 are SIGINT and SIGTERM, which cancel the turn as the panel's Stop does and release the lock first. Without `--write` the diff is printed and nothing is saved. `caotang scan` (`packages/cli/src/run-scan.ts`) is not an agent turn: it takes no provider and no key and calls no model, so it needs no policy; it is specified in [coherence.md §9.1](coherence.md).

Turns and calls run one at a time. The events of a turn are held until read, and past 4,096 held events the oldest streamed text (`model.delta`, `model.reasoning`, `draft.delta`) is dropped, never another event.

## 12. Recurring tasks

A recurring task is an intent, a plan or a scan that the project remembers and offers when it is due. The definitions live in `tasks.json` beside `caotang.json` (project-format §1); the model, the codec, the recovery posture and the due-date rule are the pure package `@caotang/tasks`, and the run is the desktop app's (`apps/desktop` `recurring-tasks.ts`). The recovery posture is `coherence.json`'s: an unreadable file is kept under a `.corrupt-<timestamp>` name and restored from a snapshot, a file from a newer format is shown and never overwritten, and so is a file with no `formatVersion`, which is most likely another program's: it is left as it is and nothing is saved to it until the writer renames or removes it. This section is the browser build. A command line for tasks, an agent or MCP tool for them, a tray, and a model task that starts by itself are not built (below).

**A task.** `{ id: "t_" + 10 Crockford base32 characters, name, enabled, schedule, whenDue, body, permission, maxModelCalls? }`. `schedule` is `manual`, `on-open` (once each time the project opens), `daily` or `weekly` (a weekday), the last two from a local `HH:MM`. There is no cron syntax. `body` is `{ kind: 'intent', text }`, `{ kind: 'plan', steps }` (the planner's own `agent.plan` steps, parsed with `parsePlan` when the file is read: a step that does not parse makes that task unrunnable and visible, and does not fail the load) or `{ kind: 'scan', scope: 'full' | 'changed', checks? }` (the deterministic checks of coherence.md §5.1; no model). `permission` is `read-only` (Plan only) or `ask`, and a larger word in a file is read as `ask`: the file is a ceiling and can only lower a run. A task that calls a model is an instruction, or a plan with a model-backed step (`usesModel`).

**Due.** `dueTasks(file, lastRuns, now, timeZone, opening)` is pure: it reads no clock and no default zone. A daily or weekly task is due when the most recent occurrence of its rule, as a local wall-clock minute, is later than the wall-clock minute of the task's last handled run on this machine (a run or a skip). So a task missed for several days is due once; a task whose time falls in a spring-forward gap is due when the clock first passes it; and a task that ran in the first pass of a repeated fall-back hour does not run again in the second. A manual, disabled or unrunnable task is never due, and an `on-open` task is due only on the evaluation made as the project opens.

**Offered, not sprung.** A due task is offered as a card with **Run now** and **Skip**, in the agent panel, shown with the drawer closed too, and announced through a polite live region. Skip is a record, so the offer does not return before the next occurrence. `effectiveWhenDue(task, consent?)` decides what starts without a click: only a `scan` whose `whenDue` is `run`. A scan reads the project and calls no model, so it needs no consent and no cap. Anything else is offered, whatever the file says: starting a model task, or a plan, by itself needs a consent record for exactly that task (its `bodyHash`: body, schedule, permission and cap) and, for a model task, a `maxModelCalls` cap. The function takes that consent and the hash is tested, but no consent is kept or asked for in this build, so a model task saved as `run` is offered and says so. An unattended run of a model would stage its results for the writer's review and never apply text; that staging is not built for tasks.

**A scan task** runs `session.scanCoherence` with the checks Settings › Coherence has on and the documents a read rule withholds (`harness.withheld('coherence.scan')`, §4) left out, the way the agent's own `coherence.scan` leaves them out, and appends its run and findings to `coherence.json` through the session. It makes no gateway request. A scope over the document guard is not approved on the writer's behalf: the run fails and says so. A run says what it did not do in its record: a whole-project scan that had no document to read fails with "Nothing was scanned" (and names a read rule when one withholds anything), and a scan that dropped checks turned off in Settings › Coherence lists them, as the agent's own `coherence.scan` does for its skipped checks. A `changed` scan with nothing changed is a legitimate empty run and stays `done`.

**Run now** is an ordinary turn: `submit` or `submitPlan` with `role: 'background'` (so the gateway's ledger and the request log record it under the Background role and the role's profile is used), a session of its own for that role, the task's `maxModelCalls` as the turn's call cap (it can only lower the model-call limit the writer set in Settings › Agent, never raise it), and the permission mode `effectiveMode(task.permission, setting, panel)`: the lowest of the file, the app setting and the panel's current mode. The cards are the writer's, as in any turn. An unattended run, when there is one, cancels at an approval request and never approves it; the seam is `SubmitOptions.mode`, and the modes of the permission-mode decision are the only vocabulary.

**Runs are the machine's.** Each run is a record in the app database (`task-runs`, project-format §1): when, status (`done`, `failed`, `stopped`, `skipped`), one sentence, the model requests and tokens it used, and its turn so that **Restore to before this run** is offered while the app still holds that turn. A history keeps the newest 20 for each task. A bundle, a folder and an export carry none of it.

**Only while the project is open.** Due tasks are evaluated as the project opens and then every 60 seconds while the tab is visible. There is no Service Worker and no background process; the panel and the guide say so.

**The writer's, not the agent's.** Tasks are made, changed, switched off and deleted in the panel. The registry has no tool for them (the tests assert it), `tasks.json` is not a bus target, and the MCP server neither reads nor writes the file. Because the agent cannot make a task, it cannot make itself run on a schedule.

**A task is saved when the indicator says so.** A save of `tasks.json` is several writes (the snapshots, then the file) and none of it is in the browser store until it lands. The save indicator reads *saving* from the moment a save is asked for until it has landed, as it does for a findings write, so the tab's leave-warning and a writer's reload see the task as unsaved while it is.

**Not built.** A model task that starts by itself (the consent record and its screen, and the staging of an unattended run's results for review); `caotang tasks` on the command line and in CI (after `caotang agent`); a task made by the agent; tray runs with the window closed; cron syntax.
