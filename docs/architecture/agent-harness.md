## 1. What "drives the app" means concretely

- The agent is an **operator**: it performs app actions — restructure the binder, draft/edit scene text, set statuses, fill synopses, compile exports — through a **tool surface served by the app's command bus** (the exact command implementations the UI uses). The human never transcribes agent output by hand.
- Every tool call is **visible** (activity log), **grouped** (one agent turn = one undo group), **verifiable** (post-conditions), and **previewable** for multi-step plans.
- Useful *offline from chat*: "reorganize act 2 into scene cards with synopses from my notes", "find continuity drift between chapters", "compile chapters 1–3", "trim 10% from every scene over 2k words, showing diffs".

## 2. Interaction loop

1. **Intent** — free-text instruction or scheduled agent task.
2. **Plan** — for multi-step work the agent emits a plan (ordered steps, each = one tool call with params + expected effect) rendered as a reviewable card; user approves/edits/rejects **once per plan** (batched confirmation). Single reversible ops skip the plan. Single confirm-class ops show a one-step confirm card. **Plan cards are editable before approval** — steps can be reordered, dropped, and params tweaked in place; **the edited card becomes the executed plan** (cheap by design: a plan is data, not prose). Editable plan params include range anchors (edit-anchors.md §2 — the user can fix the target text before approving). **Edit-time dependency check:** Caotang's cards are structured data, so an edit that **drops or retargets a step** statically flags dependents in place: a later step whose params reference the dropped step's outputs (a `TextAnchor` captured from an earlier step's apply, a doc id the earlier step created) renders a "will re-resolve at execution" badge (anchors re-resolve through the edit-anchors §3 ladder at apply time; never a silent mis-address). This is a validation pass over plan data. **Multiple edit rounds are normal:** an edited card re-enters preview rather than skipping it.
3. **Act** — stepwise execution on the command bus; the UI highlights affected nodes/documents live (activity log entries carry node ids + human titles).
4. **Verify** — post-conditions checked per tool (target exists, word counts moved, artifact non-empty). Failure → self-correction ladder: retry with adjusted params (max 2) → structured report with options. **Never silent success; never a bare error string** (errors are written for the model, naming the next corrective tool).
5. **Report** — compact turn summary: what changed, diffs where relevant, undo group id, tokens spent.

**The plan preflight.** Every step of a plan is checked before the card is shown, so the card never promises a step the apply would refuse: a `scene.draft` or `shots.derive` step that names a document or scene the project no longer holds is refused there, before its model call is spent, and the refusal goes back to the planner and onto the card. The deferral rule is unchanged — a step that targets a scene an earlier step of the same plan may create is not refused for that.

**The conversation memory.** One agent session per open panel: the turns before this one are the L6 of the next turn (context-assembly §2). The session is rebuilt when the resolved profile, the model or the thinking level changes, and the per-turn state is cleared on every settlement, so a cancelled, refused or failed turn leaves nothing behind. There is no "new conversation" control in v0.1, and a reload starts the list again, because the conversation memory is in memory only.

**Structured ask-back envelope** (shared by verify failures and anchor non-resolution — one shape everywhere):

```ts
interface AskBack {
  code: 'verify_failed' | 'anchor_unresolvable' | 'needs_input' | 'conflict';
  reason: string;                       // model/user-facing, names the drift or failed postcondition
  candidates?: { from: number; to: number; similarity: number }[];   // anchor drift: ≤3 re-match hits
  revisionDrift?: number;               // apply-time doc.revision − captured revision
  options: string[];                    // 2–3 next actions, e.g. ["re-select in editor", "doc.read the doc", "drop this step"]
}
```

The ask-back renders as a **card in the agent panel** (buttons for the options, not freeform chat) and is the model-facing payload verbatim — one format serves both the model's retry reasoning and the user's review.

**Two wires, one loop.** A turn's wire is chosen once, from the resolved model's capability row (provider-gateway §4): when the row reports `tools`, the planner's callable surface travels as native tool declarations — the reply's tool calls arrive as `tool_calls` with a `tool_calls` finish, results return as `tool` messages keyed by `toolCallId`, and the assistant's own turns (calls + reasoning blocks included) are replayed verbatim. When the row does not, the same loop runs the JSON-in-text protocol: tools described in the system prompt, calls answered as `{"steps":…}` JSON, results in a user message. The choice is per turn and per profile; the steps, cards, refusals and retries above are identical either way — the wire changes how the model *says* a call, never what the call does. Malformed call arguments surface as a keyed tool error with a corrective message, never as a crash.

## 3. Tool registry (v0.1 — frozen surface, 14 tools)

**Slicing principles:** workflow-shaped N-to-1 tools promoted to Tier-1 (a typical goal in ≤5 calls); fine-grained primitives exist on the command bus and are composed *internally* by compound tools — they are **not** separately exposed to the model in v0.1 (Tier-2 dynamic loading = v0.2, evidence-gated). One risk level per tool. Flat primitive params with constrained enums. Idempotent: every call carries a turn-scoped `callId`; the command bus dedupes replays.

## 4. Permission model

- **Auto:** all read tools (incl. `codex.read`); `meta.set`; `notes.append`; structural ops *within an approved plan* (`binder.restructure` is confirm at the plan level, then auto inside it).
- **Confirm (batched per plan):** `synopsis.fill`, `scene.draft`, `codex.write`, `binder.restructure` standalone, `export.compile`, `notes.replace` (v0.2 tool).
- **Never (v0.1):** network beyond the configured provider endpoint; deleting nodes; leaving project scope; touching provider profiles.
- **Hard-deny list — not approvable by any flow** (enforced at the bus gate, [command-bus.md](command-bus.md) §4): network egress beyond the configured provider endpoint; node/codex-entry deletion; provider-profile mutation; leaving project scope. Explicitly **rejected for v0.1**: a classifier/auto-approve mode (Caotang's writes are prose edits inside undo groups, so write-confirm + diff preview + one undo group is cheaper and more honest than a judge model). Per-primitive approval toggles are likewise rejected — one risk level per tool is the honest simplification.
- Every confirmation is batched per plan card; mid-plan new confirm-class calls pause the plan with a delta card.

## 5. Undo & safety

- **One agent turn = one undo group** on the command bus (compound tools sub-group internally, exposed as one) — mechanics in [command-bus.md](command-bus.md) §5.
- `scene.draft` / any body-text mutation snapshots the prior body first (project-format §8 write-ahead) — the safety net writers want before mass edits, made automatic.
- **Checkpoints, framed for users:** each turn renders in the activity log as a checkpoint row — **"restore to before this turn"** — a restore affordance rather than an abstract "undo", which is what makes agent edits trustworthy. Snapshot retention budgets are in [command-bus.md](command-bus.md) §5.1. **Two-lane undo ([editor-engine.md](editor-engine.md) §7):** agent turn applications run as one transaction batch tagged `addToHistory: false` — the user's Ctrl+Z never replays agent edits; restore = snapshot-based, immune to in-editor undo position drift. Restore confirmation states scope explicitly (user edits made after the turn are included in the restore).
- Call-id dedupe: replays of the same `callId` within a turn return the cached result (idempotency).
- Activity log (per turn): timestamped tool calls, params digest, affected node ids+titles, token usage, undo group id. The log keeps every row it is given; the Activity panel shows a 200-row window of it, and the Markdown export carries every row that is not a `view.*` command.

## 6. Context assembly (per model call)

**Spec in [context-assembly.md](context-assembly.md)** — fixed 8-layer stack (system / project summary / codex / structural synopses / prior-scene synopses / focus-doc tail / conversation memory / task), budgets (12k default; tail 3k chars; story-so-far 2k tokens; codex 1k), bottom-up deterministic drop, forward-outline suppressed by default, prompt preview on every confirm-class plan card. Strategy: synopsis tree + mention-keyed codex, zero embeddings.

## 7. Verification & self-correction ladder

Post-conditions are per-tool assertions (e.g. `scene.draft`: doc body non-empty, word delta matches mode; `binder.restructure`: tree validates against project-format schema). Ladder: adjust params → retry (≤2) → structured failure report with 2–3 options. Trace assertions in evals mirror this (§9).

## 8. Streaming & UI integration

Streaming responses render progressively in the agent panel; tool-call cards collapse to summaries on completion (in-progress actions show without stealing focus). **Per-tool status card component vocabulary:** every tool call renders as a card `{tool name, risk badge, live status, collapsible args/result, elapsed timer}` with the lifecycle **pending-approval → running → done | cancelled | failed** (muted appearance for cancelled/failed). **Consecutive tool calls group** in one collapsible container that auto-expands while streaming and collapses on completion. Cancelled/failed cards stay visible with the structured error/AskBack envelope inside — never bare text outside a card. **A step refused before any card is shown for it** (a draft refused before its model call, an external tool the turn has not loaded, or a single write-auto step its preflight refuses) **is a failed status card of its own in the turn**, carrying the refusal in the words the planner is sent; the same refusal goes back to the planner, so the card and the planner's next request say the same thing. No partial tool results are ever rendered (results arrive whole — consistent with the MCP atomicity posture, extensibility §3.3). Draft text streams into a ghost-preview region of the editor, committed only on tool completion + undo-group registration. **Ghost-preview post-generation loop:** when generation completes, the ghost region offers **Apply / Retry / Discard** — Apply commits into the undo group; Retry regenerates from the same assembled context (deterministic variant seed, same budget); Discard empties the ghost without touching the doc. Rejected: auto-apply ("auto-keep") defaults; prose edits are never applied without preview. The apply-then-review alternate (tracked-changes marks in-editor) stays a v0.2 option, using `@handlewithcare/prosemirror-suggest-changes` (exact 0.1.8, MIT; per-span attrs = tool-call id, so review groups accept/reject per tool call; editor-engine §12 and §15).

**Task list.** The panel shows a checklist of the turn, derived from the events above and never declared by the model, so it costs no tokens, is the same for the same events, and cannot claim work that did not run. `reduceTaskList` (`agent/progress.ts`, pure, exported with the loop) folds a turn's events: the planner row (in progress while the model is asked or a draft streams), one `reads:<round>` item for each round of reads (a count, not a row per call), and one item per step of a plan card, keyed `<card sequence>:<origin>`. A card shown again after an edit re-derives its own items: a dropped step is `skipped`, a reorder reorders its items, a refused step is `failed` with the first sentence of the refusal as its reason. A second card, whether a one-step confirm or a later plan, appends its items after the first card's. Item states are `pending`, `waiting` (the card waits for the writer), `in_progress`, `done`, `skipped` (dropped, cancelled, or never run after a failure or a stop) and `failed`; exactly one item is in progress while the model is asked or a step runs, and none is left open once the turn reports. Every tool has a phrase (`TASK_PHRASES`, keyed by tool name, so a registry row without one fails the type check and `progress.test.ts`); an external tool's phrase is built from its server key and alias, never from its description. `model.call` is emitted by the one budgeted call site (`modelCall`), after the count is taken and before the request goes out, so the footer's "Model calls: N of 8" matches what `BudgetExceeded` sees; the footer turns to a warning on the last two calls. The agent header shows `headerLineOf` ("Step 3 of 5 · Drafting “The Landing”", "Waiting for you · Plan, 3 steps"), a polite live region that moves with the step and not with streamed text; the checklist itself is an ordered list that states each state in words, open while the turn runs and folded when it settles. The list is in-app state: it is never sent to the model or anywhere else. A model-declared list (an `agent.todo` protocol row beside `agent.plan`, `risk: 'meta'`, replacing the whole list on each call and merged under the derived state) is a follow-up gated on eval evidence that the derived list misses multi-round work; it would change the frozen surface and spend tokens, so it is not built.

**Diff rendering for the loop (editor-engine §14):** ghost regions and plan-card diff blocks render prose diffs **word-granular** via the two-path renderer — DMP word-mode (`diff_linesToWords` recipe + `diff_cleanupSemantic`) for text-vs-text previews (zero steps exist), changeset + `simplifyChanges` + widget/inline decorations for in-editor post-Apply review (v0.2, over the completed turn's steps). Mark/attr-only edits surface as plan-card "modified" rows, never inline decorations. Deletions render from old-doc spans (widget decorations) — deleted text never enters the doc. Changesets build **once per completed turn** (never incrementally — build-order nondeterminism), matching the no-partial-results posture above. Zero new dependencies (both mechanisms ride existing pins).

**Plan persistence:** plan cards are data (§2 — the edited card IS the executed plan), and plans stay in-app state; there is no plan file format. If plan-as-artifact export ever lands, it must be front-matter-structured Markdown (structured plan JSON in the front matter, a human-readable body), so the structured head round-trips unambiguously; free-text re-parse is rejected. Finished plan cards are history, not state: they belong to the activity log and undo group they produced; no separate plan store exists.

**Ghost mechanics ([editor-engine.md](editor-engine.md) §8):** the ghost region is a **separate read-only editor instance** sharing the Caotang schema ([editor-engine.md](editor-engine.md) §3) — decorations in the main editor were rejected (delta-churn on every streamed chunk, coupling to live selection). Ghost appends are history-excluded and never bump `doc.revision`; Apply goes through the bus (`doc.write` / `editor.replaceRange` after anchor resolution), after which the main editor re-renders from the store (Lane 2); Retry/Discard never touch the doc. `expectedRevision` on Apply guards the user-mid-keystroke race (conflict envelope, ghost preserved).

**Refusals on the card.** A refusal is said on the card it belongs to, in words. A plan step the harness refuses shows its reason beside its disabled **Approve**. A draft that would replace a scene's text (`scene.draft` in `draft` mode on a document that already holds text) is refused at the card's preflight as well as before its model call, so a card cannot approve what its apply would refuse. That refusal is two plain sentences: the refusal itself (the document already holds its words, so nothing was written), and a hint that names only the choices the card offers (continue, or rewrite a passage), since the card offers no overwrite. The planner is given the same refusal as the result of its call. A step refused before any card is made, which has no card to carry its reason, is shown as a failed status card of its own in the turn (the paragraph above), so a refusal never stands as bare text outside a card; the planner is sent the same words.

## 9. Evals (deterministic, mock-provider)

Scenarios run headless against the mock provider (provider-gateway §8): scripted intent → expected plan/confirm cards → tool-call trace assertions (ordered, with param digests) → final project-state assertions (project-format schema validation) → response-shape assertions (caps respected, errors model-facing). Tool descriptions are **versioned, tested artifacts**: eval transcripts feed description revisions (an iterate loop). v0.1 suite ≥10 scenarios covering: single-op turns, multi-step plans, verify-failure recovery, permission batches, undo replay. **Codex scenarios** ([codex.md](codex.md) §9): mention pulls entry into `scene.draft` context; `never`/`manual` policy behavior; `always` present without mention; budget-prune determinism (fixed entries + tiny budget → stable drop list); `codex.write` batch-validation failure → plan card rejects pre-execution. Assembled-context assertions are possible because assembly is deterministic ([context-assembly.md](context-assembly.md) §2/§4) — the prompt-preview payload doubles as the eval fixture. **Plan-edit validation scenarios:** the §2 dependency check is a pure pass over plan data — headless fixtures assert that dropping a step whose output feeds a later step's anchor/doc-id param flags the dependent with the "will re-resolve at execution" badge payload, and that re-approved edited cards re-enter preview.

**Trajectory-eval discipline:** the §9 trace assertions are *trajectory* evals over our own activity log, with no framework dependency: **strict** (exact call order, exact params) for single-op turns; **unordered/subset** (same calls, any order / required calls present) for multi-step plans whose steps commute; **token-budget assertions** (per-run token ceiling + `response_token_cap` respect). Evals assert against the deterministic mock and deterministic assembly, so the suite cannot drift from behaviour. LLM-as-judge stays out of the CI suite (it would break determinism) — judging is a *product* feature (`coherence.review`), not an eval mechanism. Streaming scenarios assert card-state transitions match the mock script's call timeline. **Task-list assertions:** every scenario run is held to the task list's invariants (`taskListFailures`, called by `checkRun`): never two items in progress, one in progress while the model is asked, none open after the report. A scenario may also state its final list (`tasks`, strict order): the single-op turn lists the planner row and its one step, the multi-step turn lists its read round and each step of the card.
