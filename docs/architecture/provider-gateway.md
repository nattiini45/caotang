# Provider gateway — BYOK model access spec (v1)

> Status: built. Scope: everything between the agent harness / editor and the provider's HTTP endpoint. The harness's tool-surface decisions live in [agent-harness.md](agent-harness.md); this file owns the *transport, config, accounting, and the mock contract*.

## 1. Responsibility & ownership

- **Owns:** provider profiles (kind/preset/URL/key/model), the adapter registry, HTTP client, streaming, retries/backoff, abort, token accounting, request/response log, mock provider, and the optional trace observer (§3.1).
- **Never:** sees tool names' meaning, binder state, or prompts' meaning. It transports messages; the harness owns prompt assembly. It is the *only* module that makes network calls (ARCHITECTURE §2.6).

## 2. Profiles (data shape)

```ts
interface ProviderProfile {
  id: string;                 // generated, stable
  name: string;               // "Anthropic direct", "OpenRouter main"
  kind: 'endpoint' | 'mock';  // endpoint = speaks over HTTP; mock = the no-key fixture
  preset?: string;            // the preset it was created under; 'generic' = hand-rolled endpoint
  baseUrl: string;            // https://api.anthropic.com — stored WITHOUT trailing slash; the route path appended at call time
  apiKey: string;             // stored via §7, in the sealed payload — never on this record
  defaultModel: string;
  temperature?: number;       // no default; sent only when the caps allow it (§2 "Request parameters")
  maxOutputTokens?: number;   // default 4096; harness may override per call
  params?: RequestParams;     // the profile's own request parameters over the model row's (§2 "Request parameters")
  pricePer1k?: { prompt: number; completion: number };  // optional, USD; shown as an estimate, and read by a cost limit (agent-harness §7.1)
  isActive: boolean;          // exactly one profile active at a time
}
```

- **Multiple named profiles, one active.** Per-call model override is a parameter of `complete()` (harness chooses, e.g. cheap model for synopses), not a profile property.
- `settings` owns profile CRUD UI; the gateway owns validation. `baseUrl` is normalized on save and must be **https** — no other scheme and no loopback endpoints for provider profiles, except for the three local model presets below (local MCP servers are a different spec's concern).
- **Presets** (`packages/gateway/src/presets`): one row per shipped provider — its base URL, default/fast/vision models, auth header style, quirks, a per-model capability table (`ModelCaps`: native tools, images, JSON modes, thinking levels + how they map to wire fields, `thinkingShape` and `thinkingDisplay` for Messages routes, how reasoning replays) and a browser/CORS note. A preset may split models across adapters (`OpenCode`'s `claude-*` and two Qwen ids run on the Messages route, everything else on Chat). `keyOptional` is true only for `generic`, `opencode` and the three local servers — everywhere else a key is required. The live `/models` answer decides which model ids exist; the table supplies what a listing does not say.
- **Window and output cap.** A row may state `contextWindow` (the provider's documented window, in tokens) and `maxOutputTokens`. `modelLimits` takes the window from the live listing first and the row second; the model picker prints the row's. The output cap is informational — the profile's cap is what a request sends. `modelLimits` reports it as `modelMaxOutputTokens` (the listing first, the row second) beside the `maxOutputTokens` a request is sent with. The harness may raise one request's cap toward it: the planner's retry after a reply the provider cut at its output limit asks for twice the cap, never above `modelMaxOutputTokens`, and never when the model advertises none (agent-harness §2). The Claude rows state 1,000,000 and 128,000 from Anthropic's model overview (read 2026-10-20), and only for the four exact ids it names: a Claude id not on the page has no row and no window. Anthropic's `GET /v1/models` reports the window as `max_input_tokens` and the cap as `max_tokens`, each nullable; the Messages adapter reads both under the shared rule that a null, zero or absent number is not stated.
- A `generic` profile is the hand-rolled escape hatch: custom https base URL, optional sealed headers, OpenAI-Chat route.
- **First-party hosts are pinned to their native route.** A profile whose base URL host is `api.openai.com` resolves to the `openai` preset (`openai-responses`, its `store:false` + stateless quirks and its model rows), and one at `api.anthropic.com` to the `anthropic` preset (`anthropic-messages`), whatever preset the profile names: `generic`, another preset, an unknown id or none. The host is read from the parsed URL, so case, a missing `/v1` and a trailing slash do not matter; every other host keeps its preset's route, and a profile with no known preset still falls back to OpenAI-Chat with empty caps. Why: GPT-6 models (`gpt-6-sol`, `gpt-6-luna`, `gpt-6-astra`, `gpt-6.1-sol`, `gpt-5.6-sol`) answer Chat Completions with 400 "Function tools with reasoning_effort are not supported … use /v1/responses" while Responses works on every model (checked against the live API 2026-11-07), and Anthropic's OpenAI-compatible chat endpoint is a compatibility layer beside Messages. There is no wire-format picker in settings, so nothing in the UI can override the pin. The pin is the effective preset everywhere a preset answers: `resolveRoute` picks the adapter and caps, `listModels`' static catalogue, `modelLimits`' row fallbacks (window, advertised output cap, price) and `modelCaps` all resolve the same pinned row, so a profile pointed at `api.openai.com` never reports another provider's table.
- **Request parameters** (`ModelCaps`, `ProviderProfile.params`). There is no sampling default: a request carries `temperature` only when the request or the profile sets one and the caps do not deny it (`denylist`). A caller that asks for temperature 0 on purpose (encoding review, picture transcription, the coherence review) gets it on a model that takes one and silently goes without it where the row denies it. A model row says what the model takes: the fields it rejects (`denylist`), the `strict` flag its function tools need (`toolStrict`; absent sends no flag) and the wire value of each thinking level (`effortWire`, over the style's default mapping). A profile's `params` lay its own choices over the row, field by field, in `withParams` (`presets/registry.ts`), which `resolveRoute` applies, so the body, `modelCaps` (the levels Task roles offers) and `modelLimits` all see the same caps:
  - `temperature: true` takes `temperature` off the denylist the model row wrote (a request's or the profile's value is then sent even on a row that takes none), `false` puts it on; absent follows the row. The profile's own `deny` wins over the flag: `deny: ['temperature']` keeps it denied even with `temperature: true`, while the flag alone still lifts a model row's default denial — an explicit refusal cannot be overridden by the same profile's allow. On its own (no stored temperature) the flag is a valid shape an SDK write can produce: it lets a request that asks for a temperature send one where the row takes none.
  - `toolStrict` sets the flag on every function tool, on all three routes; absent follows the row.
  - `effort` is the levels the profile offers, each with its wire value (`{low: 'low', max: 'xhigh'}`); an empty map offers none and sends no thinking field. A row without an effort style takes the route's own (`reasoning_effort` on Chat, `reasoning.effort` on Responses, Messages' `output_config.effort`).
  - `deny` adds field names to the row's denylist — a compatibility list for an endpoint that refuses a field, not arbitrary request-body deletion. Only the optional fields the adapter would write can be left out: what a request needs (the model, the messages or input, the stream and its output cap) always goes out, and a denied `max_tokens` is not removed but sent under the route's other name, `max_completion_tokens`. A denied name does suppress every generated field of that name on every effort style — `reasoning_effort`, `reasoning.effort`, `thinking.type`, `thinking.type+effort`, `enable_thinking+budget`, `reasoning.enabled`, and Messages' `thinking`/`output_config` — so `deny: ['output_config']` sends no effort at all; `modelCaps` reports the remaining levels accordingly.
  - The store checks them: `params` itself must be an object — an array or any other container is refused `invalid/params` on create and update alike (a refused update keeps the stored rules) — booleans stay booleans, thinking levels are the keys, and short identifiers (`[A-Za-z0-9_.-]{1,40}`) are the wire values and field names, at most 24 of them. `ProfilePatch.params: null` clears them, as `temperature: null` clears the temperature.
  - Settings › Providers shows them in the profile form's **Advanced request parameters** disclosure: Temperature (follow the model, send a value from 0 to 2, send a request's value, never send), Strict tool schemas (follow, on, off), Thinking levels (follow, send none, choose the value sent per level, seeded from what the model sends) and Leave out these request fields. **Send a request's value** stores the flag `temperature: true` with no number: a temperature a request asks for goes out even on a model that takes none, and the valid SDK flag-only shape reads as this mode — an unrelated edit writes the same shape back, so it never blocks a save. A temperature saved before these controls existed (or written by the SDK with no flag) shows **send a value** without the flag: it keeps meaning send-where-the-model-takes-one — on a row that takes none, the same "takes no temperature" note follow-mode shows says so — and an edit that leaves the control alone writes the same shape back; `temperature: true` plus a number is stored only when **send a value** is picked or the shown value is changed. While a field follows the model the form says what the row sends ("gpt-6.1-sol takes no temperature, so none is sent.", "Sent as: Low → low, …, Max → max"; DeepSeek's "Off → thinking disabled"), and when the profile's own leave-out list is the thing suppressing a field — temperature, or the whole thinking control — the note says that instead. The "Sent as" line and the custom values' seed come from `effortWireValue` (effort.ts), the function the adapters write the body with.
  - The OpenAI rows, checked against the live API on 2026-11-07 with `max_output_tokens` 16: every row refuses `temperature` and `top_p` (400 "Unsupported parameter") except at effort `none`, so both are denied; tools go out with `strict: false`, because Responses treats an absent flag as `true` and makes every property required (a model then fills optional parameters, such as a zero-length selection); every level is sent as its own name and off as `none`. `gpt-6-sol` and `gpt-6-luna` take none, low, medium, high, xhigh and max; `gpt-6-astra` and `gpt-6.1-sol` the same without none; `gpt-5.5` none to xhigh without max. All accept `text.format: json_object`. Prices from OpenAI's list (Standard, read 2026-11-07): `gpt-6.1-sol` $2 / $10, `gpt-6-astra` $10 / $50, `gpt-6-luna` $0.10 / $0.50 per 1M tokens; `gpt-6-sol` and `gpt-5.5` are not on the list and stay unpriced.
  - The Anthropic rows, checked the same day: all four refuse `temperature` and `top_p`; each takes `output_config.effort` low, medium, high, xhigh and max with adaptive thinking; only `claude-haiku-5-5` takes `thinking: {type: 'disabled'}` (Sonnet 5.5 asks for `between_tools`, which the adapter does not send; Opus 5.5 and Fable 5.1 cannot turn thinking off). No tool `strict` flag is sent.
- **Local model servers** (`ollama`, `lmstudio`, `llamacpp`; the preset's `local` block, `cors: 'local'`). A server on this computer, on the OpenAI-Chat route. Their base URL goes through `normalizeLocalBaseUrl` instead of `normalizeBaseUrl`: `http` or `https` to `localhost`, an address in `127.0.0.0/8` (each octet range-checked) or `[::1]`, judged from the parsed hostname with no DNS lookup. A LAN address, a `*.local` or `*.localhost` name, a look-alike such as `127.evil.example` and a URL with userinfo are refused, and the message says why: plain http is allowed only to this computer, so a key or manuscript is never sent unencrypted over a network. `normalizeBaseUrl`, the generic kind and every other preset stay https only. The gateway and the MCP client share one loopback predicate (`src/loopback.ts`); the MCP client also accepts `*.localhost` names, the local presets do not.
  - Defaults are `http://127.0.0.1:11434/v1` (Ollama), `http://127.0.0.1:1234/v1` (LM Studio) and `http://127.0.0.1:8080/v1` (llama-server), written as `127.0.0.1` so a hosts-file or IPv6 mapping cannot redirect them. The writer may edit the port or host within loopback. The egress pin compares the request origin with the profile's origin as for any endpoint.
  - The key is optional and sent only if the writer set one on that profile (LM Studio's token, `llama-server --api-key`); it is sealed like any key and never reused for another profile.
  - Capabilities are conservative, because they depend on the model the writer pulled: no native tools and no images, so the agent speaks the JSON-in-text wire, and a `*` row with a 4,096-token window, used only when the server's own `/models` listing reports none (assembly warns before it overruns instead of the server truncating silently). The profile's `maxOutputTokens` stays the writer's override.
  - Profiles and base URLs of local servers are a settings-UI change only: the agent and MCP have no command that creates or alters a profile or its base URL.
  - Not built: reading each server's own model details (Ollama's show, LM Studio's REST API, llama-server's props) to fill tools, vision and the window; Ollama's Messages route; servers on a LAN; local-to-cloud fallback chains (which must word the fallback as sending the text to the cloud provider).

## 3. Wire adapters

`Gateway.complete(request, signal?, beforeSend?)` accepts an optional synchronous caller admission check outside the serializable request. The gateway/transport invokes it after asynchronous credential resolution and immediately before counting and dispatching each attempt, including retries after backoff; mock requests check it before counting too. A thrown refusal propagates unchanged and makes no new fetch or ledger attempt. The callback never enters a provider body, trace request, project file or export. Gateway decorators must forward it.

Three wire formats ship, one adapter each, behind `ProviderAdapter` (`src/adapters/`). The gateway resolves a profile+model to `{adapter, ctx}` — the pinned first-party route for `api.openai.com` and `api.anthropic.com` (§2), else the preset's route, or the generic Chat route — and the adapter owns everything route-specific:

```ts
interface ProviderAdapter {
  completePath(model): string;                       // '/chat/completions' | '/responses' | '/messages'
  modelsPath(ctx): string | null;                    // null = no listing route; the capability table answers instead
  headers(ctx, secrets, purpose): Record<string,string>;  // auth + protocol headers; transport adds accept/content-type
  buildBody({req, ctx, temperature, effective, jsonObject, cache?}): Record<string, unknown>;  // cache: §3 "Prompt caching"
  createStreamParser(ctx): StreamParser;             // per-call SSE dialect reader
  parseModels(json): ModelInfo[] | undefined;
}
```

- **openai-chat** — `{model, messages, max_tokens|max_completion_tokens, stream, stream_options}`; nested `function` tools; `reasoning_content`-style thinking deltas; `[DONE]` ends the stream.
- **openai-responses** — `{model, input items, instructions, max_output_tokens, stream}`; flat `function` tools; `function_call_output` items answer calls; reasoning items replay verbatim (encrypted content included, on routes that emit it). Shipped routes are *stateless*: `store: false` where documented (OpenAI, xAI) makes `previous_response_id` unusable, so full history is resent.
- **anthropic-messages** — `{model, messages, system, max_tokens, stream}`; `system` lifted out of the array; `tool_use`/`tool_result` blocks; signed `thinking` blocks replayed verbatim; named SSE events (`message_start`, `content_block_*`, `message_delta`, `message_stop`), with `error` events raised as provider failures post-200. `anthropic-version` is always sent; `anthropic-dangerous-direct-browser-access` is sent only by presets that opt in with the `browserAccess` quirk — Anthropic's own host rejects browser calls without it, and no other shipped host has been observed to require it on this route. The opt-in is keyed to the preset while the enforcing host is the profile's own `baseUrl`; the host pin (§2) gives any profile at `api.anthropic.com` the `anthropic` preset's quirks, so the header always reaches Anthropic's own host.

- **Normalized model** (`types.ts`): `ChatMessage` carries `toolCalls`/`toolCallId`/`isError`/`reasoning` alongside `content`; `ChatRequest` carries `tools`, `toolChoice`, `thinking` and `role`; `ChatChunk` carries `reasoningDelta`, terminal `toolCalls`/`reasoning`, and `finishReason` gains `'tool_calls'`. `ReasoningBlock.raw` is opaque — stored and replayed by the adapter, never interpreted above the seam.
- **Thinking:** `thinking: 'off'|'low'|'medium'|'high'|'xhigh'|'max'` is mapped through the model's capability row (`effortStyle`, seven wire mappings in `adapters/effort.ts`). A level the row does not list is never sent — the UI only offers listed levels, the mapper is the second line. A row's `effortWire` names the value each level is sent as (the OpenAI rows send `xhigh` and `max` as themselves); without it `xhigh` and `max` go out as `high` on the `reasoning_effort` family and `off` as `none`. Every row whose provider documents `xhigh` or `max` names them (effort audit, 2026-11-07); rows still unverified carry a TODO and keep the default. On `thinking.type` an on-level is `enabled` unless `effortWire` names another (MiniMax M3: `adaptive`), never guessed from the level count; `thinking.type+effort` sends `thinking: {type: 'disabled'}` and no effort for off (DeepSeek, Hunyuan, Z.ai GLM 5.2+). On an effort route that takes no budget (and an adaptive Messages row) a call that thinks, at a level or at the provider's default, has its output cap lifted to 16,384 (never above the row's `maxOutputTokens`) when neither the profile nor the request set one, since the reasoning shares `max_tokens` with the answer. On a Messages route the row's `thinkingShape` says what is sent: `adaptive` (every Claude 5 row) writes `thinking: {type: 'adaptive', display: 'summarized'}` and `output_config.effort` and never `budget_tokens` (the old shape is a 400 there); `budget` (a Messages row that says nothing) writes `thinking: {type: 'enabled', budget_tokens}`. Thinking on drops `temperature` in either shape.
- **Effective output:** `chatSpec` settles the cap once per call (`effectiveOutput`) and every adapter sends that result. On a route whose thinking is a token budget (Messages `budget`, `enable_thinking+budget`), `max_tokens` is raised to the budget plus the profile's own cap, held to the row's documented output maximum; when that clamp would leave the budget at or above `max_tokens`, the budget is lowered (never below 1,024), and if even that does not fit thinking is left off, so no request is sent that the provider would reject. `ChatRequest.reasoningBudget` is the per-call budget: a number on the budget styles, and elsewhere the nearest listed level by a fixed table (`levelForBudget`); it is ignored beside `off`. The request log line records the cap that was sent, and Settings shows it in a "Max tokens" column (the format probe records its own 16). `modelLimits(profile, model, thinking, request?)` settles the same cap `chatSpec` would transmit and reports the excess over the base cap as `thinkingTokens` — the lift implicit thinking earns included, absent when the sent cap is the base cap. A caller that prices or reserves one specific call passes that call's `maxOutputTokens`/`reasoningBudget` and its `role` in `request`, so the excess is the one the call's transmitted cap carries on the route it is sent through: a `role` with no named profile resolves through the same §6 router `complete` uses (`roleRoute`), whose profile, model and thinking level stand in for the ones the call leaves unset, so a role-routed call is settled on the role's profile and never the active one's. The excess follows the route: a smaller request cap on a budget route keeps the same budget delta, a request cap on an effort route is sent as-is with no lift, and a `reasoningBudget` raises the cap exactly as the body does — so a run-limit reservation and a cost estimate price what is sent, not a nominal share that can exceed the transmitted cap.
- **Message parts** (`parts.ts`, [pictures.md](pictures.md) §7): `ChatMessage.content` is a string or an array of `{type: 'text'}` and `{type: 'image'}` parts. A string is sent exactly as it always was on every route; only an array maps onto a route's blocks: Chat `image_url` with a data URL, Responses `input_image` with a data URL, Messages a `base64` source with the part's `media_type`. An image part carries its bytes, a sha-256 `hash`, a `size` and a `mime` of PNG, JPEG, GIF or WebP, and may carry a caption.
  - **Refused before anything is sent**, with words for the writer or the model and never the bytes: a part of an unknown type, an image with no bytes, a `mime` outside the four, a `size` or `hash` that does not describe the bytes, bytes whose magic number is not the declared `mime`, an image on any message that is not the user's, content that is neither a string nor an array, and a request over its route's limits. The adapters refuse the same way when a body is built (`EgressDeniedError`).
  - **Limits per route**, the gateway's own and conservative, not a provider claim: Chat and Responses 20 images, 20 MiB an image, 64 MiB a request; Messages 20 images, 5 MiB an image, 32 MiB a request; a route-agnostic call (the mock, an estimate) takes the Messages row.
  - **The vision gate:** a request with an image is refused unless the model's capability row says `vision`, ahead of the egress check's key reveal: nothing is sent, no key is opened, nothing is logged or counted, and the refusal names the model and says to choose a vision-capable model in Settings or send a caption or transcription instead. A request with no image is never gated. A mock profile's row is the mock's (`capsVision`).
  - **Bytes are transient.** They ride the wire and nowhere else. The request log holds no body, the ledger no content, and an error, a preview, a summary or a log line shows an image only as its placeholder (`[image 1: image/png, 812 KB, sha256:ab12cd34…]`) or as its `hash`, `size`, `mime` and the image count. Each image's base64 form joins the call's redaction list, so a provider that echoes the body in an error has the image scrubbed like a key.
  - **Estimates, not claims:** text parts count as text; an image counts by its route's formula, `ceil(w × h / 750)` on Messages and `85 + 170 × ceil(w/512) × ceil(h/512)` on Chat and Responses, from the dimensions in its header. A route-agnostic estimate (a run limit's reservation, the plan card) takes the larger of the two, so it never undercounts on either route; an image whose header does not parse counts `ceil(size / 64)`. The base64 form is never counted as text. The provider's own `usage` replaces the estimate when it reports one.
- **SSE:** the parser yields `{event, data}` pairs (Anthropic and Responses name their events); `[DONE]`/termination is adapter-declared, not a transport rule.
- **Prompt caching** (issue #86). A `ChatMessage` may carry ordered `parts` (`{text, cacheBoundary?}`) beside `content`, which stays the parts joined with a blank line and is what an adapter that does not cache sends; a part marked `cacheBoundary` ends a prefix worth caching (context assembly marks the end of its stable layers, context-assembly §2). Whether a call caches is settled in `chatSpec`: the request's `cache` policy, else the profile's `promptCache` (`{mode: 'off' | 'auto', ttl?: '5m' | '1h'}`, saved per profile in Settings › Providers, absent = on), against the model row's `cache` field (`explicit` | `automatic` | `none`; absent = `none`). The adapter is handed a `CacheSettings` (style, lifetime, the row's `cacheMinTokens`, and a routing key) only when the policy is on and the row caches; otherwise it gets nothing and the body is byte-for-byte what it was before caching existed, so a generic endpoint and every provider whose caching the table does not state are unaffected. Each block breakpoint is sent only when the prefix it closes reaches the row's minimum (estimated by the gateway's `ceil(chars/4)` rule); Anthropic's top-level breakpoint is always sent once the profile and the row cache.
  - *anthropic-messages, `explicit` rows (the Claude 5.x rows):* `system` goes as one text block; `cache_control` marks the last tool, that system block, and the boundary part of the first user message that has one (sent as text blocks, one per part); a top-level `cache_control` lets Anthropic move the fourth breakpoint along the growing thread. Four at most, the documented limit, and all carry the profile's lifetime (`{type: 'ephemeral'}`, or `ttl: '1h'`), since mixed lifetimes must run longest first. The schema hint keeps its place as the leading user message.
  - *openai-responses, `explicit` rows (GPT-5.6 and later):* `instructions` takes no breakpoint, so the system text becomes a `developer` message of `input_text` parts with `prompt_cache_breakpoint: {mode: 'explicit'}` on its last part, the schema hint a second developer message after it, and the boundary part of the first user message carries a breakpoint too. Implicit caching is left on (no `prompt_cache_options` is sent), so the growing thread is cached as well; the lifetime is the provider's 30-minute default.
  - *openai-responses, `automatic` rows (models before GPT-5.6):* the schema hint moves after the system text in `instructions`, so a structured call and a plain one of the same kind share their prefix, and `prompt_cache_key` is `caotang-<FNV-1a 64 of the profile id and the call's system text>`: stable per kind of call, and never a project name. `prompt_cache_retention` is never sent (no opt-in to 24-hour retention).
  - *openai-chat:* no field is sent; a provider that caches by itself (DeepSeek and others) benefits from the stable prefix alone.
  - *Usage* (issue #78, step 2, carried here): `Usage.promptTokens` is every input token billed, cache reads and writes included, and `cachedPromptTokens`, `cacheWritePromptTokens` and `reasoningTokens` are subsets, present only when the provider reports them. Anthropic's `input_tokens` counts only what follows the last breakpoint, so the adapter adds `cache_read_input_tokens` and `cache_creation_input_tokens` back (from `message_start`, or a final `message_delta` that restates them); OpenAI reads `prompt_tokens_details` / `input_tokens_details` (`cached_tokens`, `cache_write_tokens`) and `completion_tokens_details` / `output_tokens_details` (`reasoning_tokens`); DeepSeek's `prompt_cache_hit_tokens` is its cached count. A figure that is not a count, or exceeds its total, is dropped.
  - *Forecast terms:* `modelLimits` carries `cache: {readMultiplier, writeMultiplier?, minTokens?}` when the profile caches and the row names a read multiplier (`cacheReadMultiplier`, `cacheWriteMultiplier`); Anthropic's one-hour lifetime writes at 2×. Context assembly prices a reused prefix with it (context-assembly §5).

### 3.1 Trace observer

`GatewayOptions.observe` (and `Gateway.setObserver`, which attaches or detaches it between calls) is told each provider call's lifecycle: `request` (after role routing, so the resolved profile, model and thinking level are known), `first-token`, `attempt` (each try, with its request-log outcome, so a retry is visible) and `response` (finish reason, the reply, the reasoning text, tool calls and replay blocks, usage, whether that usage is the provider's or the `ceil(chars/4)` estimate, and how many attempts it took). A mock profile emits the same events. `ChatRequest.callIndex` is attribution only, like `turnId`: it joins an event to the harness's records of the same call and changes nothing on the wire. A call that fails, or whose caller stops reading, still ends in a `response` carrying the error.

The observer is the one place a body leaves the gateway, so it has rules. Every string of an event passes `redact` with the call's own secrets (the key, and a generic profile's sealed header values) before the observer sees it, and an event carries no header. Every observer call is made inside a `try`, its type returns `void`, and a throw is swallowed: a call behaves the same with any observer, and with none it gathers nothing. Its one consumer is the in-tab agent trace (agent-harness §5.2), which keeps it in memory.

## 4. Retries, errors, timeouts (contract, not vibes)

### Shared completion queue

One gateway instance owns a foreground-first queue per resolved profile id, shared by `complete` and `completeOnce`. A profile's app-local `maxConcurrentRequests` is an integer from 1 to 8; absence on an older profile follows its kind's default: 3 for an endpoint, 8 for the demo/mock. Settings → Providers exposes **Requests at once** on both kinds. This metadata never enters a project, bundle, export or provider payload. It limits overlapping calls; it does not start fan-out work.

A slot belongs to one completion call until its iterator finishes, fails, is abandoned or is cancelled, including that call's existing retry/backoff policy. Running calls are never preempted. Waiting calls with role `background` have lower priority than all other calls; each priority is FIFO. A committed limit change on the built-in profile store immediately schedules waiting calls against the new cap without interrupting admitted calls or bypassing a shared pause. Its optional `subscribeLimits` hook is additive for injected stores: it reports only successful changed-limit updates, listener failures cannot reject a committed update, and legacy stores without the hook are still read at each scheduling entry. The gateway subscription has the lifetime of its profile-store/gateway pair. The resolved profile id stays fixed while queued; after admission the gateway re-reads the profile and role allow-list before building the route or revealing credentials, so removal or a revoked role cannot dispatch a queued call under stale metadata.

An aborted queued call is removed without a transport attempt, key reveal, request-log entry or ledger row; it resolves with the normal cancelled terminal error chunk and zero usage. Returning or throwing into a completion iterator aborts its internal signal immediately, combined with the caller's signal, rather than waiting for a pending admission or transport read to finish. A cancellation while admitted credentials are being read is checked again before dispatch and creates no attempt or usage row. Tracing distinguishes iterator return from explicit caller abort and registers any revealed scrub values before a cancelled no-send exit. Queue time precedes the admitted call's transport timeout. Each admitted call retains the existing retry/timeout and partial-stream rules below, and releases its slot on every exit path. Model-list and save-time capability probes retain their existing separate validation path.

Every completion HTTP 429 pauses admission for that profile until its `Retry-After` delay, or the same backoff delay selected by the call's retry policy when no readable header exists. The pause starts when the status and headers arrive, before reading an error excerpt; cancelling that read does not remove the pause. Concurrent pauses extend the deadline to the latest one, never shorten it, including a final exhausted attempt. Other profiles remain independent. Already admitted calls keep their slots and their existing retries; the pause gates new admissions rather than cancelling running work. A foreground request still goes ahead of queued Background calls when admission resumes. Queued cancellation clears its listener/timer work, while attempt counts and usage continue to describe actual sends only.

| Failure | Behavior | Error surfaced to harness |
|---|---|---|
| Network error / timeout | Retry up to **2** retries, exponential backoff 1s → 4s, jitter ±20%. **Stream started = no retry** (partial output already delivered). | `ProviderError('network', detail)` |
| HTTP 401/403 | No retry. | `ProviderError('auth', 'Key rejected by <host>. Check the profile in Settings.')` |
| HTTP 404 on endpoint | No retry. | `ProviderError('endpoint', …)` |
| HTTP 429 | Honor `Retry-After` if present, else backoff; up to 2 retries. | `ProviderError('rate_limit', …)` after retries exhausted |
| HTTP 5xx | Retry per network rule. | `ProviderError('provider', status + body excerpt ≤ 300 chars)` |
| 200 but malformed SSE | Fail the stream once with raw excerpt. | `ProviderError('protocol', excerpt)` |
| Post-200 provider error event | Same as a status error. | `ProviderError('provider', excerpt)` |
| Context length exceeded | **Not retried, not truncated silently.** | `ProviderError('context_length', 'Prompt ≈ <N> tokens exceeds model window (<M>). …')` |

- Error text follows the finding: **written for the model/user to act on** (names the corrective surface — Settings, activity log), never a bare code.
- `ProviderError` keeps its seven kinds and existing message contract. Additive `reason` metadata distinguishes `timeout` and `model-list-unreadable` without parsing English text. An optional `providerReply` carries only the provider's bounded, redacted response excerpt (at most 300 characters), separate from generated gateway instructions and local diagnostics. For JSON errors it uses a string `error.message`, `error`, or `message` when present, otherwise the response excerpt; it never translates those values. HTTP errors, including 401/403, may supply it; network failures and timeouts do not invent a provider reply. This does not change retry policy or the persisted request-log/trace shape.
- Timeouts: connect 10s, first-token 30s, idle-between-chunks 60s, total request 5min (configurable in settings, defaults only). A preset may carry its own (`PresetDef.timeouts`, plumbed per call as `CallSpec.timeouts`, laid over the defaults and under the gateway's own settings). The local model servers use connect 180s, first-token 180s and idle 120s, because the server loads its model from disk before it answers and the browser's permission prompt waits inside the connect phase; the total stays 5min. Every other provider keeps the defaults.
- **Local model servers.** Browsers report a CORS refusal, a refused connection and a Local Network Access denial identically (a bare `TypeError`), so a failed call to one is told apart in the transport: Node and desktop shells name `ECONNREFUSED`; a permission error names itself; an opaque failure is checked with one bare no-cors GET (no headers, no body, no key) — if the server answers it, the browser blocked the real request on CORS; if not, the browser's `loopback-network` permission being `denied` makes it an access denial, and otherwise nothing is listening. Each becomes `ProviderError('network')` with the preset's own text — `OLLAMA_ORIGINS`, LM Studio's *Enable CORS*, llama-server's `--cors-origins`; "Nothing is listening on 127.0.0.1:11434. Is Ollama running?"; or a pointer to the browser's site settings — and is final (`permanent`: not retried). A 404 whose body names the model (a model not pulled) is a `provider` error with the server's words, not "no endpoint".
- **Egress pinning:** every request's URL must equal the origin of the *resolved* profile — checked in `assertEgress` before a socket opens, and before any key is decrypted, so a refused request never touches key material, and one profile's key can never ride to another profile's endpoint. A named profile is reachable whether or not it is the active one (task roles run on their own profiles).
- Every request/response (including retries) lands in the **local request log** (§6), capped at 50 entries per session, inspectable UI. It stores no request bodies, headers or keys (the trace observer of §3.1 does see bodies, and feeds only the in-tab trace, in memory), and every error detail, log note and quoted provider excerpt passes through `redact` (`src/redact.ts`): every secret in the call's `secrets` list (the key, plus a generic profile's custom header values) is replaced wherever it appears, and anything shaped like a bearer token or an `sk-` key is replaced too.

## 5. Structured output

### Profile verification and selection

Saving an endpoint checks its model list and then its response format using the profile's explicit id. Refreshing its model list also names that id. Neither check activates a profile or restores a previous selection: a following turn uses the writer's chosen profile even while other profiles are being checked. An explicit activation remains the writer's choice, including when checks finish out of order.

Saving an unknown or failed profile repeats the check even when its fields are unchanged, so editing and saving is a real retry after a temporary failure. A verified profile's unrelated edits keep their previous result and do not add a probe.

The non-secret `ProfileView.verification` is an additive field in the app database, separate from `isActive` and the response-format capability cache. Its machine is `provider.verification`: `unknown`, `checking { attempt }`, `verified { checkedAt }`, or `failed { checkedAt }`. Check starts synchronously; only that attempt can settle its result. `verified` means the model-list operation answered (the documented catalogue for a provider without a listing route), not that inference, credentials or every model has been tested. Format failure keeps the existing JSON-in-prompt fallback without turning a successful listing into a failure. There is no new inference request or activation gate.

Only settled verification metadata is persisted. Older records without the field, malformed metadata and interrupted checks read as `unknown`, even when a response-format cache exists. The metadata contains no response body, error detail, key, URL or prompt. Endpoint, default-model, key or custom-header changes invalidate verification and cached format support; unrelated edits preserve them. Save-time format results from a superseded check cannot repopulate the cache. Profile removal never resurrects a result.

Settings publishes each endpoint row's verification kind as `data-state` (`demo` for the built-in fixture). Unknown, checking and failed endpoints show **Not verified**, checking adds a polite **Checking this profile…** announcement, and a failed row says to edit and save it to check again. A failed result and its mark survive reload. Model-list refresh persists its new result. These states do not change role resolution, request/run log formats, profile ids, the key vault or project/bundle formats.

The Providers section publishes `data-panel-state="working"` until its current operation and queued save settle, then `idle`. Reload and visual tests wait for this durability boundary as well as the profile's check result, rather than treating an enabled button as a storage signal.

Save feedback is one complete localized sentence per typed cause: a rejected key, absent model list, unreachable provider, timeout, unreadable browser model route, rate limit, provider refusal or unknown check failure. It names the saved profile once and never concatenates a second saved-profile template or tells a writer already in Settings to open Settings. Any provider-supplied excerpt appears separately under **Provider reply:** in its original language, with bidirectional isolation. The transient additive `SaveOutcome.probeFailure` carries the cause and optional reply; the existing `probeError` string remains compatible for non-UI callers. Neither cause details nor provider replies enter persisted profile verification metadata.

Existing actionable local-server CORS/permission guidance is retained separately as **Connection guidance:**, never mislabelled as a provider reply. Its existing gateway/preset wording stays unchanged pending the wider gateway localization follow-up (#596).

- Harness needs JSON for plans and verify steps. Contract: `responseFormat: {jsonSchemaHint}` → the adapter states it (a system message on Chat, `instructions` on Responses, a leading user message on Messages) and JSON mode is added **only** where the model's capability row allows it: `response_format: {type:'json_object'}` on Chat, where for preset profiles the row answers and for a generic profile a one-shot probe call at save time answers, cached on the profile; `text: {format: {type: 'json_object'}}` on Responses where the row says `jsonObject` (every OpenAI row), with no probe request (the probe answers from the row, so the profile list says "Structured output accepted"); nothing on Messages, which has no such mode.
- Response side: harness owns parsing/validation (gateway stays dumb). Non-JSON return is a harness-side error with the raw text attached — gateway does not retry on content, only transport.
- **Native tools:** when the model's capability row says `tools`, the harness sends `ToolDef[]` natively (authoritative); otherwise the JSON-in-text protocol remains the fallback. Tool results come back as `role: 'tool'` messages keyed by call id; refusals and ask-backs keep travelling as user messages. Tool names are wire-safe on every route (issue #486): the registry's dotted names (`doc.read`) are refused by Anthropic (`^[a-zA-Z0-9_-]{1,128}$`) and OpenAI/Gemini (`^[a-zA-Z0-9_-]{1,64}$`), so the gateway, above the adapter seam (`tool-names.ts`), renames each request's declared tools and replayed tool calls to a per-request, collision-checked form (`.` → `__`, any other illegal character → `_`, at most 64 characters, an already-safe name unchanged) and renames the tool calls the stream assembles back, so callers above the gateway only ever see registry names. A wire name the codec never issued comes back unchanged.

## 6. Token accounting

- The gateway records one terminal `Usage` per call, not one per streamed chunk, into **calendar-day and turn rows**. Both carry `version: 1`, profile, model, role, billed input/output tokens, request count, cache-read/write and reasoning subsets, `estimatedRequests`, `unpricedRequests`, `providerCostRequests` and optional `costUsd`. Turn rows also carry `turnId`, optional `sessionId` and optional `agentPath`. The row key includes every attribution field; a day row has no turn, session or agent path. `turnRowsOf`, `turnTotals` and `sessionTotals` return copies or sums without repricing them.
- **Price at call time.** The call captures the same price chain `modelLimits` uses: profile, then the last provider listing, then the preset model row. A valid provider-reported USD cost (including zero, currently OpenRouter's Chat `usage.cost`) wins. Otherwise cost is the uncached input at the prompt rate, cache reads/writes at their route rates (ordinary prompt rate where unknown), and output including reasoning at the completion rate, divided by 1,000. The request's cache lifetime sets the write premium. Editing a price later does not change recorded cost. No known price means absent cost, not free usage. A sum can be partially priced: `unpricedRequests` names the missing calls. Retried attempts count as requests, but only the final attempt's available usage is priced; earlier attempts stay unpriced.
- **Reported and estimated counts.** `Usage.source` is optional (`provider` when absent, for compatibility) or `estimate`; `providerCostUsd` is an optional validated wire figure. The transport's missing-usage fallback, including a failure before output, uses the prompt estimate plus the visible and reasoning output delivered so far and increments `estimatedRequests`. It estimates completion tokens from the combined character count, with reasoning as a subset, including reasoning-only output on cancellation, failure or abandonment; it retains only the reasoning character count for this estimate. Reported usage remains authoritative. The mock's deterministic token counts are its provider contract, not a missing-usage fallback. OpenAI Chat and Responses cache/reasoning details are subsets of their two totals; Anthropic adds its separately reported cache reads and writes into input, with thinking already in output.
- **Durability.** The existing browser app DB's `usage` key stores `{version: 1, days, turns}`. Every call queues a save through the existing ordered save-channel pattern, and an explicit provider save waits behind earlier saves. All day and turn rows survive reload without the former 200-row eviction or an age limit (H3-L1). The reader migrates a bare day-row array and unversioned snapshots, preserves the original local day and role, and marks old counts unpriced instead of inventing a historical cost. Unsupported or malformed snapshots are refused atomically; the app reports the read failure and does not overwrite the unreadable ledger on subsequent saves. Rows contain accounting metadata only, never credentials, request/reply text or manuscript text. This ledger is distinct from the project's run log.
- **Review attribution.** An agent's `coherence.review` passes the parent `turnId` through the model port. A standalone Findings review uses one generated `review-…` accounting id across all of its extraction and judgment calls; a separate review gets a separate id. Each encoding-helper request gets its own `encoding-review-…` id under the Background role. `ChatRequest.usageTurnId` carries these standalone accounting ids; it fills the ledger's `turnId` only when no actual agent `turnId` exists. It does not create an agent turn in the trace: standalone calls remain in the existing Reviews group (agent-harness §5.2).
- **Session attribution and display.** A durable conversation keeps its accounting identity across project visits and reloads; only New session starts an empty session total. Its foreground roles, delegated calls, background tasks and nested coherence reviews carry the same accounting `ChatRequest.sessionId`. A fork's inherited turns retain their original accounting identity and are not charged again under the fork. The loop's optional `usageSessionId` supplies that grouping while `sessionId` keeps each role/task's existing turn-id namespace; absent, accounting uses the loop's session name. The panel shows the session's requests, input/output tokens and summed known cost, with a keyboard-accessible breakdown by profile, model and role. Counts include retries and calls that stopped or failed; restoring or rewinding work never refunds them. Standalone reviews outside the controller stay in device history, not its session total. Starting another session never deletes device history.
- **Recorded cost surfaces.** A completed turn displays `TurnReport.costUsd`, never all its tokens at the Chat profile's price. The report and session disclosures name estimated counts and unpriced requests; a partially priced sum is labelled partial, and absent cost is not zero. Settings shows daily recorded cost and an estimated-count marker in a fitting desktop table; optional cache-read/write and reasoning detail sits below each row. On narrow screens each row becomes a labelled record showing its model, role, requests, input/output tokens and cost without sideways scrolling. These subsets are not added again to input/output totals. Its local **Export usage (CSV)** downloads all daily rows with stable English headers, raw decimal USD/counts, accounting metadata only and the shared spreadsheet-formula guard on every cell. It includes estimated, unpriced and provider-cost request counts. The detail toggle is view state, not a saved setting. All displayed money uses `formatUsd` with the interface locale's `Intl.NumberFormat` USD currency, four decimals below one dollar and two above, and “about” wording; the provider's bill is authoritative.
- `role` is the task role (`chat` | `drafting` | `background`) the request ran under, so cost is visible per role. Activity log shows per-turn totals (harness) and settings shows per-day totals (gateway ledger). This is local-only accounting; Caotang sets no quota of its own, and the run limits a writer sets are enforced by the harness, not the gateway (D4 below, agent-harness §7.1).
- **Delegated agents** (agent-harness §2, "Delegate") are attributed beneath the turn. A `ChatRequest` and a `UsageAttribution` carry an optional `agentPath` (`<turn>/reader#1`), and the ledger's turn rows are keyed by it as well as by profile, model and role, so a turn's tokens can be split by the agent that made the request. A request carries the **parent turn's** `turnId`, so `turnTotals(turnId)` still sums the whole turn, children included. The day rows do not carry it. `agentPath` is display and ledger only; no gateway behaviour reads it, and it adds no network destination: an agent's requests go through the same profile, key and egress pin as the turn's own.
- **Background tasks** (agent-harness §2) stage under the `background` role, on the profile, model and thinking the role resolves to, with the task's id as the session name, so the ledger's rows for a task carry `role: background` and a turn id that names it, and the task's row in the panel shows their totals. Priority between the foreground and the background is cooperative: the task's runner makes one call at a time and waits before each while a foreground turn is busy. The gateway's per-profile limiter also ranks queued foreground calls ahead of queued Background calls (§4). A call already in flight is not preempted, so it still counts against a rate-limited key.

## 7. Key storage (v0.1 shape)

- Browser: keys in IndexedDB **outside** the project DB, encrypted at rest with AES-GCM via **non-extractable WebCrypto key**. Plaintext never enters `localStorage` and never syncs. **Threat model:** this protects against *casual* theft (dumped IndexedDB blobs, shared machines) — **not** against XSS in the app origin or a compromised device (origin JS can *use* the key while the app is open). No stronger primitive exists for a no-backend web app; the honest assumption is recorded here, and the desktop app on the roadmap upgrades to OS keychains. The MCP bearer-token vault (extensibility.md §3.6) reuses this exact store.
- The sealed payload is versioned: `{v: 2, apiKey, headers?}` carries a generic profile's sealed custom headers with the key; entries sealed before v2 (a bare key string) decode as `{apiKey}` unchanged.
- Never written to any file in the project artifact (project-format.md §2 forbids secrets there).
- Mock/dev: `MOCK` profile type needs no key.

## 8. Mock provider contract (test-critical)

The app's keyless provider also scripts the harness's structured Background compaction request, matched by role, schema hint and the fixed compaction system prefix. It returns four deterministic section strings, explicitly labelled as a demo rather than a factual account of the manuscript. It does not infer decisions or echo the supplied history into a scene. The gateway/harness prefix guard pins the two constants without introducing a gateway dependency on the harness; unrelated demo drafting requests keep their existing refusal.

The mock provider is a **deterministic, scriptable** implementation of `ProviderGateway` used by Vitest headless tests and Playwright runs (ARCHITECTURE §1.6).

```ts
interface MockScript {
  match: (req: ChatRequest) => boolean;    // picks the response for a request
  respond: (req: ChatRequest, callIndex?: number) => MockResponse | AsyncIterable<ChatChunk>;
}
// MockResponse adds toolCalls?: readonly ToolCall[] and reasoning?: string; finishReason covers 'tool_calls'.
```

- **Deterministic:** same script + same request = same response bytes. No clock, no randomness (temperature ignored). A `nativeCall(name, args)` script answers a `req.tools` request with a terminal `tool_calls` chunk carrying the call; the call's id is numbered by the request's position in the run, so replays stay byte-identical.
- **Scriptable:** `echo`, `toolJson` (canned JSON tool call), `stream(words)`, `fail(mode)`, `nativeCall` (native tool call + optional reasoning). `capsTools: true` reports `{ tools: true }` from `modelCaps`, so the harness's capability gate can be exercised without a provider.
- **Usage accounting:** fake token counts = `ceil(chars/4)` so ledger assertions work unchanged.
- **Streaming shape:** yields chunks with `await setImmediate` between them so consumers' async logic is exercised identically to real SSE.
- **Cassettes:** a cassette is recorded model answers for one golden task (agent-harness §9), replayed through the mock as one script (`replayScript`, `packages/harness/src/agent/cassette.ts`). It is line-delimited JSON: a `header` record (`format: "caotang.trace/1"`, task, preset, model, `recordedAt`, and `synthetic: true` for an answer a person wrote), then one `exchange` per request, holding the request as sent (messages, tools, response format; tool-call ids numbered `call_<n>` by position), its `key` and the response. The key is the sha256 of the canonical JSON of the messages, the tools and the response format; it leaves out the model, the temperature, the turn id, the task role and every other knob, so re-pinning a model id breaks no cassette. A request is answered with the first unused exchange of its key. A request with no match fails the turn with a protocol error and is noted in `misses`: the message names the first message that changed, the character where it differs with the recorded and the new text around it, or the tool or format that changed, and the command that records again. A cassette is data, never code: the loader checks a size cap, every record's shape (an unknown record kind or field is refused), that each exchange's key is the key of its request, and that nothing in it has the shape of a credential; the writer scrubs the keys it is given and the shape of a key, then reads its own output back through the loader. Replay goes through the same gateway, loop, bus and confirm cards as live output. This module is the minimal, self-contained form of what the trace record format (#76) and the shared request key and cassette scripts (#82) will own; when they land their key and format replace these and the names here are the ones to absorb.

## 9. CORS and the browser

The app calls providers straight from the page, so a preset's usefulness in the browser depends on its CORS answer. The registry records what the sweep found (`cors: 'ok'|'blocked'|'preflight-fails'|'unknown'|'local'` + a note); presets that cannot answer a browser request are shown disabled with the honest label *"Desktop app or hosted only"*. The sweep itself is `e2e/providers-cors.spec.ts` — a real Playwright page running a real preflight per preset — run on demand; see [providers-browser-cors.md](providers-browser-cors.md).

The flag speaks for the **chat route**, the POST the agent sends (the route the default model takes, so OpenCode's Claude ids are asked on `/messages`): a preset a page cannot chat with is `blocked` however readable its model list is, and a preset flagged `ok` whose chat route the browser cannot read fails the sweep. The **models route** (the GET Settings makes when a profile is saved) is asked too, and judged apart: a provider can answer both preflights and still leave its 401 for one route without `Access-Control-Allow-Origin`, which the page then cannot read. A preset whose chat route reads but whose model list does not stays `ok` and is reported, not failed (the sweep's `cors-models-route` annotation). When the app meets that case it says what is true: *the browser did not let this page read the model list from the host (a mistyped key can look the same), chat may still work* (`providerMessages.modelListUnreadable`), not "could not reach the host, check your connection and base URL". Today that is Anthropic: its `GET /v1/models` rejection of a bad key carries no allow-origin header, while `POST /v1/messages` rejects with one.

A local model server (`cors: 'local'`) is not swept: whether the browser may call it is a setting on that server, which the preset names (`local.corsFix`). The Settings picker lists them in their own group, **On this computer**, with a setup note and the vendor's documentation link per product, and shows "Your text stays on this computer" only while the profile's address is a loopback literal. Chrome and Edge ship Local Network Access: a public https page that fetches `http://127.0.0.1` asks permission once. The transport passes `targetAddressSpace: 'loopback'` to `fetch` where the browser takes it (feature-detected; elsewhere it is left out), and the form explains the prompt before the first request. Firefox and Safari are unverified, and the UI promises nothing for Safari. All of this is verified against stub servers that imitate each product's CORS default (`e2e/providers-cors.spec.ts`), not against the real products; see [providers-browser-cors.md §4](providers-browser-cors.md). A self-hosted build with a stricter `connect-src` must admit `http://127.0.0.1:*`; the built app's `connect-src *` needs no change.

**Desktop shell (planned, not built).** The desktop app on the roadmap (Electron on a pinned Chromium; decisions.md, epic #16) is constrained before it exists. Keys never cross into the webview: the OS keychain is held by the native side and the webview gets put, delete and a presence check, never a read; without a keychain the WebCrypto vault above stays, with a visible notice, never plaintext. Provider calls are then made natively and attach the key by profile id. That call is not a general fetcher: https only, to the configured profiles' origins and connected MCP URLs, and never loopback, so local models are unchanged. Whether a CORS-blocked preset streams through it is proven in a spike before the label above changes.
