## 1. Verdict (adopted)

**Minimal viable storyboard = corkboard variant over an additive `shot` node kind + metadata — confirmed.** One data model, two export recipes (shot fields are *exactly* the camera half of an AI-video prompt pack). No product to reject outright: the market is SaaS-collab (Boords, from $39/mo — its value is the cloud approval loop) or desktop-drawing (Storyboarder); Caotang's local-first, writer-centric variant is the unoccupied spot.

**First-landing scope (v0.1-of-track):** shot node kind + storyboard corkboard variant + shot-list CSV export + PDF contact sheet. **Parked:** animatic MP4 (derived, heavy — parked), NLE/EDL interchange (production-pipeline territory — parked), paper-photo round-trip (recorded, not built).

## 2. Data model

### 2.1 Node kind + tree placement

```ts
tree[].type: 'shot'              // new node type joining root|folder|document (additive; loaders tolerant)
tree[].kind: 'storyboard'        // container marker on the folder that holds shots (display hint for corkboard variant)
```

- **Hierarchy:** sequence → scene → shots, with **the script as the spine** (every production tool links shots to script scenes; Storyboarder makes an imported scene the storyboard unit). A `shot` node lives under a document node's implicit shot container OR under a sibling folder marked `kind: 'storyboard'` — **adopted: sibling folder** (keeps the three-tier UI model untouched: folders contain nodes; a scene document's children would violate it). Default flow: "Derive shots" creates `<Scene Title> — Shots` folder under the scene's parent, `type: 'folder'`, `kind: 'storyboard'`, shots as its children.
- **Where the derive offer sits:** the scene's own view offers *Derive shots from this scene* while no `<Scene Title> — Shots` folder exists beside it. An empty storyboard board offers *Derive shots from “<scene>”* only when exactly one screenplay scene beside it has no shots folder, and the board is not itself a scene's shots folder; the name in the button says which scene the request names, and the board's copy says the shots go in a new folder, `<Scene Title> — Shots`, not on that board (derive makes the folder; it does not fill the empty board). Both send the same request (`deriveIntentOf`) through the agent, and both are dropped once the scene has its folder, so derive never makes a second folder for one scene. Two offers for one request is kept on purpose: the scene view is where a writer chooses the scene, and the board offers only when that choice is already made.
- Shots are real tree nodes: reorder/reparent/status/label/keywords/synopsis work via the existing command set; no new binder commands.
- **`covers` back-link (the script↔shot sync point):** each shot carries optional references to the script elements it covers (see §3.2). There is **no live two-way sync** — nobody maintains two-way sync; reverse invalidation is the deterministic coverage check (§5), not automatic rewrites.

### 2.2 Shot record (per-kind metadata, additive manifest field)

```ts
interface ShotMeta {
  image?: string;              // asset id — file inside the project folder; never a path outside it (project-format §2 no-outside-scope rule extends to assets)
  imageAlt?: string;           // caption if the image is absent
  shotSize?: 'WS'|'FS'|'MFS'|'MS'|'MCU'|'CU'|'ECU'|'OTS'|'POV'|'INSERT';  // fixed v1 enum (Boords/StudioBinder set, extended with OTS/POV)
  cameraAngle?: 'eye'|'low'|'high'|'birds'|'worms'|'dutch'|'overhead';    // fixed v1 enum
  cameraMovement?: 'static'|'pan'|'tilt'|'dolly-in'|'dolly-out'|'truck'|'crane'|'handheld'|'zoom'|'rack-focus';  // fixed v1 enum
  lens?: string;               // free text ("35mm anamorphic") — free field, no enum
  action?: string;             // ≤ 1000 chars — what happens in-frame
  dialogue?: DialogueCoverage[];   // script-line references covered by this shot
  durationSec?: number;        // seconds, ≥ 0; the animatic substrate
  transition?: 'cut'|'dissolve'|'wipe'|'fade-in'|'fade-out'|'match-on-action';  // fixed v1 enum (outgoing transition)
  vendorRefs?: VideoShotRef[]; // the AI-video prompt-pack fields attach here — video-prompt-pack.md §4 (this field is RESERVED now, typed there)
}
interface DialogueCoverage { kind: 'fountain-element'; docId: string; anchor: TextAnchor; }   // edit-anchors.md §2 shape — the covered cue/dialogue/heading range
```

- **Contract rules (project-format §2 discipline):** unknown enum value on load → keep string, surface "unknown value" chip, never drop; unknown metadata fields → tolerated/dropped-with-notice per §6 unknown-tolerance; `image` dangling id → field dropped with load warning (same rule as codex `attachments`), at project open and only against a list of the project's pictures that can be trusted — the browser's copy or a folder's `assets/` listed without failure, a folder whose attach was refused still listed, and a folder file that differs from the browser's copy counted as present; `durationSec` missing → shot excluded from animatic computations and flagged by the coverage check.
- **Asset storage:** `assets/` joins the project-folder layout (sibling of `docs/`; flat, opaque-id filenames `a_XXXXXXXXXX.<ext>`, PNG/JPEG/WebP v1, PSD-later per Storyboarder's precedent). Manifest-referenced only (§2 `image`); loaders ignore unknown files so the directory is additive with no manifest schema change; zip deliverable includes it; `ToC.md`-style human map not needed (images carry alt text). Images are content files (severity tier: content), snapshotted by the artifact write path; **images never leave the project folder** (no media storage beyond the project).
- **shotNumber is derived, not stored** (Boords' auto frame numbers): rendered from sibling `order` at display/export time; renumbering is free on reorder. A user-facing "lock numbers" option is rejected — derivation is the point (Storyboarder renumbers on reorder).

## 3. Editor & panel integration

### 3.1 Corkboard variant (the storyboard view)

- A folder with `kind: 'storyboard'` renders the corkboard in **shot mode**: cards = children in sibling order, card body = **image thumbnail** (asset, `<img>` from local asset path) + shot-number chip + one spec row (`shotSize · angle · movement · durationSec s`, each closed-list value in the shot editor's words, §3.1), S/M/L zoom mapping like ui-modules §3 (S = number + thumbnail only; M = + spec row; L = + action text + status/label).
- **Gestures → commands** (ui-modules §3 doctrine): card reorder = `binder.move`; metadata edits = the selected card's Fields panel, saved by its Save shot control (the Inspector does not draw the shot fields); new shot card = `binder.create` (context menu; type `shot` inside a storyboard-kind folder). **The module adds three bus commands** (command-bus §9): `storyboard.create` makes the `<Scene Title> — Shots` folder, `shot.create` makes one shot card with its stored metadata, and `shot.setMeta` writes a whole stored shot value over the one it replaces. Each carries the fact its plan was made against (`storyboard.create`'s `scene`, `shot.setMeta`'s `expect`), and the apply refuses when that no longer holds, so an undo is the same command with the values swapped. Their guards belong to this module and run in the apply, which the store supplies through `ProjectCommandOptions.shots`. Zoom/asset-view state = view state.
- Card image slot: click → lightbox zoom (view state); drag-and-drop an image file onto a card → asset import (`project.importAsset` internal op, one undo group, writes `assets/` + sets `image`). **Paste-from-clipboard** supported (the Storyboarder PSD-handoff lesson at 1% of the weight).
- Empty state: "No shots — derive from the scene's script, or draw/import a frame." (the title of an editable board; the derive action is the one §2.1 places). A read-only board offers neither a derive nor a new frame, so its title is "No shots in this storyboard yet".
- **Card contents by size.** The number chip, the picture (or its alt text) and the warnings (the unknown-value badge and the notes) show at every size. The warnings stay at S because a value the load kept as unknown must be seen (§2.2). Beyond that:
  - **S** is the number and the picture only. Its footer (Earlier, Later, Fields) is hidden from sight but stays in the tab order, and it is drawn as soon as focus enters it.
  - **M** adds the title, **one** spec row, and the coverage line (`N lines covered`). The spec row is `shotSize · cameraAngle · cameraMovement · durationSec s`, with `lens · transition` after it when they are set, so the camera values are in one row, not two. The row prints the **labels** the shot editor shows (`SHOT_ENUM_LABELS`, looked up by `enumLabelOf`: `Medium close-up (MCU) · Bird’s-eye view · Dolly in · 4 s · 35mm · Dissolve`), the transition included, and a value the list does not have is printed as it is. One builder, `cardSpecRowOf`, makes the row for the board and the sheet; `specRowOf` is its first four parts, which the derive plan card also uses. The stored value is always the enum value. The shot list (§6) keeps the tokens.
  - **L** adds the action text, the node's status chip, and its label chip. The status and the label are resolved through the project vocabulary, as the corkboard card resolves them: a status the vocabulary lacks reads `Unknown status`, and a node with none reads `No status`.
  - **Deviation recorded:** the coverage line shows at M and L, although §3.1 names no coverage row. It is the one visible count of the §5 check, so it is kept at the sizes that show detail.

### 3.2 Shot fields and prompt (the selected card)

- Selecting a card opens its shot-fields block (§2.2), drawn in the board's Fields panel for that card, not in the Inspector. It holds the image picker (project asset list, and the file, drop or paste pictures), the enum dropdowns (fixed enums above), the action textarea, the script coverage (**pick text in the open script doc → anchor captured fresh**, the Finding-evidence-capture pattern, coherence.md §6.3 — never stored as raw offsets alone; the picked words are located in the stored body whatever its line endings, a passage found more than once is refused with its count, and the anchor's range is the stored body's), the durationSec number field and the transition picker. The fields are saved as one shot by its **Save shot** control, not by debounced autosave.
- The prompt section (video-prompt-pack.md §2) keeps the text typed for each target model while the shot stays open, so a switch of vendor and back loses none of it. A stored prompt that changes under the editor (an undo, or an agent's apply to this shot) replaces that vendor's unsaved text with the stored values, and the section says so.
- Image editor = **none in v1** (crop/sketch = parked; Storyboarder's Shot Generator is a product-scale feature). Import-only posture.

## 5. Coherence: deterministic coverage check (v0.2-of-track candidate)

- **`script.shot-coverage`** (rides coherence.md §5.4's closed-registry rule — adding a check is a spec change + fixtures): (a) every cue/dialogue element covered by ≥1 shot's `dialogue[]` anchor → else info finding naming the element; (b) every shot has a `durationSec` → else info; (c) `dialogue[]` anchors that no longer resolve (drift) → info "re-anchor" (anchors re-resolve via the ladder only at *fix time*; the check just reports — edit-anchors §3 posture). Zero model calls; findings into the standard inbox; dismissal lifecycle standard (coherence.md §6).
- **Cross-medium consistency** (script ↔ storyboard ↔ branches) activates here per coherence.md §11 — this check is its first concrete instance.

## 6. Export (two recipes at the exporter seam)

- **`ShotListCsvRenderer`** (v0.1-of-track): columns = shotNumber, image filename, shotSize, cameraAngle, cameraMovement, lens, action, dialogue (rendered as `DOC:cue` refs), durationSec, transition (StudioBinder's column set is the convention). UTF-8 CSV, one row per shot in binder order; The XLSX variant (`shot-list-xlsx`) is built: the same rows (`shotListRows`), one sheet, numbers as number cells (§8 A4).
- **`ContactSheetPdfRenderer`** (v0.1-of-track): per-shot card grid — image, number chip, spec row, action line — paginated A4/Letter (Storyboarder/Boords precedent); title header from template variables. Same lazy-load + acceptance-gate pattern as screenplay.md §5.3's PdfRenderer (shared pagination pass where layouts permit; separate emitters).
  - **Built** as the exporter's `contact-sheet-pdf` format. The page plan is `@caotang/storyboard`'s (`planContactSheet`, `paginate`): three columns of 16:9 cards, 15 to an A4 page and 12 to a Letter page, in binder order, numbered 1 to n as the shot list numbers them. A card is the picture, the number chip on it, one spec row (the board's M row: `shotSize · cameraAngle · cameraMovement · durationSec s`, then `lens · transition` when set, in the editor's words) on up to two lines, and two lines of action, each cut with an ellipsis. The second spec line is paid for inside the card (a 7 pt spec font, 8.5 pt leading and a 3 pt gap), so a card is 136.62 pt tall and the A4 page still holds five rows. The header is `{project} — {storyboard} — {date}` with `Page n of N` on the right; `{storyboard}` is the storyboard the selection names, or the one every shot sits in, or "All shots". The paper is the recipe option `pageSize` (`A4`, the default, or `Letter`).
  - **Deviation recorded:** each page's header has a second line, the shot count, the animatic total and the shots left out of it for want of a duration (§2.2), the three numbers the board header shows. §6 names no such line; a printed sheet is read away from the board, so it carries them.
  - **The emitter** is `pdf-lib` (exact pin 1.17.1, MIT), dynamically imported in `packages/exporter/src/render-contact-sheet.ts`, so the editor bundle never loads it. Latin text is set in the PDF's built-in Helvetica, so a Latin-only sheet fetches and embeds no font. Its encoding is WinAnsi. Every other character cluster is set in the fallback font, Noto Sans Mono CJK SC Regular 2.004 (OFL-1.1), embedded through `@pdf-lib/fontkit` (exact pin 1.1.1, MIT, also dynamically imported) as a subset of the glyphs the file uses. It covers Han (simplified and traditional), kana, Hangul, Greek and Cyrillic; its Greek, Cyrillic and halfwidth forms are monospaced, the screenplay PDF's font (the two PDFs share one CJK file and one emoji file, [screenplay.md §5.3](screenplay.md)). The font lives in `vendor/noto-sans-cjk` (`@caotang/font-noto-cjk`): a TrueType WOFF built from the upstream OTF by a pinned script, with its source URL and checksums. fontkit cannot subset the upstream CID-keyed CFF font correctly, hence the TrueType build. The exporter reads it through the `loadFallbackFont` port, only when a run needs it: the app fetches it from its own origin as a separate asset (no CDN, Content-Security-Policy unchanged), and Node (the MCP server, the tests) reads it from `fonts/` beside the bundle or from the package (`@caotang/pdf-fonts/node-loader`). The byte checks (`checkFontBytes`, `sfntFromWoff`) and the fontkit helpers are in `@caotang/pdf-fonts`, which the screenplay PDF uses too. Emoji are set in a further fallback, Noto Emoji Regular 3.002 (OFL-1.1, monochrome), in `vendor/noto-emoji` (`@caotang/font-noto-emoji`): the variable font Google Fonts publishes, pinned by commit and checksum and instanced at weight 400 into a static TrueType WOFF (566 KB) by a pinned script that keeps its GSUB ligatures. It is read through its own port, `loadEmojiFont`, the same way and only when a sheet holds an emoji. Text is resolved per grapheme cluster (`Intl.Segmenter`; `emojiStyleOf` in `packages/pdf-fonts/src/emoji.ts`, the classifier the screenplay PDF uses too): a cluster in emoji presentation (RGI emoji, VS16, keycaps, flags, skin tones, tags, joined pictographs, `Emoji_Presentation`) goes to the emoji font; a pictograph whose default is text, or one with VS15, tries Helvetica, then Noto Sans Mono CJK, then the emoji font. Each emoji cluster is laid out with fontkit's `font.layout`, so ZWJ sequences, skin tones, flags, keycaps and tag sequences draw as the font's ligature; a ZWJ sequence with no ligature draws as its parts, as UTS #51 recommends: 90 of Emoji 15.1's 108 "facing right" people (the woman and man walking, kneeling or running, and everyone with a white cane or in a wheelchair); the person walking, kneeling or running facing right has a ligature. The emitter embeds both fonts itself (`packages/exporter/src/cid-embedding.ts`, over the CID-font writer in `@caotang/pdf-fonts` that the screenplay PDF uses too), each as a Type 0 font over a fontkit TrueType subset with a CID per distinct glyph-and-text pair, a CIDToGIDMap and a ToUnicode entry carrying the exact text, because pdf-lib's embedder writes ToUnicode from fontkit's glyph code points, which a monochrome ligature leaves short (👍🏽 would copy as 👍) and which gives two characters that share a glyph (‧ and ・) one entry. A test lays out every fully-qualified emoji of Emoji 15.1 (`emoji-test.txt`), the version the font supports, and prints them all in a sheet without one `?`. A character no font has is drawn as `?`, and the compile log names each one; so is every character whose font cannot be read, with the reason. Line wrapping in the plan works on grapheme clusters: it counts a wide character as one em and an emoji as 1.3 em (Noto Emoji's advance), breaks between Chinese and Japanese characters and between emoji (Korean breaks at spaces), never inside a cluster, with closing marks kept off the start of a line; the emitter cuts a line that overflows with the real fonts' widths. Noto text has no bold, and Han characters take their SC forms, since the build keeps no layout features. PNG and JPEG pictures are embedded once each; a WebP picture, a picture whose file is gone and bytes the engine cannot read show the card's caption (`imageAlt`, or "No image"), and the log names the picture. A selection with no shot is refused, as the shot list is.
  - **Acceptance:** the tests read the PDF back with `pdf-lib` (page count and size, embedded images, metadata, the fallback fonts' subsets and their ToUnicode text, one CID per emoji sequence, and the Emoji 15.1 coverage). No visual check against a PDF reader is automated.
- Animatic MP4: **parked** (frames × durations + audio = derived render; valuable but heavy — revisit with prompt-pack usage). NLE EDL export: **parked**. Both recorded, not specced.

## 7. Evals (headless, mock provider)

- `shots.derive`: fixture script → deterministic proposed-shot assertions on mock scripts (count, field shapes, anchor capture points); plan-card tree diff shape; approval → folder + node creation asserted via project-format validation.
- `shots.annotate`: batch validation failure (unknown id / bad enum) → pre-execution plan rejection; inverse-undo restores prior metadata.
- Coverage check fixtures: covered/uncovered script lines, missing-duration shot, stale anchor (§4).
- Export fixtures: CSV row order + escaping; contact-sheet layout smoke (headless PDF, page count sane).
