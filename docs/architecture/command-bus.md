# Command bus & undo — the spine every module talks through (v1)

> Status: built. §9 lists every one of the registry's 60 command names (`packages/bus/src/command.ts` `COMMAND_NAMES`).
> Cross-refs: tool registry = [agent-harness.md](agent-harness.md) §3 · write-ahead snapshots = [project-format.md](project-format.md) §4 · edit anchors = [edit-anchors.md](edit-anchors.md) · usage ledger = [provider-gateway.md](provider-gateway.md) §6.

## 1. Purpose

One in-process bus. UI gestures and agent tools both emit commands onto it; **no module mutates project state except by executing a command**. This is what makes "agent drives the app" safe (same surface as the human), auditable (activity log), and reversible (undo groups).

Non-goals: no network in the bus (the gateway owns transport); no cross-worker bus in v0.1 (a background task stages drafts on the main thread and never issues a command, agent-harness §2; a delegated agent never issues one either: it reads, and a write it wants is a proposed step that reaches the bus only as a step of the parent turn's approved plan, agent-harness §2, "Delegate"); **no event-sourcing** — undo is compensation-based (§5), rejected alternative: full event log (weight without v0.1 benefit).

## 2. Command envelope & descriptors

```ts
interface Command {
  id: string;                 // "cmd_" + 10 chars Crockford base32 (same generator family as node ids)
  name: CommandName;          // from the registry (§9; 60 names)
  params: object;             // flat, enum-constrained, schema-validated
  issuedBy: 'user' | 'agent';
  turnId?: string;            // agent turn this command belongs to (agent-issued only)
  callId?: string;            // tool-call id; idempotency key within the turn (§6); the MCP server mints a fresh pair per request, and answers a retry from its own cache keyed by the caller's `_meta` key (extensibility §9)
  createdAt: number;          // epoch ms; log/display only — never affects behavior
}

interface CommandDescriptor {
  mutates: 'project' | 'view' | 'none';   // view = ephemeral UI state (selection, scroll, active doc) — never persisted
  agentRisk: 'read' | 'write-auto' | 'write-confirm' | 'never';   // gate for issuedBy='agent' (§4)
  undo: 'inverse' | 'compensable' | 'none';   // §5
  validate(params, snapshot): Result<NormalizedParams, CommandError>;   // pure, total — runs BEFORE any effect
  postconditions?: Postcondition[];           // checked after apply; harness §7 reuses these
  guardsRevision?: true;                      // §6 — opt this command into the revision backstop (below)
}
```

- `guardsRevision` is §6's opt-in, and it is declared on **exactly the rows whose Params carry `expectedRevision?`** — `doc.write`, `editor.insert`, `editor.replaceRange`. A flag rather than a params-shaped rule, because a rule keyed on the params makes a *new* document-writing command silently unguarded. It is checked **after** the §4 gate and **before** `apply`, against the same snapshot `validate` was given: the last point at which a refusal still has §3's zero partial effects, and the reason the common path reads once.

- `validate` is pure and total: a command that passes validation cannot fail **mid-apply** for validation reasons. Batch commands (`binder.restructure`, `codex.write`) validate the whole batch first and list failures per-op (agent-harness §3). The three storyboard rows read the snapshot's manifest directly, so a snapshot without one fails loudly in `validate` rather than standing their state checks down.
- `mutates: 'view'` commands skip undo registration and appear in the activity log as non-undoable view events.

## 3. Execution pipeline (fixed order)

```
validate → permission gate (§4) → apply → postconditions → undo-group registration (§5)
        → activity-log append (§8) → subscriber notification
```

- Synchronous in-process (v0.1); the only async boundaries live **inside** a single command's apply (provider call, export emit) and are awaited by it.
- **`executeAsync`.** A command whose apply awaits — `mcp.invoke` reaches an external server — is dispatched through `executeAsync`, which runs the same admission, gate, register, log and notify steps around the awaited apply. `execute` still refuses an apply that returns a promise, and it refuses a command declared `asyncApply` before anything runs; either refusal names `executeAsync`, so no synchronous caller changes. `executeAsync` runs both kinds of command.
- **`ApplyRefusal`.** An apply that refuses on purpose throws `ApplyRefusal` carrying the `CommandError` the caller should get. On either entry point the bus returns that error, with the command id and, if the apply had already captured an effect, the undo group added to its details, so the refusal is not reported as an internal defect. Any other throw from an apply is an internal error, and it names the undo group an effect left behind. The exporter's refusals are `ApplyRefusal`s, so a refused compile writes no undo group and no activity row.
- Failure at any step aborts with **zero partial effects** (validate-first discipline).
- Subscribers (binder tree, corkboard, inspector, editor, agent panel, codex panel) receive post-commit notifications with command id + affected node ids, and **re-render from the store, never from command params** — single source of truth.

## 4. Permission gate

- `issuedBy: 'user'` — a UI gesture is its own confirmation; only destructive commands (`project.deleteNode`) add an explicit confirm dialog (UI responsibility).
- `issuedBy: 'agent'` — gated by `agentRisk`:
  - `read` → auto.
  - `write-auto` → auto, undo-registered.
  - `write-confirm` → allowed only inside an **approved plan** or a **one-step confirm card** (agent-harness §2); mid-plan new confirm-class calls pause with a delta card.
  - `never` → refused with a model-facing error naming the corrective path (e.g. deletion → "propose it in your report; deletion is UI-only").
  - The writer's **agent rules** (agent-harness §4) run in the harness before dispatch, in the order hard-deny, deny, ask. They need the binder tree, which the gate does not have, so the gate stays pure over `(descriptor, command, context)` and is not changed: a deny or an ask never reaches it, and a rule can only refuse a call or ask for a card the gate would have let through.
- **Grant inheritance (compound tools):** compound tools execute their sub-mutations *inside their own apply step*, not as separate bus dispatches — internal primitives (`editor.replaceRange` inside `scene.draft`) inherit the compound tool's granted permission and are never individually gated. Direct agent emission of a `never`-class command is refused even inside approved plans.
- **Allowlisted primitives (agent-harness §3, "Primitives as deferred tools"):** a short set of primitives is exposed as tools of their own, each gated *as its command is*: the tool's risk is the descriptor's `agentRisk`, so a `write-confirm` primitive still needs the approved plan or the confirm card and a `write-auto` one applies at once. They dispatch as ordinary agent commands and never under an inherited grant. The set is the harness's `PRIMITIVE_TOOLS`; the commands that may never be on it (every delete, `doc.write`, `editor.insert`, `editor.replaceRange`, `view.*`, `project.importAsset`, `shot.importImage`, `shot.importImages`, `asset.import`, `asset.importBatch`, `codex.importBatch`, `mcp.invoke`, the four `skill.*` commands) are `NeverExposed` in the harness types, so naming one does not compile.
- **Hard-deny, non-approvable by any flow** (mirrors Claude Code's "actions no mode auto-approves" list): network egress beyond the configured provider endpoint; deleting nodes or codex entries (a memory note is the same class: `memory.forget`); mutating provider profiles; leaving project scope.
- **Permission modes decide cards, never the gate** (agent-harness §4). `PermissionContext` has no mode: `approvedPlan` and `confirmed` are facts about the flow, set when a plan or one-step card is approved, and a mode that approves a card sets the same facts the writer's approval does. Every mode leaves the hard-deny list, the `never` class and the param-dependent refusals (a dismissal) exactly as they are.

## 5. Undo & the checkpoint framing

- **One agent turn = one undo group; one user gesture = one undo group.** Compound tools sub-group internally (per-doc compensations inside `synopsis.fill`) but expose a single entry.
- Undo executes compensations **in reverse order** within the group:
  - `inverse` — the descriptor generates the exact inverse command (meta sets, renames, moves, attach/detach).
  - `compensable` — the command captured a restore artifact at apply time: doc **body snapshot** before any text mutation (retention budgets → **§5.1**), codex entry prior-state copy, emitted export filename (undo = delete from `exports/`). An undo of a body write puts the snapshot's body back **as a write**: the document's `revision` moves up by one, as it does for any mutation, and is never set back to the number the snapshot recorded (project-format §4). §6's `expectedRevision` therefore cannot match a number the document had before newer text.
- **Step-tagged entries and `undoFrom`.** An `UndoEntry` registered by an agent command carries the command's `callId` (`entryFor` in the pipeline copies it); a user gesture's entry carries none. `UndoStore.undoFrom(groupId, callId)` is "restore to before one step": it selects the first entry whose `callId` equals `callId` or starts with `callId + ':'`, which covers a compound tool's sub-commands (`callId:idx`) and a port's retries (`callId:port:N`), and compensates that entry and every entry registered after it in the group, newest first. The earlier entries stay applied, and the group stays on the stack while anything is left in it; a step restore that leaves no applied entry drops the group, as `undo` does. It uses the same `isReplaying` flag as `undo`, so an inverse it dispatches registers no entry of its own, and the same failure rule: an entry that fails stays, in registration order, with the group. A `callId` no entry carries is `not-found` and changes nothing. The match is on `:` and not `.`, because `p.1` is a prefix of `p.10`. The id a step was dispatched under may differ from the id of its status card: a plan names a step `<plan>.<index>`, a mixed plan's native run `<prefix>.s<k>.<index>`, and a one-step card uses its own id, so the harness records, per turn, the call id each card dispatched ([agent-harness.md](agent-harness.md) §5) and never rebuilds one from model or server text. A step is a menu entry over the turn's existing row: retention still counts one checkpoint per turn ([§5.1](#51-snapshot-retention-budgets)), and a step costs no snapshot of its own.
- **Independence rule: restoring one checkpoint and keeping the edits after it.** A body snapshot is a full body and is never re-based, so a restore has always taken back every later group first (`restoreBefore`). `restorePlan(groups, activity, target, ancestorsOf)` (`restore-plan.ts`, pure) asks whether that is needed and returns `exact` only on a positive proof, else `with-later`, naming the later groups, the groups that block it and the node ids that overlap. The target is a whole group or one step of it (`fromCallId`). The proof: (1) **every command** of the target entries and of every later group is on an explicit allowlist of commands with a precise node footprint (`FOOTPRINT_CLASS`: the body writes `doc.write`, `editor.insert`, `editor.replaceRange`; the node-field writes `binder.setMeta`, `binder.setSynopsis`, `notes.set`, `notes.append`, `binder.rename`; and `binder.move`); any other command (codex, vocabulary, recipes, project fields, coherence, export, mcp, create and delete, anything unclassified) is a global touch and gives `with-later`; (2) **every entry has an activity row** of the same command and call whose `affected` names the nodes, and a missing row, a row with no `affected`, a defect row on the group or a group not on the stack gives `with-later`; (3) **no later group wrote the same node**, a document's body included, even when the text regions look disjoint; (4) **no structural meeting**: a move touches the node and the child lists of its old and new parent, and the check is symmetric: a later write to a node whose parent the target's move changes (or the reverse), two moves under one parent, or a move of an ancestor of a node the other side touched all give `with-later`. Only the node-level rule is built; a text-level rebase of a snapshot is not. `FOOTPRINT_CLASS` is a `Record<CommandName, …>`, so a new command name does not compile until it is classified, and a test fails if the table and the closed set differ. The planner is gated by a property and differential test over the real commands (`packages/store/test/restore-plan-property.test.ts`): for random undo stacks, an `exact` plan never coexists with measured touches that meet, and after the restore every node and child list a later group changed is byte-identical to before and the project equals one in which the target never ran. The app proves the plan again after saving the writer's typing (`ProjectSession.restorePlanFor`, `restoreExact`) and refuses, changing nothing, if the typing now meets the change or any document is still unsaved after the save (typing the planner cannot see is never proved independent, so the plan is `with-later`); a failed compensation stops there and is reported.
- **Checkpoint framing:** each agent turn renders in the activity log as a checkpoint row — **"restore to before this turn"**. One click = undo the group. Redo = v0.2 nice-to-have (store group inverses; not required for v0.1's promise).
- **Two-lane undo:** Lane 1 = editor-native `prosemirror-history` for user keystrokes (untouched); Lane 2 = every bus text mutation applied as one transaction batch tagged `tr.setMeta('addToHistory', false)` + the per-turn/autosave snapshot. Agent edits and snapshot restores are **never replayed by the user's Ctrl+Z**; "restore to before this turn" is snapshot-based, so checkpoint rows stay immune to in-editor undo position drift. The restore confirmation states scope explicitly (edits made after the turn are included in the restore, unless the independence rule above proves the restore exact, when the dialog also offers to keep them). Full contract + fixtures: [editor-engine.md](editor-engine.md) §7. Regression-tested sharp edges: excluded-transaction-then-undo bookkeeping, appended-transactions-during-undo, metadata lost on redo replay.

### 5.1 Snapshot retention budgets

Unbounded checkpoint storage is the failure this prevents: full snapshots only when a body changed, a count cap and an age cap, and each document's first snapshot kept as the baseline. The adopted ladder:

1. **Full body snapshots, not deltas.** Bodies are 1–10k words; delta machinery is complexity without a measured need at this scale. (Revisit only if real corpora show otherwise — the eval suite would surface it.)
2. **Cap: 100 checkpoints per project** (Claude Code's number, validated at far higher churn than a writing session produces). Oldest evicted first. Config-exposed (`retention.checkpointCap`, default 100).
3. **Retention: 30 days** (same clock as `cleanupPeriodDays`; a checkpoint past either limit is evicted). Config-exposed (`retention.checkpointDays`, default 30).
4. **Snapshot-on-write dedupe:** a body unchanged since the last snapshot is not re-stored — the checkpoint references the existing snapshot (Obsidian's changed-files-only rule).
5. **First-snapshot-per-doc preserved:** while any later snapshot of a doc exists, its first snapshot is never evicted (the diff baseline — Claude Code's exact rule; makes per-doc history reconstruction cheap).
6. **Orphan cleanup on eviction:** deleting a checkpoint removes any snapshot no remaining checkpoint references (this is the rule that prevents unbounded growth).
7. **Storage:** the IndexedDB runtime store, never the artifact (project-format §1 — snapshots are derived, rebuildable, never trusted).
8. **Surfaced budgets:** Settings › Data shows checkpoint count + estimated size + a one-click "trim to cap now" (the user-visible guarantee that the cap is real).

Determinism: eviction is a pure function of (checkpoint list, cap, days, today-injected) — headless-testable; the eval suite holds an eviction fixture (100+ checkpoints → cap respected, first-snapshots preserved, zero orphaned snapshots).

## 6. Idempotency & concurrency

- **callId dedupe:** replays of the same `callId` within a turn return the cached result without re-execution. Cache is per turn, cleared at turn end.
- **Optimistic concurrency:** document-writing commands carry optional `expectedRevision` (per-doc `revision` counter, project-format §4). Mismatch → `CommandError('revision-conflict', 'doc was modified since plan (rev N → M)')`; the edit-anchor ladder (edit-anchors.md §3) is the first line of defense, revisions are the backstop.
- **A save to a project folder is a second concurrency check, and it refuses rather than writes.** The folder is another writer's too: a save into it is held back when the folder changed since this session last loaded or saved it. The verdicts are `locked` (a lock file: the Caotang MCP server may hold the folder), `changed` (`caotang.json` was changed or removed), `unknown` (a folder holding another project, which this session never held a copy of), `earlier` (a folder holding this project's own earlier save, with no copy of it held in this session or kept across a reload in the app database), and `files` (a document or codex file was changed, removed or added, named by its title in the question). Nothing is written until the writer answers: `lockConfirmed` and `overwriteConfirmed` are the answers, and a `files` refusal found part way through the write is `partial`, with the files before it written. A change found only after the write finished (a file another program changed while the save wrote, `caotang.json` replaced, or a lock that appeared) is a refusal marked `after`: the save was written, and the next save asks. What a confirmed save replaces is copied first to `.caotang-backup/<time>/` and the `saved` outcome names that folder (folder-guard.ts). The session log is written before any project file, so a log the folder cannot take refuses the save with nothing written. The digests the check compares are the writer's own copy (lifecycle `saveFolder`, folder-digests.ts). A folder holding the book a separate copy was made from refuses the copy's save outright, whatever the writer answers; a folder holding this project's own id is checked against the copy kept for it across a reload, so it is saved straight away when unchanged and never called another project (project-format §8). The `files`, `unknown` and `earlier` questions also offer "Save as a new folder…", which saves into an empty folder the writer picks (project-format §8). Accepting a recovery of a folder makes the same check (§5 of project-format).

## 7. Error shape

```ts
interface CommandError {
  code: 'invalid-params' | 'not-found' | 'cycle' | 'revision-conflict' | 'permission-denied'
      | 'hard-denied' | 'limit-exceeded' | 'io-error' | 'postcondition' | 'internal';
  message: string; // model/user-facing: names the corrective surface, never a bare code
  correctiveHint?: string;  // e.g. "use binder.read_tree to list valid ids"
  details?: object;         // per-op failures for batch commands
}
```


- Postcondition failure is **never** silently auto-undone: the harness verify ladder (agent-harness §7) decides retry vs structured report; the undo group stays intact and user-reversible either way.

## 8. Activity log

One entry per executed command:

```ts
interface ActivityEntry {
  at: number; command: string; issuedBy: 'user' | 'agent';
  turnId?: string; callId?: string; undoGroupId?: string;
  source?: 'native' | 'mcp';                      // set for the MCP client (extensibility.md §2/§6); default 'native' — externals tag 'mcp'
  affected: { nodeId: string; title: string }[];   // human titles, not bare ids
  tokensSpent?: number;      // agent turns only (gateway ledger feeds it)
  summary: string;           // digest: "moved 3 scenes into Chapter 4"
  defect?: 'late-undo-capture';  // a defect row: the command named was NOT executed again
}
```

**A defect row is not a second execution.** One entry per executed command is the rule for the *rows that report an effect*, and a defect is not an effect: it is the bus reporting that an apply did something the spec does not allow. The one defect row in v0.1 is the late undo capture — an apply that stashed its undo scope and captured from a timer, an event or a floating continuation, after the dispatch settled. Its row carries the `defect` marker and **no undo group**: the dispatch's registration is closed, so the payload was dropped.

**The marker is in the data; the rendered surfaces do not show it yet.** A reader of the log's *entries* — the bus's own `ActivityEntry`, and any structure that keeps the entry — can tell a defect row from an execution by the marker, and the row belongs to no group. The activity panel and the Markdown export below do not render the marker: a defect row appears there as an ordinary change row, so a reader counting rows in the *rendered* output still counts an execution. The L6 conversation-memory block (`packages/context/src/layers/turns.ts`) renders no rows at all — it merges the rows' own summaries into a single `Outcome:` line — so the marker never reaches that line: what lands there is the defect row's own summary, which announces the drop in prose. That gap is in the renderers, not in the log.

**One defect row per dispatch, and the first late capture is the one reported.** The defect is the capture, not how many there were, and a scope stashed on a high-frequency timer would otherwise write a row per capture into a session-lifetime log.

The log keeps every row it is given. The Activity panel shows a 200-row window of it, and the Markdown export carries every row that is not a `view.*` command (agent-harness §5).

The `agentRisk` and `undo` columns are the descriptors' own (`packages/bus/src/descriptors*.ts`), and the owning spec for each is named in its notes.

**The Params column is a closed set, not a minimum.** A key a command does not list is **refused** with `invalid-params`, never accepted-and-dropped. The word in the header above is "essentials"; a reader that picked the fields it knew and ignored the rest is the behaviour §2's "schema-validated" annotation rules out. Two consequences the reader of this table should know:

- **The refusal is what makes the codex provenance rule (codex.md §2) enforceable.** `codex.upsert`'s ops are held to their own field set the same way, and `origin` is the load-bearing one: provenance is harness-owned from `context.issuedBy`, so an op naming its own is refused rather than quietly written with the harness's value.
- **The refusal names the key and the accepted set** (§7's corrective surface), and a batch is validated as a whole with failures listed per-op (§2), so one bad key costs one round trip rather than one per key.
- **Scope: the rule above governs the top-level keys of `params`, plus the nested shapes *this table spells out*, and one nested object is outside it.** `binder.setMeta`'s `patch: {status?, label?, …}` is written out here, and `codex.upsert`'s `entries: CodexUpsert[]` names a type whose field contract [codex.md](codex.md) §2 states — so both are held to a closed set (`PATCH_KEYS`, `CODEX_OP_KEYS`), each refused per-op. **`editor.replaceRange`'s `range` is the exception: this table says `range` and nothing more**, so there is no interior set for the code to hold it to, and `{from: 0, to: 3, length: 99}` validates today with `length` silently dropped.

`view.*`'s `various` is the only row this table does not spell out; those three shapes are declared in `packages/bus/src/params.ts` (`DECLARED_PARAMS`) and held to the same rule, and a test asserts the exemption is exactly those three rows.

**`mcp.invoke` ([extensibility.md](extensibility.md) §6).** External tool calls ride this row. Its `agentRisk` is the external tool's effectiveRisk, read-auto or write-confirm and never write-auto, so the table's `write-confirm` is the default and the per-call `read` is the exception described in its notes. `undo: 'none'` and `mutates: 'none'`: externals are not project state, and the bus still gates, audits and dedupes the agent action. A call that was sent and then timed out or was cancelled fails with `details.mayHaveActed: true` (unless the tool is a trusted read): the server may have done part of the work, and no caller may report the call as having changed nothing. The harness hands the turn's `AbortSignal` to the awaited call, so a Stop reaches it; this is the one started command a Stop interrupts, because it has no project change to leave half-applied (agent-harness §2).

**`mcp.readResource` ([extensibility.md](extensibility.md) §6, §4 rule 8).** The one command whose caller is always the writer. It is `agentRisk: 'never'`, so the gate refuses `issuedBy: 'agent'` before anything runs, and its `validate` refuses a call without `pickedBy: 'writer'` besides: two closures, so a descriptor change that loosened one would still meet the other. `undo: 'none'` and `mutates: 'none'`, like `mcp.invoke`. The descriptor in the registry is the bus's floor (closed key set, the literal); the store registry replaces it with the MCP client's, which also checks the URI against the server's live listing and the template's pin.

## 10. Evals (headless)

Scripted command sequences → final-state assertions (project-format schema) → **undo-replay assertion**: undo-all ⇒ byte-equal snapshot of pre-script state → permission-matrix assertions (each `never` command refused for agent, allowed/destructive-confirmed for user) → error-shape assertions (codes + corrective hints) → callId-replay dedupe assertions.
