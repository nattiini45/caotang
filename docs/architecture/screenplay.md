# Screenplay — document kind + Fountain render pipeline (post-v0.1)

> Status: built, except where a section says otherwise. §5.3's PDF renderer is built and compiled as the `pdf` export format.
> Scope: Attaches to `project-store`/`binder` (a document kind), `editor` (decoration styling), `exporter` (three renderers), `coherence` (mention/check feed).
> Cross-refs: kind vocabulary = [project-format.md](project-format.md) §2 media-additive note · exporter recipe shape = [exporter.md](exporter.md) §2/§3 · body projection & anchors = [project-format.md](project-format.md) §3 + [edit-anchors.md](edit-anchors.md) §2 · findings model = [coherence.md](coherence.md) §3/§5.1 · context layers = [context-assembly.md](context-assembly.md) §2.

## 1. Verdict (adopted)

**Screenplay = a document kind + exporter recipes, never a separate module.** Fountain is to screenplays what Markdown is to novels: the ownable plain-text storage format. The "separate screenwriting module" alternative is rejected — Fountain files *are* the binder (sections = folders, scene headings = scene documents, `=` synopses = the synopsis field), and formatted output is a compile target like DOCX.

**First-landing scope (v0.1-of-track):** Fountain as first-class doc kind (editor + structure import) · Fountain/FDX import · Fountain export · paginated PDF at the exporter gate. **Post-track:** FDX *production* half (revision marks, colored/locked pages, scene-number locking — the later FDX-production stage).

## 2. Data model

### 2.1 Document kind

```ts
tree[].kind: 'screenplay'        // documents only; absent = 'prose' (project-format §2 media note)
// body file: docs/<id>.fountain — raw Fountain source for THIS scene (one scene heading per file)
```

- **Scene-per-node, not script-per-node.** A screenplay document node holds one scene (its heading + following elements). Rationale: mirrors the novel model exactly (one editor instance per document node — editor-engine §12's per-scene split applies unchanged), makes corkboard/inspector/filters/coherence work per scene with zero adaptation, and each file is valid standalone Fountain (opens in Beat/Highland).
- **A full-script `.fountain` import is a structure op, not a storage mode:** parse → binder tree (see §3); Caotang never stores a monolithic script file. Export reassembles the whole script from scene files in binder order.
- **Fountain-native annotations stay in body text:** `[[inline notes]]` and `/* boneyard */` are preserved verbatim in the file and never rendered in formatted output (fountain.io semantics). Screenplay docs do **not** use Caotang's `%%`/`@` Markdown-annotation conventions (editor-engine §13) — `[[…]]` is the kind's native equivalent, kept for interchange fidelity.
- **Front matter redundancy (project-format §3)** applies unchanged: `id/title/status/label/keywords/synopsis` in YAML; the body below is Fountain.

### 2.2 Structure mapping (the file ⇄ binder contract)

| Fountain construct | Binder mapping | Formatted output |
|---|---|---|
| `# Act` / `## Sequence` (Sections) | folder nodes (created on import) | **never emitted** (structure lives in the tree; Caotang emits its own `#`-sections on export from folder titles — see §5.2) |
| `INT./EXT. — LOCATION — TIME` line | document node, `kind: 'screenplay'` | scene heading (styled element) |
| `= synopsis line` under a heading | node `synopsis` field (manifest + front matter) | **never emitted** |
| `[[inline note]]` | stays in body text | never emitted |
| `> transition TO:` / `CUT TO:` | body text (element type at parse) | styled element |
| `DANIEL ^` dual cue | body text of the scene file | side-by-side columns at render |
| `===` forced page break | body text | honored at pagination |
| `Key: value` title-page block | **template variables** (`{title}/{author}/{date}` — exporter §2); NOT stored per file | title page at compile |

Round-trip rule: **import maps file → tree once; export emits tree → file.** The binder synopsis field is the single synopsis truth (the `=` line is consumed on import; regenerated on export from the manifest). This is the project-format §3 doctrine (structure never duplicated into prose files) applied to Fountain: `=`-lines in body text are tolerated on load (treated as import residue, re-synced to the manifest synopsis with a one-time notice) but are not a second truth.

### 2.3 Element model (parse layer)

```ts
type ScreenplayElement =
  | { type: 'scene_heading'; text: string; forced: boolean }
  | { type: 'action'; text: string }
  | { type: 'character'; text: string; dual?: boolean }        // cue line; dual = caret pair second
  | { type: 'parenthetical'; text: string }
  | { type: 'dialogue'; text: string }                          // lines following a cue until blank line
  | { type: 'transition'; text: string; forced: boolean }
  | { type: 'centered'; text: string }
  | { type: 'page_break' }                                      // '==='
  | { type: 'section'; depth: 1|2|3; text: string }             // only inside imports (consumed)
  | { type: 'synopsis'; text: string }                          // only inside imports (consumed)
  | { type: 'note'; text: string }                              // [[…]] — preserved, never rendered
  | { type: 'boneyard'; text: string }                          /* … */
  | { type: 'title_page'; entries: Record<string, string> }     // only at file start of an import
```

Parse is **lenient with zero hard failures** (fountain.io philosophy, adopted as a contract): every unparseable line degrades to `action`, never an error. Forcing characters (`. heading`, `! action`, `@ cue`, `> transition`) are honored and stripped on output. Element inference order per fountain.io: heading prefix (INT/EXT/EST/INT./EXT or `.`) → transition (`TO:` suffix or `>`) → cue (uppercase line followed by non-blank text) → parenthetical (inside dialogue block) → else action.

## 3. Editor integration

**Decision: raw-Fountain text editing + live decoration styling — no element-typed ProseMirror schema in the first landing.** The screenplay body edits as plain text (Highland/Beat's proven model); a parse pass derives element spans per document and drives **decoration styling** (same decoration machinery as mention/finding rendering, editor-engine §14 conventions). Rejected for the first landing: extending the Caotang PM schema with `scene_heading`/`dialogue` node types + a Fountain↔PM serializer (a second remark-prosemirror-scale boundary; unjustified until inline element surgery is proven needed — revisit only with usage evidence; the parse layer is the seam that would host it).

- **Body projection** = the raw Fountain text (project-format §3 coordinate system unchanged): `doc.read` ranges, edit anchors, and mention detection all address Fountain characters directly. No new coordinate system.
- **Decorations** (styling only — never mutating text): scene headings (bold + underline), cues (bold, uppercase as typed), parentheticals (muted), transitions (right-aligned visual class), centered (centered), page-break marker. Live re-parse on **debounced idle** (800 ms autosave cadence, editor-engine §9) — never per keystroke; a 110-page script parses in the single-digit-ms class (line-based state machine; benchmark-gated like any parser pick, §7 A4).
- **Element palette / autocomplete (writer-facing):** Enter-after-cue → parenthetical/dialogue continuation; Enter on empty dialogue → back to action. Tab-completion of cue names from codex characters (deduped against previous cues in-file). The Source tab also has an element menu (Ctrl+E, or Cmd+E on a Mac, or the Element button) that rewrites the caret's line as one of nine elements through `convertLine`, and a chord per element that does the same from the text: Ctrl+Shift+1..9 on Windows and Linux, Cmd+Alt+1..9 on macOS, digit N being the Nth entry of `LINE_ELEMENT_TYPES` (the menu's digits). The chord matches `event.code`, needs exactly the platform's modifiers, and is ignored while AltGraph is down, while composing and on key repeat; it is handled only in the Source field, never in the global keymap. A line that already is the element is left as it is, and one that cannot be it posts a status line and changes nothing. There is no Section or Synopsis chord: sections and synopses are the binder's. These are editor affordances over the parse layer, not new commands.
- **Scene navigator:** the parse's scene-heading list drives a navigator strip (Highland/Scrivener pattern) — view-only; the binder tree remains the structural truth.
- **Pages: a paginated page view that becomes an editor, in milestones** (owner decision, reversing the earlier verdict of no paginated WYSIWYG page view; docs/decisions.md). The source stays the raw Fountain text and the Source tab stays the one place the text changes today; the **Pages tab** draws the paginated scene (formatted, paginated, ≈Highland's Go-to-Preview) from the same pass as the renderers, and each line it draws that prints an element carries that element's source range (§5.3, `LayoutLine.source`). **Milestone 1, built:** a line (click, or Enter on the focused line) opens its element in the Source tab with the caret at the element's start, scrolled into view; the tab writes nothing. **Next, not built:** an editor on the page itself. It must keep to the rules the mapping sets: it writes only the mapped Fountain range, through the same autosave path as the Source tab; generated text (`(MORE)`, `(CONT'D)`, page and scene numbers, the title page) is never editable; an edit whose range no longer holds the text it was opened on (the agent applied or undid a change) is refused with a notice, not applied to the wrong characters; and the Enter and Tab behaviour on the page is specified here before it is built. *As built:* a script page is a grid of the page's occupied rows, blank rows collapsed, each line at its `LayoutLine.x` in characters; the two sides of a dual pair carry the same paginator rows, so they share a grid row and stand side by side, while the DOM keeps the paginator's array order (left speech whole, then right speech whole). A scene number takes its heading's row.
- **Ghost preview / `scene.draft` / anchors:** work unchanged — the agent reads and writes Fountain text through the standard tools; the scene draft's role text (`sceneRole`, context-assembly L0) carries a screenplay note, chosen by the doc's kind and the mode: a draft asks for Fountain with the scene heading kept, and a passage asks for its Fountain alone. No new context layers (L3/L4 synopses already come from the manifest tree).
  - **The note by mode (as built).** A `draft` of a screenplay scene writes the whole scene, so its role asks for the Fountain with the scene heading (INT. or EXT.) kept. A `continue` or a `rewrite_selection` writes one passage of a scene that already has its heading, so its role asks for that passage's Fountain only, with no heading, no title and no note. A second heading inside a scene is a defect. Prose scenes keep the prose role in every mode.

## 4. Mention & coherence integration (free cross-medium payoff)

- **Character cues are a mention source:** the parse layer emits cue names as detection terms for the per-doc `MentionIndex` (codex.md §4) — additive detection surface keyed on `kind: 'screenplay'`; same cache, same invalidation on doc write.
- **Deterministic coherence checks ride the existing namespace** (coherence.md §5.4 — adding a check is a spec change, never a runtime plugin): `script.cue-collision` (a cue name matching no codex entry → info finding prompting codex creation, the `pov.coverage` pattern), `script.cue-consistency` (same character cued with mixed case/spelling variants → warning naming both spellings — alias discipline). Both are pure arithmetic over the parse output + codex; zero model calls.
- **Cross-medium consistency (script ↔ storyboard ↔ branches)** activates when storyboard and branching-dialogue artifacts exist (coherence.md §11): the deterministic class compares screenplay scene coverage against `shot.covers` refs (storyboard.md §5).

## 5. Export (three renderers at the exporter seam)

All three sit behind the exporter's closed recipe shape (exporter.md §2); `format` enum widens additively: `'fountain' | 'fdx' | 'pdf'` join at the screenplay-track gate. Recipes are per-format as everywhere else; **title page** emits from template variables `{title}/{author}/{date}` as Fountain key-value block (Fountain/FDX/PDF) — never stored per file.

### 5.1 `FountainRenderer` (identity — the stored file *is* Fountain)

```ts
interface FountainRenderer { emit(blocks: FlatBlock[], opts: { title: string; author?: string; templateId?: string }): Promise<Blob>; }
```

- Stage-2 flatten blocks map 1:1: `chapter` → `# <title>` section line; `scene` → the scene file's Fountain body verbatim (guaranteed valid — it was parsed from Fountain); `separator` → blank line (screenplays don't use `***` — the template's `separator` option is ignored for screenplay formats with a compile-log note).
- **Round-trip acceptance gate:** export(import(X)) for a fixture corpus of whole-script Fountain files is byte-identical modulo the documented synthesis (sections from tree, `=`-lines from synopsis). Same bar class as the project-format §8 acceptance test.
- Undo/error semantics = exporter §5 (`export.compile` confirm-gated, artifact in `exports/`, auto-versioned filenames).

### 5.2 `FdxRenderer` (import-first, v0.2-of-track; emit at the FDX-production gate)

- **Import (v0.1-of-track):** `.fdx` → typed paragraphs → element model → scene nodes + tree. `SceneProperties` (`Length` eighths, `Page`, `Title`, `CharacterArcBeats`) are preserved **informationally** into `shot`-less scene metadata only where a slot exists (length → computed word/minute estimate note in the compile log); unknown sub-elements ignored (loaders-tolerant rule). A numeric character reference that names no character XML allows — a surrogate, a control character, U+FFFE or U+FFFF — stays as it was written, as an unknown entity does. Community parsers exist for import (rsdoiel/fdx reads Final Draft/Trelby/Celtx/FadeIn output) — study-first, vendor-if-dormant posture (the parser-pick pattern, §7 A4).
- **Emit (v0.2-of-track):** paragraphs → `<Paragraph Type="…">` XML; scene numbers/revision marks/locked pages are production conventions with **no Fountain representation** — scoped to the FDX-production stage (which subset a credible FDX export emits vs normalizes). The `FdxRenderer` seam is reserved now; that stage decides its field set.

### 5.3 `PdfRenderer` (paginated — the hard artifact)

- **Layout constants (industry standard, fixed for v1):** 12pt Courier Prime (embed font, OFL); US Letter 8.5×11″; margins: left 1.5″, right 1.0″, top 1.0″, bottom 1.0″; ~55 lines/page (leading single-spaced); action full width; dialogue indent 1.0″ from left margin, width 3.5″; cue indent 2.2″; parenthetical indent 1.6″, width ~2.0″; transitions flush right; page number top-right from page 2. *(Constants table sourced from the quoteunquoteapps/screenweaver guides; verify against afterwriting's output at the parser and PDF-engine benchmark gate, §7 A4.)*
- **Page-break rules (the hard part, deterministic):** scene headings never orphaned at a page bottom; cues never separated from their first dialogue line; dialogue splits only at sentence ends with centered `(MORE)` at the page bottom + `CHARACTER (CONT'D)` cue at the next page top; parentheticals stay with their cue where possible; transitions never at page top. These are the fixture list for the render test suite (each rule = a positive + negative fixture).
- **Source ranges.** Every `LayoutLine` has `source: TextRange | null`, the span `[from, to)` of the Fountain text of the element the line prints, taken from the parser's `range` on the element it was given (an element with none gives `null`). It is the whole element, forcing character included: each wrapped line of a paragraph points at the paragraph, a cue uppercased for print points at the cue as typed, a dialogue split across pages by `(MORE)` and `(CONT'D)` keeps one range on both sides of the split, and each column of a dual pair points at its own element, so the right column never maps into the left. Generated lines have `null`: `(MORE)`, `NAME (CONT'D)`, the page number, the scene numbers and every title-page line. The renderers (`pdf.ts`, `fdx.ts`) ignore the field, so their output is byte for byte what it was.
- **Engine:** a Caotang-owned pagination pass over the element stream (pure function: elements + constants → pages) + a PDF emitter (`pdf-lib`-class library, lazy-loaded at the exporter edge — the DOCX/EPUB lazy-import pattern; exact pick joins the benchmark gate with the parser decision, §7 A4). afterwriting's MIT pipeline (aw-parser + PDF stage) is the studied reference implementation; vendor-if-dormant applies.
- **Options (recipe/template):** scene numbers on export (left/right/both, off by default — Final Draft's number-scene command is a *compile-time* feature; Scrivener's years-long scene-number request confirms it never lives in the editor); title page on/off; `(CONT'D)` handling on/off.
- **NOT in scope at any gate:** revision marks + colored/locked pages (the FDX-production stage), a page-accurate preview (blank rows kept) and print CSS. Parked explicitly.
- **As built.** The `pdf` export format compiles this renderer (exporter.md §5).
  - **Engine.** No PDF library. The pagination pass is `paginate.ts`, and the writer is `pdf.ts`: uncompressed content streams of positioned text in Courier Prime and, where the script needs it, the CJK fallback. The one dependency is `@pdf-lib/fontkit` (pinned, 1.1.1), which cuts the fallback's subset. It loads with the fallback, never for a Latin-only script. The fallback fonts are not this package's: the CJK and emoji files are the two the storyboard contact sheet uses (`vendor/noto-sans-cjk`, `vendor/noto-emoji`), read through a `FontLoader` the host passes (the exporter's `loadFallbackFont` and `loadEmojiFont`) and cut and written with `@caotang/pdf-fonts`, the package both PDFs share for byte checks, fontkit helpers, the CID-font writer and the coverage tables. A compile with no loader prints what the font would have printed as `?`, and says so. The benchmark of A4 is therefore moot for the emitter. A script with no printed page still writes one blank page: PDF 1.7 §7.7.3.2 asks the page tree to hold at least one page, and a reader refuses a file whose page tree is empty. The refusal of a selection that prints nothing is the exporter's gate, not the writer's (exporter.md §5).
  - **Font.** Courier Prime Regular (A3) is embedded whole as a TrueType font program (`FontFile2`, written in hexadecimal so the file stays ASCII). The font module is loaded by a dynamic import when a PDF is drawn, so the editor bundle never carries it, and nothing is fetched: the font travels inside the app. Its metrics are tested against the font's own tables.
  - **CJK fallback.** A character WinAnsi cannot encode prints in Noto Sans Mono CJK SC 2.004 (OFL), a Pan-CJK font with Hanzi, kana and Hangul. The file is `vendor/noto-sans-cjk` (`@caotang/font-noto-cjk`), the upstream CID-keyed CFF font converted to TrueType and stored as a 10.7 MB WOFF by a pinned script (source URL and SHA-256s in its README), the same file the contact sheet embeds. The build keeps the font's `locl` feature and the glyphs it reaches, so a Han character can be drawn in the form of the project's language: `hanLocaleTag` (`@caotang/pdf-fonts`, han-locale.ts) turns the language into an OpenType language system tag (`ja` into `JAN `, `ko` into `KOR `, `zh-Hant`, `zh-TW` and `zh-MO` into `ZHT `, `zh-HK` into `ZHH `; `zh`, `zh-Hans`, `zh-CN`, `zh-SG`, no language, a malformed tag and any other language into none, the font's own Simplified Chinese forms), and the subset takes each character's glyph from fontkit's `layout(char, undefined, 'hani', tag)`, which is one glyph for one Han character or fullwidth punctuation mark, so the one CID per character and the ToUnicode map stay as they are. `PdfRenderOptions.language` is the project's language, the one the right-to-left rule reads; the exporter passes it from the project's Project details. With no tag a character takes the cmap glyph, as before. Only the glyphs the script uses are embedded: a TrueType subset as a Type 0 font (`CIDFontType2`, `FontFile2`, `Identity-H`, a `CIDToGIDMap` and a `ToUnicode` map), so the text copies and searches. Each character has its own CID, so two characters the font draws with one glyph (‧ U+2027 and ・ U+30FB) copy back as themselves, each with its own width. The font, fontkit and the subsetter load by a dynamic import, only when the layout holds such a character and the host gave a loader. In the browser the file is a build asset on the app's own origin; under Node (the MCP server) it is read from `fonts/` beside the bundle, or from its package. **Two files.** The font comes as the full file and a common file cut from it to the characters of everyday use (`common-charset.txt` in `vendor/noto-sans-cjk`: the font's non-Han characters, the 2,350 Hangul syllables of KS X 1001, and 4,460 Han characters from Unihan, 1,956,568 bytes against 10,692,940, within a build budget of 2 MB). The host's loader is the full file's and carries the common file's as `common` (`withCommon`, `@caotang/pdf-fonts`); `loadNotoCjk` reads the common file when every character the layout sets in the font (`fallbackCharacters`) is in it (`cjkLoaderFor`, `@caotang/pdf-fonts/common`, whose table is the common file's cmap), and the full file when one is not. A character the full font has and the common file lacks is printed like any other, with no "?" and no note, and the PDF holds the same font program from either file, so what a PDF contains never depends on which file was read; the layout's coverage table (`noto-cjk-coverage.ts`) stays the full font's. A loader with no `common` is read as it was. A Latin-only file is byte for byte what it was before the fallback, and a test holds it to that.
  - **Width rule.** The grid is Courier at 10 characters to the inch. A character whose Unicode East Asian Width is Wide or Fullwidth takes two columns (14.4 pt); every other character takes one. Wrapping, centring, right alignment and run placement all count columns. A fallback glyph starts at its cell's left edge and advances the cell's width. Indents, column widths and the 54-line page are unchanged.
  - **Line breaks.** A line breaks at white space, and also between Chinese or Japanese characters (Han, kana, CJK punctuation, fullwidth forms), except before a closing mark (`。`, `、`, `」`, small kana, `ー` and the like) and after an opening mark (`「`, `（`). Korean breaks at spaces, as Latin text does; a Hangul word wider than the column breaks between syllables. `。`, `！` and `？` end a sentence for the dialogue split, with no space needed after them.
  - **Emoji fallback.** After Courier Prime and the CJK font, emoji print in Noto Emoji Regular 3.006 (OFL), Google's monochrome emoji font: the static wght=400 file the Google Fonts API serves, as a WOFF in `vendor/noto-emoji` (`@caotang/font-noto-emoji`; source URL, size, build command and SHA-256s in its README), the same file the contact sheet embeds, and, like the CJK font, a common file beside it (`common-emoji.txt` in `vendor/noto-emoji`: the fully-qualified emoji that are one code point, from the groups Smileys & Emotion, People & Body, Animals & Nature, Food & Drink and Symbols, and the keycaps; 298,992 bytes against 579,236, within a budget of 300 kB). `loadNotoEmoji` reads it when every unit the layout sets in the font is one of those (`emojiLoaderFor`); a ZWJ sequence, a skin tone, a flag, a tag sequence or an emoji of another group reads the full file and prints the same. Its outlines are TrueType, so the subset is a `glyf` font, written as the CJK subset is (`CIDFontType2`, `FontFile2`, `Identity-H`, a `CIDToGIDMap` and a `ToUnicode` map). The font, fontkit and `emoji-font.ts` load by a dynamic import, only when the layout holds an emoji the font prints and the host gave a loader; the file is a build asset on the app's own origin in the browser (the CSP is unchanged) and `fonts/` beside the bundle in the MCP server and the `.mcpb`.
  - **Emoji as clusters.** Text is measured and broken in units: a code point, as before, or a grapheme cluster that is an emoji (`Intl.Segmenter`; `emoji.ts` in `@caotang/pdf-fonts`, the one classifier both PDFs use): one starting with an emoji-presentation character, a keycap, or a pictograph with U+FE0F, a ZWJ, a skin-tone modifier or a tag. U+FE0E, or a text-style pictograph alone (`©`, `❤`), is text: Courier Prime, then the CJK font, then Noto Emoji. A cluster is laid out with fontkit's `font.layout` (the font's GSUB), so a ZWJ sequence, a skin-tone sequence, a flag, a tag sequence or a keycap is one glyph; failing that the selectors and tones are dropped, and failing that the first emoji prints (a sequence newer than the font; the log says so). The woman and man walking, kneeling or running facing right are one glyph in the font that fontkit does not reach (its layout stops at the parts), so `emojiLayoutGlyph` (`@caotang/pdf-fonts`) gives the glyph HarfBuzz lays them out as from a table that `scripts/emoji-coverage.mjs` generates with harfbuzzjs, a devDependency of that package, and it is tried first; nothing loads HarfBuzz when a PDF is written. The font draws them without a gender sign. Each distinct cluster has its own CID and its ToUnicode entry is the whole cluster, so the text copies back as typed even where clusters share a glyph (the font has no skin tones). A cluster is never split across fonts or lines.
  - **Emoji width.** An emoji cluster takes two columns (14.4 pt), whatever its code points' East Asian Width; so does a character only Noto Emoji has. It is set at 10 pt, the glyph centred in its cell, so it fits the 12-pt line. A line may break before or after an emoji, never inside one. A Latin-only file is byte for byte what it was, and a test holds it to that.
  - **Arabic and Hebrew.** After the CJK font and before the emoji font, Arabic, Persian, Urdu (basic letters; Nastaliq is not drawn) and Hebrew print in Noto Sans Arabic 2.013 and Noto Sans Hebrew 3.001 (OFL), the static TrueType files of notofonts releases in `vendor/noto-sans-arabic` and `vendor/noto-sans-hebrew` (`@caotang/font-noto-arabic`, `@caotang/font-noto-hebrew`; each README names the release, URL and SHA-256), read through the host's `loadArabicFont` and `loadHebrewFont` and loaded, with the shaper and bidi-js, only for a document that holds the script (`rtl-font.ts`, a dynamic import). The pieces are in `@caotang/pdf-fonts`: `rtl-script.ts` (which characters each font prints, from coverage tables generated by `scripts/script-font-coverage.mjs`, and how a line is cut into runs), `bidi.ts` (`bidi-js` 1.1.0, exact pin: the paragraph direction by rules P2 and P3, levels, the line reordering of rules L1 and L2, the mirroring of rule L4; checked against a slice of `BidiCharacterTest.txt` 13.0.0, the Unicode version bidi-js implements) and `shaper.ts` (`Shape(text, font, direction, script)` returning glyph ids, advances and offsets; the only module a HarfBuzz backend would replace). The backend is `@pdf-lib/fontkit` 1.1.1. A spike against HarfBuzz 1.6.3 on the vendored fonts (`scripts/shaping-spike.mjs`, with its golden result in `packages/pdf-fonts/test/fixtures/shaping/`) found unmarked Arabic and Hebrew identical glyph for glyph, and marked text different in about half the samples, one of which throws. A mark (Unicode category Mn of the two scripts: the Arabic harakat, shadda and dagger alef, the Hebrew points and cantillation) is therefore left out of the shaped word and counted in the compile log, and the file's text keeps it. An engine failure is a run printed as `?`, never a failed export. A word is a run of letters of one font (its marks and joiners with it); each digit or punctuation mark of a script is a run of one column. A run's width is its shaped advance at 12 pt, rounded up to whole Courier columns (`ceil(advance / 7.2)`), with the spare room on the side the run ends. **Direction.** A paragraph (one element) takes its direction from its first strong character; with none, from `project.language` (`ar`, `fa`, `ur`, `he`, `yi` read right to left), and only in a document that holds Arabic or Hebrew. A right-to-left paragraph is right-aligned inside its own column (the dialogue's columns 10 to 45, a dual column, the cue's, the action's), its lines are marked `rtl`, and a mixed line is reordered per UAX #9 at the paragraph's direction. The page is not mirrored: margins, indents, transitions, page numbers, scene-number sides and the order of dual dialogue stay as they are, because that is a claim about industry practice that nobody here can check; it waits for a native reader, and is then a separate, reversible export option. **Layout.** `layoutPdf(blocks, options, measure?)` stays synchronous and pure; the optional `measure(run)` returns a run's columns, and `withMeasure` holds it for the call. Without one a word counts a column for each letter, which is the layout a compile plans with before any font is read (the gate and the page count in the log); `preparePdf` then loads the shaper and the fonts and lays out again with the measure, and the exporter logs the measured page count when it differs. Units of text with Arabic or Hebrew are grapheme clusters (`Intl.Segmenter`), so a line never splits a letter from its marks; other text splits as before. Sentence ends for `(MORE)` include U+061F, U+06D4 and U+061B. The lines of a paragraph are resolved one at a time at the paragraph's direction. **Writing.** Each line with either script, or in a right-to-left paragraph, is written from a plan of runs in logical order, each at its column. A word is set glyph by glyph at the shaper's positions (a text operator would drop a mark's offset), the glyphs left to right in their visual order, in a CID font written by the shared `cid-font.ts` with a CID for each (glyph, text) pair. **Text for a reader.** The runs of these two scripts carry no `/ActualText`. Each glyph has the letter it draws in its ToUnicode entry, which is how Word and LibreOffice write right-to-left text, and a reader puts the word back in logical order by its own bidirectional rules (pdf.js and Poppler do, as the CI job checks; Acrobat is the reader this was written for and has not been run). `/ActualText` was tried first and is wrong for Poppler (Evince, Okular, `pdftotext`): it spreads the text over the word's box from left to right and then reverses a right-to-left word as it does any other, so it returned `ةراس` for `سارة` and `םולש` for `שלום`. The text of a glyph is the letter of the run matched to it (`clusterTexts` in `shaper.ts`): fontkit 1.1.1's own report of a glyph's code points is the first text that ever used the glyph (a medial beh was reported as a noon), and the pieces of a dotted letter have none, so the letters, in the order of the text, are matched to the glyphs that advance (the drawn order reversed for a right-to-left run); the positioned dots Noto Sans Arabic draws as glyphs of their own, and a joiner's blank, advance 0 and have no text of their own. **The CIDs of glyphs with no text.** A glyph with no ToUnicode entry is not a glyph with no text to pdf.js: it reads the character whose number is the CID (`toUnicode.get(code) || code`), so the dots came out inside the word as control characters, and as a space, a letter or a digit once the file held more than 31 CIDs. Mapping them to U+200B, which pdf.js skips, was tried and is wrong for Poppler: the character sits on the dot's own line and cuts the word into pieces (`رأيت` came out in three, the last on the next line). So in Arabic and Hebrew a glyph with no text takes a CID that is itself a format character (category Cf) pdf.js skips, from a list of 38 (`CidNumbering` in `cid-font.ts`: U+00AD, U+0600 to U+0605, U+061C, U+06DD, U+070F, U+200B to U+200F, U+202A to U+202E, U+2060 to U+2064, U+2066 to U+206F, U+FFF9 to U+FFFB), has no ToUnicode entry, which Poppler ignores, and the other CIDs count up around them; the CID-to-glyph map and the widths are written for the sparse CIDs. Past the 38th distinct glyph (Noto Sans Arabic has about as many dot glyphs in all, a document uses far fewer) it falls back to a counted CID with a U+200B entry. Devanagari's later glyphs of a cluster have counted CIDs and the U+200B entry (the words carry `/ActualText`, which Poppler uses instead). `tools/pdf-validate` removes U+200B, and no other character, from what pdf.js and Poppler give back, and a test reads a file with more than a hundred CIDs through pdf.js untouched. A run whose advancing glyphs are not one for each letter (a ligature of the font, none in the two vendored fonts today) is one cluster, the whole run on its first glyph. A mark that is not drawn (harakat, Hebrew points) and a ZWNJ or ZWJ is a glyph of its own that draws nothing (the font's space glyph, advance 0) and carries the character as its ToUnicode text, set after its letter in logical order (`withMarkGlyphs`): a copy keeps it, and a reader that reverses a word character by character puts it back after its letter. pdf.js appends a mark to the text item that is open and never starts an item with one, so a mark after the last letter of a right-to-left word, which is drawn first because it sits at the word's left end, was read into the item of the word drawn before it (or, with an item of its own, came out before its word). Those glyphs are flagged `final` (`ShapedGlyph.final`) and written after the word, between `/Span BMC` and `EMC`, which ends the open item: pdf.js gives the word's item and then the marks' item, in logical order, so a search or a selection joins them (`كَتَبَ`), and Poppler, which places characters by position, is unaffected; a test reads such words through pdf.js and the corpus holds them whole. Digits and punctuation of the scripts are runs of one glyph. A line's runs are written in logical order, so the order of the words in the stream is the order of the text. `/ActualText` stays on Devanagari words (written left to right, one text for a cluster whose glyphs are drawn out of order) and on a plain run drawn with a mirrored bracket. A bidirectional control character prints nothing. Arabic digits are runs of one column each. **Evidence.** Machine only: pdf-lib's read-back of the glyphs' ToUnicode texts, and in CI's `pdf-validate` job pdf.js and Poppler's `pdftotext`, which must give back every Arabic and Hebrew word of the corpus in logical order (`tools/pdf-validate`), and BidiCharacterTest. Machine-verified, not reader-verified; Acrobat is not among the readers it ran on.
  - **Devanagari.** Hindi, Marathi, Nepali and Sanskrit print in Noto Sans Devanagari 2.007 (OFL), the static TrueType file of the notofonts release in `vendor/noto-sans-devanagari` (`@caotang/font-noto-devanagari`; its README names the release, URL and SHA-256), read through the host's `loadDevanagariFont` and loaded only for a document that holds Devanagari (`rtl-font.ts`, a dynamic import). Text cannot print one code point per glyph here (conjuncts, the short i drawn before its consonant, reph, stacked marks), so a word is shaped by upstream `fontkit` 2.0.4 (exact pin, behind `shapeWord` and `BrahmicShaper` in `@caotang/pdf-fonts/indic-shaper`, lazily imported for Devanagari alone) in the project's language, which selects the font's Marathi and Nepali forms (`locl`). Subsetting stays on `@pdf-lib/fontkit` 1.1.1: glyph ids belong to the font. HarfBuzz is the reference, not a dependency: `harfbuzzjs` 1.6.3 is a devDependency of `@caotang/pdf-fonts`, and a test shapes 42 fixtures (the gate's strings, the nukta both ways, a Marathi and a Nepali `locl` case, common words) with both engines and compares glyph id, advance and offsets (`test/fixtures/shaping/devanagari-*.json`). They agree on all but one case, a half form asked for with a joiner (`क्‍ष`), whose advance differs by 59 units; the test records it. fontkit 2.0.4 keeps a glyph cache keyed by glyph id that holds the first code points it saw, so a run could shape differently after another; the shaper empties it before each run, and a test shapes after every other fixture and compares. `@pdf-lib/fontkit` 1.1.1 is not used to shape: its Indic shaper throws `regeneratorRuntime is not defined`. The CSP is untouched: fontkit is pure JavaScript, with no WebAssembly and no `eval`.
  - **Brahmic units.** Text with a character of a Brahmic block (U+0900 to U+0DFF, Vedic Extensions, Devanagari Extended) is measured and broken in extended grapheme clusters, with the conjuncts whole (क्ष, त्रि, न्दी, क़): `Intl.Segmenter` finds them and `joinConjuncts` (`brahmic.ts`) joins a cluster that ends in a virama to the consonant after it, so correctness never rests on the engine knowing UAX #29 GB9c (Unicode 15.1). A combining mark with no consonant takes no column. Latin, CJK and emoji units, and Latin-only files, are as they were. Another Brahmic script is cut into clusters too and still prints as `?`.
  - **Devanagari on the grid.** A Devanagari word is a run of the clusters the font prints; its shaped advance at 12 pt snaps up to whole Courier columns, the spare room on its right, and `measure` is the same one Arabic and Hebrew use. A line breaks at spaces; a word wider than the column breaks only between clusters. The danda and double danda (U+0964, U+0965) end a sentence for the dialogue split, so `(MORE)` and `(CONT'D)` can split a Hindi speech after them. A line that holds Devanagari is planned (`planDevanagariLine`): words shaped and drawn glyph by glyph at the shaper's offsets (a text operator drops them) in font F6, the rest plain. Each word is wrapped in `/ActualText` with the typed text, and the first glyph drawn of each cluster carries the cluster's text in ToUnicode (the clusters the shaper gave, never the glyph order: a reordered short i or a reph is drawn out of place), so a reader that ignores `/ActualText` still copies the typed text. A cue in Devanagari needs a `@` in front, as one in Arabic does: Devanagari has no case, and the parser is not changed. The Marathi, Nepali and Hindi forms differ in the file. Not verified by a native reader, and not in Acrobat.
  - **Unprintable characters.** A character no font has prints as `?`, and the compile log names it; an uncovered emoji is one `?` in its two columns. The layout reads coverage tables generated from the fonts (`packages/pdf-fonts/scripts/cjk-coverage.mjs` and `emoji-coverage.mjs`, the latter also from Unicode's `emoji-test.txt` 17.0, the version the pinned Noto Emoji supports; a test fails when the list is newer than the font), so the log knows before the fonts load. The Arabic, Hebrew and Devanagari tables are generated from the fonts by `scripts/script-font-coverage.mjs`, so a script with a font is no longer named and a script without one (Tamil, Bengali, …) still is. A test checks that every fully-qualified emoji in that list prints.
  - **Lines.** 54 lines a page: (11 − 1 − 1) × 72 / 12. The spec's "~55" is this figure.
  - **Page numbers.** The title page is not counted and has no number. Script pages count from 1, and the number is printed at the top right from page 2, as `2.`.
  - **Dual dialogue.** A pair prints in two columns of 27 characters from the same row, with a three-character gutter. The cue wraps at 23 characters, so neither cue reaches the other column or the right margin. A pair is atomic: it moves to the next page whole. A pair taller than a page is laid as its two blocks in sequence, under the dialogue rules.
  - **Options.** `sceneNumbers` (`off` by default, `left`, `right`, `both`) and `continued` (on by default) are recipe options; the title page is the recipe's `titlePage`. A heading's own `#n#` number is printed when it has one.
  - **Not drawn.** Bold or underlined headings (the layout constants name none), A4 pages, a choice of font, the mirrored page of a right-to-left project, Arabic and Hebrew marks, Nastaliq, Noto Naskh, a localised `(MORE)` and `(CONT'D)`, and the Indic scripts other than Devanagari (Bengali, Gurmukhi, Gujarati, Odia, Tamil, Telugu, Kannada, Malayalam, Sinhala), which print as `?` until each has a font.
